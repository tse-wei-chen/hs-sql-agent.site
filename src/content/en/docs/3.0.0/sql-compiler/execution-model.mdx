## Bounded compilation and schema evidence

Compilation rejects input beyond 4,194,304 UTF-16 units, 131,072 non-End lexer tokens, 8,192 grouping levels or the 65,536-node AST budget. Iterative AST traversal and bounded rendering preserve parameter ordering and fail-closed semantics across the six providers; they do not guarantee arbitrary SQL depth.

Resource budgets include 8,000,000 work units per stage, 32,000,000 per compilation, 30 seconds per stage, 90 seconds per compilation and 536,870,912 cumulative managed allocation bytes per stage. These are compilation budgets, not database query timeouts or process memory limits. Typed resource diagnostics identify rejected work.

An opt-in immutable schema snapshot resolves table/column names and proven type families, including ordered CTE/derived projections, and binds its digest into the plan fingerprint. This is bounded proof, not a full database type checker. Schema-bound DML requires a live freshness verifier; missing or changed schema proof fails closed. The default runtime remains snapshot-free. `AddHsSqlAgentNativeDmlSchemaFreshness()` provides opt-in native support.

hs-sql-agent does not treat generated SQL as a trusted command. The execution boundary is designed around parse, validation, capability checks, access policy, and provider-specific compilation.

## Query path

At a high level, query execution follows this flow:

1. Authenticate the MCP key and apply its database, table, tool, and execution scope.
2. Parse the supported SQL into a structured definition / AST.
3. Validate the statement and its supported source semantics.
4. Check the target/provider capabilities needed to preserve those semantics.
5. Compile and render SQL for the configured database provider.
6. Execute within the configured runtime limits.

The SQL compiler implementation contains explicit source-validation and target-capability stages. Unsupported syntax or a capability that cannot be proven is rejected instead of being silently replaced by a superficially similar construct.

## Why fail closed?

Cross-database SQL is full of constructs that look equivalent but differ in null behavior, type rules, operator semantics, pagination, identifiers, functions, or DML behavior.

For an AI-facing execution surface, "best effort" rewriting is dangerous because a statement can remain syntactically valid while changing meaning. hs-sql-agent therefore prefers a visible rejection over an implicit semantic downgrade.

## Provider-specific output

The public MCP surface is shared, but the final SQL is provider-specific. Current database providers are:

- PostgreSQL
- MySQL
- SQL Server
- Oracle
- SQLite
- Firebird

Support is intentionally bounded. A provider being supported does not mean every syntax feature from that database is accepted; individual compiler capabilities are expanded only when their semantics are represented and validated.

## Native GROUPS window frames

PostgreSQL 11+ and SQLite 3.28+ can compile a `GROUPS` window frame for an aggregate such as `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW)`. `GROUPS` advances by groups of rows tied on the ordering key, rather than by individual rows (`ROWS`) or numeric ordering ranges (`RANGE`). The compiler requires an explicit window `ORDER BY`, rejects invalid frame bounds and explicitly older server versions, and never silently substitutes another frame unit. MySQL, SQL Server, Oracle and Firebird are not admitted for this capability. A compiled plan does not prove the actual database runtime version; the Host must verify it before execution.

## EXCLUDE: native window frame membership

PostgreSQL 11+ and SQLite 3.28+ support four explicit frame exclusions after a `ROWS`, `RANGE` or `GROUPS` frame: `EXCLUDE CURRENT ROW` omits only the current row; `EXCLUDE GROUP` omits the current row and all peers sharing its window ordering values; `EXCLUDE TIES` keeps the current row but omits its other peers; `EXCLUDE NO OTHERS` explicitly retains every row in the frame. For example, `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW EXCLUDE TIES)`. Even with `ROWS`, exclusion still considers peers. The F# compiler and structured `WindowFrameDefinition.Exclusion` preserve these distinctions without rewriting SQL semantics. Explicitly outdated versions, and MySQL, SQL Server, Oracle or Firebird source/target providers are rejected. Compilation alone cannot attest the live server version; the Host must check it before execution.

## SQL Server RANGE frame offsets

SQL Server's T-SQL source grammar does not allow numeric `PRECEDING` or `FOLLOWING` offsets in a `RANGE` window frame. For example, `RANGE BETWEEN 1 PRECEDING AND CURRENT ROW` is rejected as **invalid SQL Server source syntax**, even if the target is PostgreSQL or SQLite. Legal `ROWS` offsets and `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` remain supported. PostgreSQL and SQLite retain their own native numeric `RANGE` semantics. The compiler checks source dialect validity separately from target rendering rather than treating the target's features as proof that the original SQL was valid.

## Bounded filtered COUNT for MySQL and SQL Server targets

A PostgreSQL-source query such as `SELECT COUNT(*) FILTER (WHERE status = 1) FROM orders` can now be compiled into a safe conditional aggregate for MySQL or SQL Server. MySQL uses `COUNT(CASE WHEN ... THEN 1 END)`; SQL Server uses `COUNT_BIG(CASE WHEN ... THEN 1 END)` to preserve 64-bit counts. `COUNT(direct_column)` is also supported, retaining SQL NULL handling, zero results for an empty match set and frame-sensitive window counts.

This is **not** general support for `FILTER`: only unqualified `COUNT(*)`, direct local-column counts and non-window `COUNT(DISTINCT direct_column)` with bounded local column/literal predicates are proven. `SUM`, computed count arguments, subqueries, volatile functions and outer references remain rejected. Raw MySQL/SQL Server source SQL containing `FILTER` is still invalid; the translation is for an eligible source dialect such as PostgreSQL, not permission to accept unsupported input syntax. SqlCore does not execute SQL or grant database access.

## Bounded conditional DISTINCT COUNT

A PostgreSQL-source `COUNT(DISTINCT amount) FILTER (WHERE status = 1)` now lowers to MySQL `COUNT(DISTINCT CASE WHEN status = 1 THEN amount END)` or SQL Server `COUNT_BIG(DISTINCT CASE WHEN status = 1 THEN amount END)`. Unlike plain `COUNT(amount)`, duplicates are counted once; NULL and unknown/false predicates contribute nothing, and an empty qualifying set returns zero. This is proven on grouped and global integer fixtures against PostgreSQL 16, MySQL 8.4 and SQL Server 2022.

The input must contain exactly one direct local-column DISTINCT operand and a bounded local predicate. Calculated operands, additional DISTINCT arguments, subqueries, volatile functions and correlated references remain rejected. **`COUNT(DISTINCT ...) FILTER (...) OVER (...)` is not allowed**: MySQL and SQL Server do not support DISTINCT window aggregates. The source `FILTER` syntax is still invalid for MySQL and SQL Server, regardless of target capabilities. Differences in string collation and provider-specific type coercion are not covered by numeric parity tests. No SQL execution or permission is granted.
