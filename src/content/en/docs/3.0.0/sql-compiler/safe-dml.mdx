## Admission, uncertainty and target evidence

When selective predicates are required, provably always-true `UPDATE`/`DELETE` filters such as `WHERE 1=1` are denied. Human approval still binds the exact plan and row-set evidence.

Custom challenge stores must atomically implement `TryPromoteAsync` for both single and batch operations. Redis and durable resume use versioned envelopes; incompatible challenges need fresh preview and consent. See the [upgrade guide](/docs/reference/upgrade-guide).

`dml.commit_outcome_unknown` and `dml.rollback_outcome_unknown` are distinct non-retryable outcomes. Preserve approval and target evidence for independent reconciliation. Neither absent witnesses nor missing Redis keys prove rollback; never automatically replay an uncertain mutation. An audit persistence failure after a known commit must not be reported as a failed mutation.

`AddHsSqlAgentTargetExecutionFence()` is opt-in and requires target provisioning plus separate proof that old workers lost DML authority. Enrolled commits execute two additional rollback-only readiness transactions on the actual connection and two independent post-commit Admission/Witness reads. Oracle uses READ COMMITTED only for the witness unique-conflict diagnostic; other readiness phases use SERIALIZABLE. Contradictory proof yields an unknown outcome. This does not provide fleet-wide enrollment or automatic live-worker reconciliation.

DML uses a stricter execution path than queries because approval must still describe the **same mutation evidence** when the server reaches commit.

## One tool, single or multi-statement

`execute_dml_sql` accepts one or more supported `UPDATE`, `DELETE`, or `INSERT ... VALUES` statements. Multiple statements are separated by semicolons.

There is no separate batch-DML tool. A multi-statement request is parsed as one batch, approved once, executed in its original order, and committed atomically inside one server-owned transaction.

Transaction-control SQL such as `BEGIN`, `COMMIT`, and `ROLLBACK` is not accepted from the client. The server owns transaction boundaries.

## What approval binds

For `UPDATE` and `DELETE`, approval binds to the exact primary-key row set observed during preview. Every statement is revalidated immediately before its mutation inside the commit transaction.

For `INSERT ... VALUES`, approval binds to the immutable literal payload and exact compiled command. `INSERT ... SELECT` remains unavailable until source-rowset approval semantics are defined.

If an earlier statement changes the row set that a later statement was approved against, the entire batch fails closed and rolls back.

## Approval providers

MCP Elicitation remains the default first-party provider. Hosts can also use the official `HsSqlAgent.Approvals.Webhook` adapter or implement `IDmlApprovalProvider` with `HsSqlAgent.Server`.

Approval providers receive transport-neutral evidence, not SQL execution primitives. They do not receive the database connection, transaction, validated execution plan, or commit authority.

## Durable pending approvals

A provider may return `Pending` for an asynchronous workflow. When the Admin Store capability is available, hs-sql-agent persists protected resume intent and approval fingerprints.

When a later completion arrives, hs-sql-agent reloads current authorization and database configuration, reparses and previews the DML, compares the approved evidence, and creates a fresh short-lived execution challenge. Changed authorization, database configuration, policy, plan, row set, or affected-row evidence makes the request stale instead of committing it.

The completion path therefore resumes **intent**, not an old database session.

## SQL Server: composite INT keys in CTE-based mutations

An explicitly opted-in SQL Server UPDATE or DELETE may read a physical source through one to three linear, nonrecursive CTEs when the source has a verified **two-column, non-null INT primary key or unique index**. Both key columns must be projected unchanged and in physical index order through each CTE. The final mutation must match both distinct target INT columns using mandatory `AND` and ordinary `=` predicates. A real SQL Server catalog check, a bounded row-set preview, approval binding and a same-transaction metadata recheck are required before execution. A parsed query or virtual catalog is not execution evidence.

Missing or reordered keys, OR-only conditions, casts, nullable or computed keys, filtered/disabled indexes and multiplying joins remain unsupported. This does not expand other providers or authorize arbitrary multi-column joins.

### Exact linguistic collation and UNIQUE comparison (G9/M05, develop only)

SQL Server's physical CTE UPDATE/DELETE proof now supports bounded built-in `VARCHAR(n)` and `NVARCHAR(n)` under four **independently identified comparison contracts**: `Latin1_General_100_BIN2` (binary, existing), `Latin1_General_100_CI_AS` (case-insensitive/accent-sensitive), `Latin1_General_100_CI_AI` (case/accent-insensitive), and `Latin1_General_100_CS_AS` (case/accent-sensitive). The source UNIQUE index, target comparison column and any separately attested physical JOIN table must match **the exact native type, bounded length and actual column collation at every key ordinal**. A typed Text snapshot alone grants no permission; F# closes the equality classes into distinct key cases and checks actual `sys.columns`/`sys.indexes` evidence.

Real SQL Server 2022 tests compare whether inserting case- or accent-variant duplicates violates the UNIQUE index with whether ordinary `=` matches the same values. UPDATE/DELETE with 1–3 CTE steps, complete AND key relationships, mixed text/UUID/numeric keys, independent Preview→Approval→Commit, and transaction-held `IsCurrent` still apply. Nullable source UNIQUE remains conditional on `ANSI_NULLS ON`. A new **v9 ProofIdentity** invalidates older approvals. Different collations (including supported-but-mismatched classes), explicit `COLLATE` overrides, implicit VARCHAR/NVARCHAR conversion, unproven CS_AI, _SC and _UTF8, CHAR/MAX, filtered/disabled indexes and incomplete equality stay fail-closed. No new MCP tools, privileges or capability grants to the other five databases.


### Nullable SQL Server UNIQUE keys with ordinary equality (G9/M05, develop only)

A SQL Server source key can now contain a nullable column **only when an actual enabled, unfiltered physical UNIQUE index covers the entire ordered 1–2-column tuple**. The bounded CTE `UPDATE`/`DELETE` proof must retain mandatory ordinary `AND`/`=` predicates against the target and a live session with `ANSI_NULLS ON` (checked through `@@OPTIONS`). A NULL source component makes ordinary equality UNKNOWN, so **it never joins a target row**. This is not NULL-safe comparison or an exception for arbitrary nullable table scans. The target-side composite proof still requires nonnullable keys, and the non-joined `VerifyLive` API cannot certify nullable source keys.

The closed F# null-semantics proof is bound to the original complete UNIQUE index, built-in exact physical types, actual source nullability, immutable metadata digest and ProofIdentity **v8**. The real commit connection and transaction recheck `ANSI_NULLS ON` along with index/schema identity using held locks. Filtered UNIQUE indexes (including `WHERE key IS NOT NULL`), disabled or nonunique indexes, `OR`, `COALESCE`, computed keys, casts, NULL-safe operators and a virtual Catalog never grant authority. Live SQL Server 2022 tests cover nullable BIGINT, DECIMAL, UUID and BIN2 VARCHAR composite keys, 1–3 CTE hops, UPDATE/DELETE, Preview→Approval→Commit, source NULL nonmatches and invalidation after index revocation. Other five providers and the default MCP tool permissions remain unchanged.


### Exact BIN2 VARCHAR/NVARCHAR physical keys (G9/M04, develop only)

SQL Server CTE `UPDATE`/`DELETE` live uniqueness assurance now supports built-in bounded `VARCHAR(n)` and `NVARCHAR(n)` **only under the exact `Latin1_General_100_BIN2` collation**. The source UNIQUE index key, target comparison column and any independently attested second physical JOIN key must agree at **every key ordinal** on the native SQL type, maximum length and physical collation. `NVARCHAR` length is checked using `sys.columns.max_length` in bytes before converting to the declared character count. This is not a blanket text-equality permission: `VARCHAR(MAX)`, `NVARCHAR(MAX)`, `CHAR`, `NCHAR`, differing lengths, Unicode-to-non-Unicode conversions, other binary or case-insensitive collations, user-defined aliases and nullable source keys remain denied.

The Host labels native strings with the existing `SqlSchemaValueKind.Text` family, but **that snapshot alone never authorizes DML**. The closed F# physical KeyTuple verifies live `sys.columns` length/collation, built-in `sys.types` identity, the complete enabled/unfiltered UNIQUE index and ordinary mandatory key equality in the bounded CTE/JOIN graph. Preview→independent Approval→Commit still rechecks the same physical metadata under transaction-held locks, and proof identity v7 makes older pending approvals invalid. Real SQL Server 2022 tests cover mixed text/UUID/numeric keys, UPDATE/DELETE, 1–3 CTE hops, self and second-table JOINs, approved commit and revoked indexes; negative cases enforce collation, length and cast boundaries. The other five databases, default MCP tools and permissions are unchanged.


### Additional non-key columns in the CTE projection (G8 / M03)

Each of the one to three CTEs may also project **direct non-key source columns** alongside the required one- or two-column INT key (up to 32 direct columns per hop). For example, `SELECT k1 AS a, payload AS extra, k2 AS b` may be followed by `SELECT a, extra, b`. Keys must retain their relative physical index order, appear exactly once at every hop and be matched with mandatory `AND`/`=` predicates. Duplicate or transformed keys, ambiguous aliases, computed expressions, multi-source or multiplying JOINs still fail closed. Physical unique-index checks, preview, approval and transaction-time revalidation are unchanged; this does not authorize general JOINs or affect other databases.

### Singleton-derived JOIN safety proof (G8 / M07, limited subset)

SQL Server may now use **one nonmultiplying JOIN per CTE hop** when the joined source is an uncorrelated derived `SELECT 1 AS marker` with **no FROM, WHERE, UNION, grouping or other rows**. A `CROSS JOIN (SELECT 1 AS marker) AS one` preserves the row count; `INNER JOIN` and `LEFT JOIN` with literal-equality `ON 1 = 1` cannot increase it. The physical INT unique-key tuple, direct key projection, bounded preview, approval and same-transaction live proof are still required. **This earlier singleton/self-JOIN proof alone does not authorize joins against different physical tables; the separate dual-live-index proof below establishes the newly allowed subset, APPLY, correlated queries, multi-row derived sources or general JOIN cardinality.**

A separate, equally narrow form permits an **INNER or LEFT self-JOIN of the same physical source table** under two distinct aliases, but only when the ON predicate contains ordinary AND-connected equality for **every component of its live-verified unique INT key**. The second alias then contributes at most one row per source row. Missing keys, OR-only matches, computed/cast keys and joins to another table still fail closed.

### Distinct physical-table JOIN with two live unique-key proofs (M07)

A SQL Server CTE may now use one **INNER** or **LEFT JOIN** against a second, different physical table. Both sources require an independently live-verified, enabled, unfiltered, nonnullable unique `INT`/`BIGINT` key tuple of one or two columns. Every source key must be matched by an ordinary, mandatory `AND`/`=` comparison to the corresponding second-table key. The physical types must match exactly per ordinal; a virtual catalog, implicit cast, partial-key equality or filtered index cannot establish uniqueness. Both index identities participate in plan/approval evidence and are rechecked on the actual commit transaction, including post-preview index revocation. This does not authorize a third physical source, many-to-many joins, `RIGHT`/`FULL JOIN`, cross-provider lowering or general arbitrary JOINs.

### Key-correlated EXISTS / NOT EXISTS filters (M07, bounded phase)

SQL Server CTE-based UPDATE/DELETE can use an **EXISTS** (semi-join) or **NOT EXISTS** (anti-join) in the first CTE's WHERE clause when it reads the **same already live-attested physical source table** under a different alias. The subquery must project a literal, perform no extra joins, grouping, ordering or set operations, and correlate **every 1–2 INT/BIGINT unique-key component** by mandatory ordinary `AND` / `=` predicates. Additional direct inner-column comparisons to literals may narrow the rows. These predicates can only filter, never multiply cardinality; the existing source-index attestation, bounded preview, approval identity and same-transaction metadata recheck remain mandatory. This does **not** permit arbitrary nested queries, another unverified table, JOIN multiplication, or general SQL Server EXISTS/anti-join execution authorization.

### Exact TINYINT and SMALLINT physical keys (G9 / M04, develop only)

The SQL Server CTE UPDATE/DELETE live proof now accepts built-in `TINYINT` (unsigned 8-bit) and `SMALLINT` (signed 16-bit) alongside `INT` and `BIGINT`. For a one- or two-column physical unique key, each corresponding source, target and independently joined key must have **the same actual SQL Server type at its index ordinal**. A wider integer, implicit cast, user-defined alias type or virtual catalog is not proof. The existing bounded CTE lineage, nonmultiplying JOIN checks, row preview, separate approval, immutable fingerprint and same-transaction index recheck remain mandatory. SQL Server 2022 tests cover update/delete, mixed key types and index revocation. This change does not enable decimal, UUID, nullable unique keys, arbitrary JOINs or any additional database provider.


### Exact UNIQUEIDENTIFIER physical key proof (G9/M04, develop only)

The SQL Server CTE `UPDATE`/`DELETE` proof now supports the **built-in 128-bit `UNIQUEIDENTIFIER` key**. This is a distinct portable `Uuid` schema value kind, **not** a number, text string or binary key. The Host reads actual `sys.tables`, `sys.columns`, `sys.types` metadata to build bounded typed source, target and optionally independently attested JOIN-key snapshots. The closed F# key algebra independently checks each unique-index ordinal and the source/target snapshot's actual type family. `UNIQUEIDENTIFIER` cannot be equated to `INT`, `DECIMAL`, `VARCHAR` or `BINARY(16)` by implicit conversion to obtain an execution proof.

One- or two-component keys may mix `UNIQUEIDENTIFIER` with exactly matched integer or decimal components; 1–3 bounded CTE hops, nonmultiplying self/physical JOINs, preview, independent approval and same-transaction `IsCurrent` re-attestation still apply. ProofIdentity advances to v6, invalidating pending older approvals. SQL Server 2022 live tests cover UUID UPDATE/DELETE, primary and UNIQUE keys, Host auto-discovery, cross-table JOIN, post-preview index revocation and mismatched-family denial. This grants no new MCP tool, default DML selection, generic JOIN capability or permissions for the other five providers.

### Exact DECIMAL / NUMERIC physical key proof (G9 / M04, develop only)

The SQL Server CTE UPDATE/DELETE live proof now also supports built-in `DECIMAL(p,s)` and `NUMERIC(p,s)`, where `1 ≤ p ≤ 38` and `0 ≤ s ≤ p`. These two SQL Server names are synonyms, but their **physical precision and scale must match at each ordered unique-key component** across source, target and any separately verified physical JOIN source. A `DECIMAL(12,2)` key does not prove a match to `DECIMAL(13,2)`, `DECIMAL(12,3)` or an integer key; SQL implicit conversion is not proof.

The Host reads actual `sys.columns` and `sys.types` metadata and verifies every column of the original UNIQUE index **without discarding unsupported alias-type columns**: a unique `(a,b)` index never establishes uniqueness for `a` alone. The sealed F# physical key-kind model includes the exact precision/scale. Existing 1–3 bounded CTE hops, nonmultiplying JOIN predicates, rowset preview, independent approval, versioned proof identity and same-transaction re-attestation are unchanged. SQL Server 2022 live tests cover fractional values, mixed integer/decimal keys, dual-physical JOINs, index revocation and precision/scale mismatch. UUID/text keys, nullable uniqueness, arbitrary joins and the other five providers remain unsupported in this proof.


## Fail-closed rules

A mutation is not committed when approval is rejected, expires, becomes stale, has a mismatched fingerprint, loses authorization, violates current policy, or cannot reproduce the approved row-set evidence.
