## 2.0.6 → 3.0.0: what breaks

- **Custom approval stores:** implement atomic `IDmlApprovalChallengeStore.TryPromoteAsync`. Sequentially consuming child challenges and registering a batch is unsafe; both single and multi-statement `execute_dml_sql` now use aggregate promotion.
- **Redis:** the approval key includes `{dml-approval}:`, with versioned `hs-sql-agent.dml-challenge` payloads (`SchemaVersion=1`). v2 keys and unversioned payloads cannot be silently reused.
- **Approval evidence:** a challenge without `ApprovalPlanBinding` is rejected. Encrypted pending resumes now use `hs-sql-agent.dml-resume` (`SchemaVersion=1`); the explicit legacy reader does **not** manufacture newly required consent.
- **Admin Store:** SQLite and PostgreSQL migrations refuse to proceed with outstanding `Pending` or `Executing` approvals. They add `AdmissionProtocolVersion`: v2 writes default to 0 and may no longer create or reopen `Pending` / `Executing`; v3 writes version 1. This does not revoke an old worker's direct target SQL credentials.
- **SQL policy:** provably always-true `UPDATE`/`DELETE` predicates such as `WHERE 1=1` are denied when selective predicates are required. Input is limited to 4,194,304 UTF-16 units and 131,072 lexer tokens.

## Safe rollout

1. Stop issuing new v2 DML previews and approvals; inventory unresolved requests and Redis challenges.
2. Stop **every** DML-capable v2 worker, resolve approvals and establish physical outcomes independently. A missing Witness, Redis key or timeout is **not** proof of rollback. Never automatically settle `Executing`.
3. Back up the Admin Store **and** the relevant encryption keys/evidence. In fleet deployments, independently withdraw old target write credentials and drain existing sessions.
4. Apply the SQLite/PostgreSQL Admin Store migration only after that drain. Upgrade every custom challenge-store implementation and all eligible workers together.
5. Request **fresh human approvals** for incompatible v2 challenges; do not replay a consumed nonce. Verify host/API integration and the six-provider CI coverage against the intended deployment.
6. Enable `AddHsSqlAgentNativeDmlSchemaFreshness()` or `AddHsSqlAgentTargetExecutionFence()` only after their separate prerequisites and target readiness tests pass. Both remain **opt-in and experimental where documented**.

## Unknown outcome and downgrade

`dml.commit_outcome_unknown` and `dml.rollback_outcome_unknown` both mean **do not retry the consumed approval**. Their API results are `outcome_unknown`, `retryable=false`; a failed audit write cannot turn an acknowledged COMMIT into a failure.

The admission-gate migration is **one-way** on SQLite/PostgreSQL. EF downgrade is intentionally blocked; any actual rollback requires an operator-managed compatible backup restore with DML workers stopped and outcomes reconciled.

`target-fence-v1` is **not** a production fleet certificate. A new-identity rollback-only probe cannot prove old worker credentials were withdrawn or authorize automatic reconciliation of `Executing`. The Oracle Witness unique-key diagnostic alone uses READ COMMITTED; other readiness phases use SERIALIZABLE.

The five canonical MCP tools are unchanged; four read tools remain preselected and DML stays opt-in.
