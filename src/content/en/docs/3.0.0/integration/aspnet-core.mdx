## Required secret protection

Configure three independent random 32-byte Base64 values before starting Docker or registering the runtime. Keep the same keys on every node and across restarts. `HMAC_KEY` and `JWT_KEY` remain separate signing secrets. Run `openssl rand -base64 32` separately for each protection key.

| Docker variable | ASP.NET Core configuration |
| --- | --- |
| `DB_ENCRYPTION_KEY` | `SecretProtection:DatabasePasswords:Keys:db-1` |
| `DML_ENCRYPTION_KEY` | `SecretProtection:DmlPayloads:Keys:dml-1` |
| `DML_FINGERPRINT_KEY` | `SecretProtection:DmlFingerprintKey` |

Set `SecretProtection:DatabasePasswords:ActiveKeyId` to `db-1` and `SecretProtection:DmlPayloads:ActiveKeyId` to `dml-1`. Missing, invalid or reused keys fail startup. Example placeholders are deliberately invalid.

`HsSqlAgent.Hosting` binds `SecretProtection` automatically. Modular hosts must bind it explicitly:

```csharp
hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
```

For new bootstrap MCP keys, provide explicit `Bootstrap:Databases:*:McpKeys:*:Key` values; startup does not generate or log them. Existing encrypted database passwords must be re-entered. Read the [upgrade guide](/docs/reference/upgrade-guide) before changing an existing deployment.

Multiple modules may call `AddHsSqlAgentCore()` on the same `IServiceCollection`. Capability configuration is accepted only on first registration; later overrides fail. Separate service collections remain isolated.

ASP.NET Core applications have two NuGet entry points. Pick the boundary you actually want the host application to own.

| Goal | Package | Ownership |
| --- | --- | --- |
| Embed the complete product | `HsSqlAgent.Hosting` | HsSqlAgent owns the standard runtime, Admin Store, built-in identity, MCP, Admin API/UI, telemetry, exception handling, and approval-provider selection. |
| Build a custom integration | `HsSqlAgent.Server` | The application selects capabilities and can keep its own authentication, authorization, UI, middleware ordering, telemetry, or approval provider. |

For a standalone service instead of an embedded .NET host, use the official Docker image.

## Embed the complete product with HsSqlAgent.Hosting

Install the batteries-included package:

```bash
dotnet add package HsSqlAgent.Hosting
```

Then add and use the standard host:

```csharp
using HsSqlAgent.Hosting;

var builder = WebApplication.CreateBuilder(args);
builder.AddHsSqlAgentStandardHost();

var app = builder.Build();
app.UseHsSqlAgentStandardHost();
await app.RunAsync();
```

This is the same first-party capability composition and configuration contract used by the official ToolBox / Docker host. URL binding and logging remain normal ASP.NET Core host concerns.

`HsSqlAgent.Hosting` includes the standard `HsSqlAgent.Server` runtime plus the official `HsSqlAgent.Approvals.Webhook` adapter. It does not introduce runtime NuGet or DLL plugin loading.

### Choose the DML approval provider

MCP Elicitation remains the default first-party approval path:

```json
{
  "DmlApproval": {
    "Provider": "McpElicitation"
  }
}
```

To use the official generic Webhook adapter:

```json
{
  "DmlApproval": {
    "Provider": "Webhook",
    "Webhook": {
      "Endpoint": "https://approval.example.com/hssqlagent/requests",
      "CallbackUrl": "https://sql-agent.example.com/api/hs-sql-agent/approvals/webhook",
      "SigningSecret": "replace-with-a-unique-secret-at-least-32-bytes"
    }
  }
}
```

Environment variables use normal ASP.NET Core configuration names, for example `DmlApproval__Provider=Webhook`. Unknown provider names fail at startup.

If you need a custom `IDmlApprovalProvider`, use `HsSqlAgent.Server` and register the provider through dependency injection. The approval system never receives authority to execute arbitrary SQL: HsSqlAgent still owns validation, approval fingerprint binding, current-state revalidation, and the final commit.

## Build a custom integration with HsSqlAgent.Server

Install the modular package:

```bash
dotnet add package HsSqlAgent.Server
```

An existing application can keep its own authentication and authorization while adding only the HsSqlAgent capabilities it needs:

```csharp
var hs = builder.Services.AddHsSqlAgentCore();

hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
hs.AddHsSqlAgentAdminStore(options =>
{
    options.Provider = "Postgres";
    options.ConnectionString =
        builder.Configuration.GetConnectionString("HsSqlAgent")!;
});
hs.AddHsSqlAgentHostAuthorization("SqlAgentAdmin");
hs.AddHsSqlAgentAdminApi();
```

The host keeps the ASP.NET Core pipeline:

```csharp
var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();
app.UseHsSqlAgentAdminApi();
app.MapControllers();

app.Run();
```

Do not call `AddHsSqlAgentBuiltInAuth()` in host-authorization mode. HsSqlAgent uses the authenticated `HttpContext.User`, does not publish its built-in identity controllers, and does not install the HsSqlAgent identity schema.

Canonical permission identifiers such as `/runtime/db-management.edit` and `/auth/role.view` are stable authorization resources, not route paths. A host policy may map them into its own permission model.

### Add MCP only when needed

MCP remains a separate machine-access boundary:

```csharp
hs.AddHsSqlAgentMcp(options =>
{
    options.PublicEndpoint = "https://example.com/mcp";
    options.HmacSecretKey = builder.Configuration["HMAC_KEY"]!; // >= 32 bytes
});
```

Then map it after building the application:

```csharp
app.UseHsSqlAgentMcp();
```

MCP keys, tool scope, table scope, rate limits, and HMAC validation remain independent from the human/Admin authorization policy.

### Use built-in identity only when wanted

If the host wants HsSqlAgent's own JWT/member/role model, select built-in authentication instead of host authorization:

```csharp
hs.AddHsSqlAgentBuiltInAuth(options =>
{
    options.Jwt.SecretKey = builder.Configuration["JWT_KEY"]!; // >= 32 bytes
});
```

Built-in identity and host-authorization mode are mutually exclusive. The packaged Admin UI is also optional for modular hosts.

## Capability ownership

| Capability | What it owns |
| --- | --- |
| `AddHsSqlAgentRuntime()` | Runtime services, operability, coordination, SQL concurrency, and DML approval persistence |
| `AddHsSqlAgentAdminStore()` | Admin database provider and connection string |
| `AddHsSqlAgentBuiltInAuth()` | JWT, password reset/SMTP, and enterprise identity/OIDC |
| `AddHsSqlAgentHostAuthorization()` | Delegation to an existing ASP.NET Core authorization policy |
| `AddHsSqlAgentMcp()` | Public MCP endpoint and MCP-key HMAC secret |
| `AddHsSqlAgentAdminApi()` | Administration controllers and controller-scoped validation/exception mapping |
| `AddHsSqlAgentTelemetry()` | Prometheus and OTLP settings |

Unselected capabilities do not allocate or validate their options.

## Current HTTP surface

| Surface | Mount |
| --- | --- |
| MCP endpoint | `/mcp` |
| Admin API prefix | `/api` |
| Admin UI | `/` |

Arbitrary relocation is not advertised until routing, frontend base paths/assets, callbacks, and security boundaries can move together.

## Legacy compatibility

Existing package consumers may continue to use `AddHsSqlAgent()` and `UseHsSqlAgent()`. New integrations should prefer either the standard `HsSqlAgent.Hosting` entry point or `AddHsSqlAgentCore()` plus explicit capability registration.

## G5: MySQL 8.4 schema changes (explicit opt-in)

MySQL InnoDB **atomic DDL is not transactional DDL**: a regular CREATE TABLE implicitly commits and cannot be undone with application ROLLBACK. The existing execute_ddl_sql tool is hidden and denied unless this particular provider is opted in, its MCP key explicitly grants the tool, and an independent DDL approval provider is configured.

Only one unqualified CREATE TABLE with 1–16 simple signed INT columns is supported. No TEMPORARY, CTAS, DEFAULT, constraints, ALTER, INDEX, DROP, batches or cross-provider execution through the MySQL Host. Preview reads live metadata without writing; approved execution verifies the real server UUID, MySQL 8.4 version, selected allowlisted database, exact-case names, InnoDB engine and object absence on a new connection. It uses a cooperative Host session lock—not a global lock against unrelated clients—then executes only SqlCore-compiled native SQL once and verifies the physical columns afterward.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentMySqlDdl(new MySqlDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedDatabases = new HashSet<string>(StringComparer.Ordinal) { "app_database" },
    PolicyRevision = "mysql84-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
```

The result may be outcome_unknown if the server reply or postcondition becomes unprovable after execution begins. **Never retry automatically**; reconcile the real database first. DML approval cannot approve DDL. The four default read-only tools and the default-unselected DML/DDL choices are unchanged.

## G5: Oracle 26ai implicit-commit schema changes (explicit opt-in)

Oracle DDL **commits before and after the statement**. An approved CREATE TABLE cannot be undone by application ROLLBACK, even if a subsequent step fails. The existing `execute_ddl_sql` tool remains hidden by default. An explicit Oracle-specific opt-in, a separately authorized MCP access key, and an independent DDL approver are required.

Only one unqualified, own-schema CREATE TABLE with 1–16 simple INTEGER columns is executable. Constraints, defaults, ALTER, INDEX, DROP, CTAS and batches are rejected. This is not generic Oracle DDL access.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentOracleDdl(new OracleDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedPdbNames = new HashSet<string>(StringComparer.Ordinal) { "FREEPDB1" },
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "SQLCORE" },
    PolicyRevision = "oracle26ai-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Also explicitly grant execute_ddl_sql to the relevant MCP access key.
```

```sql
-- DBA-run setup for the designated SQLCORE account in the target PDB.
GRANT SELECT ON SYS.V_$DATABASE TO SQLCORE;
GRANT SELECT ON SYS.V_$PDBS TO SQLCORE;
GRANT SELECT ON SYS.DBA_TRIGGERS TO SQLCORE;
GRANT EXECUTE ON SYS.DBMS_LOCK TO SQLCORE;
```

The Host must prove the actual Oracle 26ai (23.26+) kernel, writable primary PDB with a permitted identity, session owner, full dictionary visibility for active DDL triggers, and absence of the target name. Preview does not write. A session-held cooperative lock protects participating Host requests while it rechecks metadata, executes **only** SqlCore-compiled SQL once, and verifies actual columns. It does not exclude unrelated Oracle clients.

After DDL is sent, an uncertain reply or failed postcondition returns `outcome_unknown`—**never retry automatically**. Reconcile the real PDB with a DBA first. The four default read-only tools remain selected, and DML/DDL remain unselected.

## G6: PostgreSQL high-risk DROP of a verified empty table (explicit opt-in)

The existing `execute_ddl_sql` tool has one **destructive exception**: an independently approved, schema-qualified `DROP TABLE schema.table RESTRICT` on PostgreSQL. It is **disabled by default**, separate from additive DDL and all DML permissions. It deletes the table definition permanently after COMMIT; no data-bearing tables are permitted.


```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

services.AddHsSqlAgentPostgresDdl(new PostgresDdlExecutionOptions
{
    Enabled = true,
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "staging_cleanup" },
    AllowDropEmptyTable = true, // false by default; separate destructive opt-in
    AllowedDropPrincipals = new HashSet<string>(StringComparer.Ordinal)
    {
        "mcp-key:123" // replace with authenticated MCP key identity
    },
    PolicyRevision = "postgres-g6-destructive-governance-v1"
});
services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Separately grant execute_ddl_sql on the target MCP access key.
```

The authenticated MCP key ID must also appear in `AllowedDropPrincipals`. A normal `execute_ddl_sql` grant alone cannot authorize destructive DROP; changing the list invalidates pending approvals.

The PostgreSQL Host additionally requires direct table ownership, an allowlisted schema, a normal permanent table with 1–16 INTEGER columns, and **no rows, indexes, constraints, view dependencies, triggers, RLS, defaults, inheritance, publications or other unproven effects**. Preview reads metadata but never mutates. After independent human approval, the Host takes a PostgreSQL `ACCESS EXCLUSIVE` transaction lock, rechecks the physical table OID and all preconditions, executes only compiled `RESTRICT` DDL, confirms physical absence and commits. Verified rollback means failure; uncertain COMMIT or rollback means `outcome_unknown` and **must not be retried automatically**. `CASCADE`, `IF EXISTS`, nonempty tables, other providers and multi-DDL batches remain forbidden. The four default read-only tools are unchanged; DML and DDL remain unselected.

## G6/S16: PostgreSQL atomic DDL Batch (separate opt-in)

The existing `execute_ddl_sql` tool permits **2–4 independent, schema-qualified CREATE TABLE statements** on PostgreSQL 16 with a single ordered immutable plan, **one** independent human approval and **one** actual database transaction. A single-DDL grant does not enable batching. This is not a general SQL script executor.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

services.AddHsSqlAgentPostgresDdl(new PostgresDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowCreateTableBatch = true, // false by default
    AllowedBatchPrincipals = new HashSet<string>(StringComparer.Ordinal)
    {
        "mcp-key:123" // authenticated MCP key ID
    },
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal)
    {
        "staging_cleanup"
    },
    PolicyRevision = "postgres-g6-atomic-batch-v1"
});
services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Separately grant execute_ddl_sql to the key.
```

```sql
CREATE TABLE staging_cleanup.import_a (id INTEGER NOT NULL);
CREATE TABLE staging_cleanup.import_b (id INTEGER NOT NULL);
```
The authenticated MCP key must be separately listed in `AllowedBatchPrincipals` and granted `execute_ddl_sql`. Read-only Preview includes ordered compiled SQL, each physical Before state and the full batch diff. After one human approval, the Host rechecks all original absent objects and PostgreSQL cluster/schema identity, obtains cooperative locks, executes only compiled statements and verifies every table before committing **one transaction**. A confirmed rollback prevents partial application. If COMMIT/rollback is uncertain, return `outcome_unknown`: **never retry automatically**. Cross-statement ALTER/INDEX dependencies, DROP, DML, CTAS, duplicate/cross-schema targets, MySQL/Oracle implicit-commit batches and other Provider batches are rejected. Default four read-only tools remain selected; DML and DDL remain unselected.
