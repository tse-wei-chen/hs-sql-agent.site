## Protection des secrets obligatoire

Avant de démarrer Docker ou d’enregistrer le runtime, configurez trois secrets Base64 indépendants de 32 octets aléatoires. Conservez les mêmes clés sur tous les nœuds et après les redémarrages. `HMAC_KEY` et `JWT_KEY` restent des secrets de signature distincts. Exécutez séparément trois fois `openssl rand -base64 32`.

| Variable Docker | Configuration ASP.NET Core |
| --- | --- |
| `DB_ENCRYPTION_KEY` | `SecretProtection:DatabasePasswords:Keys:db-1` |
| `DML_ENCRYPTION_KEY` | `SecretProtection:DmlPayloads:Keys:dml-1` |
| `DML_FINGERPRINT_KEY` | `SecretProtection:DmlFingerprintKey` |

Définissez `SecretProtection:DatabasePasswords:ActiveKeyId` sur `db-1` et `SecretProtection:DmlPayloads:ActiveKeyId` sur `dml-1`. Une clé absente, invalide ou réutilisée empêche le démarrage. Les valeurs fictives des exemples sont volontairement invalides.

`HsSqlAgent.Hosting` lie automatiquement `SecretProtection`. Un hôte modulaire doit le faire explicitement :

```csharp
hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
```

Pour les nouvelles clés MCP d’amorçage, fournissez explicitement `Bootstrap:Databases:*:McpKeys:*:Key`. Le démarrage ne génère plus ces clés et ne les journalise plus. Les mots de passe DB chiffrés existants doivent être saisis à nouveau. Consultez le [guide de mise à niveau](/fr/docs/reference/upgrade-guide) avant de modifier un déploiement existant.

Plusieurs modules peuvent appeler `AddHsSqlAgentCore()` sur le même `IServiceCollection`. Chaque capacité n’accepte sa configuration qu’au premier enregistrement ; toute redéfinition ultérieure échoue. Les collections de services distinctes restent isolées.

Une application ASP.NET Core dispose de deux points d'entrée NuGet. Choisissez selon les frontières que l'application hôte doit réellement maîtriser.

| Objectif | Package | Responsabilité |
| --- | --- | --- |
| Intégrer le produit complet | `HsSqlAgent.Hosting` | HsSqlAgent gère l'exécution standard, l'Admin Store, l'identité intégrée, MCP, l'API/interface d'administration, la télémétrie, les exceptions et le choix du fournisseur d'approbation. |
| Construire une intégration sur mesure | `HsSqlAgent.Server` | L'application choisit les capacités et peut conserver son authentification, son autorisation, son interface, l'ordre du pipeline ASP.NET Core, sa télémétrie ou son fournisseur d'approbation. |

Pour un service autonome plutôt qu'un composant intégré dans un hôte .NET, utilisez l'image Docker officielle.

## Intégrer le produit complet avec HsSqlAgent.Hosting

Installez le package complet :

```bash
dotnet add package HsSqlAgent.Hosting
```

Ajoutez puis activez l'hôte standard :

```csharp
using HsSqlAgent.Hosting;

var builder = WebApplication.CreateBuilder(args);
builder.AddHsSqlAgentStandardHost();

var app = builder.Build();
app.UseHsSqlAgentStandardHost();
await app.RunAsync();
```

Cette composition et ce contrat de configuration sont les mêmes que ceux de l'hôte officiel ToolBox / Docker. Le binding des URL et la journalisation restent des responsabilités ASP.NET Core normales de l'hôte.

`HsSqlAgent.Hosting` inclut le runtime standard `HsSqlAgent.Server` ainsi que l'adaptateur officiel `HsSqlAgent.Approvals.Webhook`. Il n'ajoute aucun chargement dynamique de packages NuGet ou de DLL.

### Choisir le fournisseur d'approbation DML

MCP Elicitation reste le mécanisme officiel par défaut :

```json
{
  "DmlApproval": {
    "Provider": "McpElicitation"
  }
}
```

Pour utiliser l'adaptateur Webhook générique officiel :

```json
{
  "DmlApproval": {
    "Provider": "Webhook",
    "Webhook": {
      "Endpoint": "https://approval.example.com/hssqlagent/requests",
      "CallbackUrl": "https://sql-agent.example.com/api/hs-sql-agent/approvals/webhook",
      "SigningSecret": "replace-with-a-unique-secret-at-least-32-bytes"
    }
  }
}
```

Les variables d'environnement suivent la convention ASP.NET Core normale, par exemple `DmlApproval__Provider=Webhook`. Un nom de provider inconnu fait échouer le démarrage.

Pour un `IDmlApprovalProvider` personnalisé, utilisez `HsSqlAgent.Server` et enregistrez-le par injection de dépendances. Le système d'approbation ne reçoit jamais le droit d'exécuter du SQL arbitraire : HsSqlAgent conserve la validation, la liaison du fingerprint d'approbation, la revalidation de l'état courant et le commit final.

## Construire une intégration sur mesure avec HsSqlAgent.Server

Installez le package modulaire :

```bash
dotnet add package HsSqlAgent.Server
```

Une application existante peut conserver son authentification et son autorisation tout en ajoutant uniquement les capacités HsSqlAgent dont elle a besoin :

```csharp
var hs = builder.Services.AddHsSqlAgentCore();

hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
hs.AddHsSqlAgentAdminStore(options =>
{
    options.Provider = "Postgres";
    options.ConnectionString =
        builder.Configuration.GetConnectionString("HsSqlAgent")!;
});
hs.AddHsSqlAgentHostAuthorization("SqlAgentAdmin");
hs.AddHsSqlAgentAdminApi();
```

Le pipeline ASP.NET Core reste sous le contrôle de l'hôte :

```csharp
var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();
app.UseHsSqlAgentAdminApi();
app.MapControllers();

app.Run();
```

En mode autorisation déléguée à l'hôte, n'appelez pas `AddHsSqlAgentBuiltInAuth()`. HsSqlAgent utilise le `HttpContext.User` déjà authentifié, ne publie pas ses contrôleurs d'identité intégrés et n'installe pas son schéma d'identité.

Les canonical permissions comme `/runtime/db-management.edit` et `/auth/role.view` sont des identifiants stables de ressources d'autorisation, pas des routes. La policy de l'hôte peut les faire correspondre à son propre modèle de permissions.

### Ajouter MCP uniquement si nécessaire

MCP reste une frontière de sécurité distincte pour l'accès machine :

```csharp
hs.AddHsSqlAgentMcp(options =>
{
    options.PublicEndpoint = "https://example.com/mcp";
    options.HmacSecretKey = builder.Configuration["HMAC_KEY"]!; // >= 32 bytes
});
```

Puis mappez-le après la construction de l'application :

```csharp
app.UseHsSqlAgentMcp();
```

Les clés MCP, les périmètres d'outils et de tables, les limites de débit et la validation HMAC restent indépendants de l'autorisation humaine/administrative.

### Utiliser l'identité intégrée uniquement si nécessaire

Si l'hôte veut le modèle JWT/member/role de HsSqlAgent, choisissez l'authentification intégrée plutôt que l'autorisation déléguée :

```csharp
hs.AddHsSqlAgentBuiltInAuth(options =>
{
    options.Jwt.SecretKey = builder.Configuration["JWT_KEY"]!; // >= 32 bytes
});
```

L'identité intégrée et l'autorisation déléguée à l'hôte sont mutuellement exclusives. Un hôte modulaire peut également ne pas monter l'interface d'administration intégrée.

## Responsabilité des capacités

| Capacité | Configuration gérée |
| --- | --- |
| `AddHsSqlAgentRuntime()` | Runtime, opérabilité, coordination, concurrence SQL et persistance des approbations DML |
| `AddHsSqlAgentAdminStore()` | Fournisseur et chaîne de connexion de la base Admin |
| `AddHsSqlAgentBuiltInAuth()` | JWT, réinitialisation de mot de passe/SMTP, identité d'entreprise/OIDC |
| `AddHsSqlAgentHostAuthorization()` | Délégation vers une policy d'autorisation ASP.NET Core existante |
| `AddHsSqlAgentMcp()` | Point d'accès MCP public et secret HMAC des clés MCP |
| `AddHsSqlAgentAdminApi()` | Contrôleurs d'administration et gestion de validation/exceptions |
| `AddHsSqlAgentTelemetry()` | Réglages Prometheus et OTLP |

Une capacité non sélectionnée n'alloue ni ne valide ses options.

## Surfaces HTTP actuelles

| Surface | Chemin |
| --- | --- |
| Point d'accès MCP | `/mcp` |
| Préfixe de l'API d'administration | `/api` |
| Interface d'administration | `/` |

Le déplacement arbitraire de ces chemins n'est pas annoncé tant que le routage, les chemins/assets du frontend, les callbacks et les frontières de sécurité ne peuvent pas évoluer ensemble.

## API de compatibilité

Les consommateurs existants peuvent continuer à utiliser `AddHsSqlAgent()` et `UseHsSqlAgent()`. Pour une nouvelle intégration, préférez l'entrée standard `HsSqlAgent.Hosting` ou `AddHsSqlAgentCore()` avec enregistrement explicite des capacités.

## G5 : modifications de schéma MySQL 8.4 (activation explicite)

**Une instruction DDL atomique InnoDB n'est pas une transaction annulable par l'application.** Un CREATE TABLE ordinaire provoque une validation implicite et ne peut pas être annulé par ROLLBACK. L'outil existant execute_ddl_sql reste masqué et refusé par défaut. Il faut activer MySQL séparément, autoriser explicitement l'outil pour la clé d'accès MCP et configurer une approbation DDL indépendante.

La première version accepte uniquement un CREATE TABLE sans préfixe de base, avec 1 à 16 colonnes INT signées simples. Les tables temporaires, la création à partir d'une requête, les valeurs par défaut, contraintes, ALTER, INDEX, DROP et scripts multiples restent interdits. L'aperçu ne lit que les métadonnées réelles. Après approbation, une nouvelle connexion revérifie l'identité MySQL 8.4, la base autorisée, la sensibilité à la casse, le moteur InnoDB et l'absence de l'objet. Une seule instruction SQL compilée par SqlCore est exécutée, puis la structure physique est contrôlée.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentMySqlDdl(new MySqlDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedDatabases = new HashSet<string>(StringComparer.Ordinal) { "app_database" },
    PolicyRevision = "mysql84-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
```

Le verrou de session coordonne uniquement les demandes de ce service ; il **n'exclut pas les clients DDL externes**. Si le résultat devient invérifiable après le début de l'exécution, l'état est outcome_unknown. Ne jamais relancer automatiquement : examiner d'abord la base réelle. Une approbation DML ne peut pas autoriser une DDL. Les quatre outils de lecture sélectionnés par défaut et les choix DML/DDL non cochés restent inchangés.

## G5 : modifications de schéma Oracle 26ai (activation explicite)

Oracle effectue une **validation implicite avant et après chaque instruction DDL**. Une table créée ne peut donc pas être annulée par un ROLLBACK applicatif, même si une étape ultérieure échoue. L'outil `execute_ddl_sql` reste masqué par défaut. Il faut activer Oracle séparément, accorder explicitement l'accès à la clé MCP et faire approuver la DDL par une autorité indépendante.

Seule une instruction CREATE TABLE **dans le schéma de l'utilisateur connecté, sans préfixe de schéma**, comportant 1 à 16 colonnes INTEGER simples, peut être exécutée. Contraintes, valeurs par défaut, ALTER, INDEX, DROP, création par SELECT et suites d'instructions sont refusés.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentOracleDdl(new OracleDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedPdbNames = new HashSet<string>(StringComparer.Ordinal) { "FREEPDB1" },
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "SQLCORE" },
    PolicyRevision = "oracle26ai-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Also explicitly grant execute_ddl_sql to the relevant MCP access key.
```

```sql
-- DBA-run setup for the designated SQLCORE account in the target PDB.
GRANT SELECT ON SYS.V_$DATABASE TO SQLCORE;
GRANT SELECT ON SYS.V_$PDBS TO SQLCORE;
GRANT SELECT ON SYS.DBA_TRIGGERS TO SQLCORE;
GRANT EXECUTE ON SYS.DBMS_LOCK TO SQLCORE;
```

L'hôte doit vérifier la version Oracle 26ai réelle (noyau 23.26 ou supérieur), la PDB primaire accessible en écriture, la PDB et le schéma autorisés, la visibilité complète des déclencheurs DDL et l'absence de l'objet. L'aperçu reste en lecture seule. Après approbation, un verrou de session coordonne les requêtes de ce service, les métadonnées sont revérifiées, puis seule l'instruction SQL compilée par SqlCore est exécutée une fois. Les colonnes physiques sont contrôlées. **Ce verrou n'exclut pas les autres clients Oracle.**

Si le résultat devient invérifiable après l'envoi de la DDL, l'état est `outcome_unknown` : **ne jamais relancer automatiquement**. Un administrateur doit d'abord vérifier l'état réel de la PDB. Les quatre outils de lecture restent cochés par défaut et DML/DDL restent décochés.

## G6 : suppression à haut risque d’une table PostgreSQL vide (activation explicite)

L’outil existant `execute_ddl_sql` autorise une seule exception destructrice : `DROP TABLE schema.table RESTRICT` sous PostgreSQL, après approbation humaine indépendante. Cette possibilité est **désactivée par défaut**, distincte des autorisations DDL additives et DML. Après COMMIT, la définition de la table est définitivement supprimée ; aucune table contenant des données ne peut être supprimée.


```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

services.AddHsSqlAgentPostgresDdl(new PostgresDdlExecutionOptions
{
    Enabled = true,
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "staging_cleanup" },
    AllowDropEmptyTable = true, // false by default; separate destructive opt-in
    AllowedDropPrincipals = new HashSet<string>(StringComparer.Ordinal)
    {
        "mcp-key:123" // replace with authenticated MCP key identity
    },
    PolicyRevision = "postgres-g6-destructive-governance-v1"
});
services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Separately grant execute_ddl_sql on the target MCP access key.
```

L’identifiant de la clé MCP authentifiée doit également figurer dans `AllowedDropPrincipals`. L’autorisation ordinaire `execute_ddl_sql` ne suffit pas pour une suppression destructrice ; toute modification de cette liste invalide les approbations en attente.

Avant toute exécution, l’hôte vérifie dans PostgreSQL le schéma autorisé, la propriété directe de la table, son caractère permanent et ordinaire (1 à 16 colonnes INTEGER), ainsi que l’**absence de lignes, index, contraintes, vues dépendantes, déclencheurs, règles RLS, valeurs par défaut, héritage, publications ou effets non prouvés**. L’aperçu ne fait aucune écriture. Après approbation humaine indépendante, une transaction acquiert un verrou `ACCESS EXCLUSIVE`, revérifie l’OID physique et toutes les conditions, exécute uniquement la commande `RESTRICT` compilée, confirme la disparition de la table, puis valide. Un rollback confirmé signifie que la suppression n’a pas été validée ; si COMMIT ou rollback est incertain, le résultat est `outcome_unknown` et **aucune relance automatique n’est autorisée**. `CASCADE`, `IF EXISTS`, tables non vides, autres SGBD et lots DDL restent interdits. Les quatre outils en lecture seule demeurent seuls présélectionnés.
