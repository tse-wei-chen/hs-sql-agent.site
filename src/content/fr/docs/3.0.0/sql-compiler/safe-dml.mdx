## Admission, résultats incertains et preuves sur la cible

Lorsqu’un prédicat sélectif est exigé, les filtres `UPDATE`/`DELETE` prouvés toujours vrais, comme `WHERE 1=1`, sont refusés. L’approbation humaine reste liée au plan exact et aux preuves de l’ensemble de lignes.

Les magasins de challenges personnalisés doivent implémenter `TryPromoteAsync` de manière atomique, pour une instruction comme pour un lot. Redis et la reprise persistante utilisent des enveloppes versionnées. Un challenge incompatible exige un nouvel aperçu et un nouveau consentement. Voir le [guide de mise à niveau](/fr/docs/reference/upgrade-guide).

`dml.commit_outcome_unknown` et `dml.rollback_outcome_unknown` sont deux résultats distincts, non réessayables. Conservez les preuves d’approbation et de cible pour une vérification indépendante. L’absence de témoin ou de clé Redis ne prouve pas une annulation ; ne rejouez jamais automatiquement une mutation incertaine. Une erreur de persistance d’audit après un commit confirmé ne doit pas être présentée comme un échec de mutation.

`AddHsSqlAgentTargetExecutionFence()` est facultatif et nécessite de préparer la cible puis de prouver séparément le retrait des droits DML des anciens workers. Chaque commit inscrit effectue deux transactions de vérification supplémentaires, toujours annulées, sur la connexion réelle, puis deux lectures indépendantes après commit pour Admission et Witness. Oracle utilise READ COMMITTED uniquement pour le diagnostic de conflit d’unicité du témoin ; les autres phases utilisent SERIALIZABLE. Des preuves contradictoires donnent un résultat incertain. Cela ne certifie ni l’inscription de toute la flotte ni la réconciliation automatique d’un worker actif.

Le DML suit une voie plus stricte que les Query, car au moment du commit l'approbation doit toujours décrire **les mêmes Mutation Evidence**.

## Un seul Tool pour un ou plusieurs Statements

`execute_dml_sql` accepte une ou plusieurs instructions `UPDATE`, `DELETE` ou `INSERT ... VALUES` prises en charge. Plusieurs Statements sont séparés par des points-virgules.

Il n'existe pas de Tool batch DML séparé. Une entrée multi-statement devient un Batch, reçoit une seule approbation, s'exécute dans l'ordre d'origine puis est commit de manière atomique dans une Transaction contrôlée par le serveur.

Le Client ne peut pas fournir `BEGIN`, `COMMIT`, `ROLLBACK` ou un autre Transaction-control SQL. Le serveur possède les frontières de Transaction.

## Ce que l'approbation lie

Pour `UPDATE` et `DELETE`, l'approbation est liée au Primary Key Row Set exact observé pendant le Preview. Chaque Statement est revalidé immédiatement avant sa mutation dans la Commit Transaction.

Pour `INSERT ... VALUES`, l'approbation lie le Literal Payload immuable et la Command compilée exacte. `INSERT ... SELECT` reste indisponible tant que la sémantique d'approbation du source Row Set n'est pas définie.

Si un Statement précédent modifie le Row Set approuvé d'un Statement suivant, tout le Batch échoue en mode fail closed et rollback.

## Provider d'approbation

MCP Elicitation reste le Provider officiel par défaut. Un Host peut aussi utiliser l'adapter officiel `HsSqlAgent.Approvals.Webhook` ou implémenter `IDmlApprovalProvider` avec `HsSqlAgent.Server`.

Le Provider reçoit des Evidence indépendantes du transport, pas des primitives d'exécution SQL. Il ne reçoit ni Database Connection, ni Transaction, ni Plan validé, ni autorité de commit.

## Approbations Pending durables

Un Provider peut retourner `Pending` pour un Workflow asynchrone. Avec l'Admin Store, hs-sql-agent conserve le Resume Intent protégé et les Approval Fingerprints.

Lorsqu'une décision finale arrive, le serveur recharge l'autorisation et la configuration DB courantes, Parse et Preview à nouveau le DML, compare les Evidence approuvées et crée un nouveau Challenge de courte durée. Une modification de l'autorisation, de la configuration DB, de la Policy, du Plan, du Row Set ou des affected-row Evidence rend la demande stale au lieu de la commit.

La reprise concerne**l'Intent d'exécution**, pas une ancienne Database Session.

## SQL Server : clés INT composites dans les mutations avec CTE

Un UPDATE ou DELETE explicitement autorisé sur SQL Server peut lire une table source physique à travers une à trois CTE linéaires non récursives si un **index unique ou une clé primaire réelle, composée de deux colonnes INT non nulles**, a été vérifié. Les deux clés doivent être projetées sans modification et dans l'ordre de l'index physique à chaque étape. La mutation doit comparer les deux colonnes INT correspondantes de la cible au moyen de conditions obligatoires `AND` et `=`. Avant toute exécution, le serveur vérifie le catalogue réel, prévisualise les lignes concernées, lie l'approbation au plan puis recontrôle les métadonnées dans la transaction effective.

Les clés manquantes ou permutées, `OR`, les conversions de type, les clés nullables ou calculées, les index filtrés ou désactivés et les jointures qui multiplient les lignes sont refusés. Cette capacité ne s'étend pas aux autres bases.

### Projection de colonnes supplémentaires dans les CTE (G8 / M03)

Les une à trois CTE peuvent désormais projeter, en plus de la clé INT obligatoire à une ou deux colonnes, **des colonnes supplémentaires directement issues de la source** (32 colonnes maximum par étape). Par exemple, `SELECT k1 AS a, payload AS extra, k2 AS b` peut être suivi de `SELECT a, extra, b`. Chaque clé doit être présente une seule fois à chaque étape, conserver l'ordre relatif de l'index physique et être liée par les comparaisons obligatoires `AND` et `=`. Les clés dupliquées, calculées ou transformées, les alias ambigus, les sources multiples et les JOIN qui multiplient les lignes restent refusés. La vérification de l'index réel, l'aperçu, l'approbation et la revalidation pendant le commit restent inchangés. Aucun JOIN général ni autre moteur n'est autorisé par cette extension.

### Preuve de cardinalité pour une jointure à une seule ligne (G8 / M07, portée limitée)

Chaque étape CTE de SQL Server peut désormais contenir **une seule jointure dont l'absence de multiplication des lignes est démontrée**. La source jointe doit être une sous-requête indépendante telle que `SELECT 1 AS marker`, sans `FROM`, `WHERE`, `UNION`, regroupement ni lignes supplémentaires. `CROSS JOIN (SELECT 1 AS marker) AS one` conserve la cardinalité ; `INNER JOIN` et `LEFT JOIN` avec l'égalité littérale `ON 1 = 1` ne l'augmentent pas. La clé INT unique physique, la projection directe, l'aperçu, l'approbation et la vérification en transaction restent indispensables. **La seule preuve précédente de jointure singleton ou auto-jointure n'autorise pas les autres tables physiques ; la preuve indépendante des deux index ci-dessous établit le sous-ensemble désormais admis. Les jointures avec d'autres tables physiques, APPLY, les requêtes corrélées, les sources à plusieurs lignes et les jointures générales ne sont pas autorisées.**

Une seconde forme, tout aussi limitée, autorise une **auto-jointure INNER ou LEFT sur la même table source physique** sous deux alias distincts, à condition que le prédicat ON compare par égalités ordinaires reliées avec AND **toutes les colonnes de la clé INT unique vérifiée en base**. Le second alias fournit alors au plus une ligne par ligne source. Toute clé manquante, comparaison OR seule, clé calculée ou convertie, ou jointure avec une autre table est refusée.

### Jointure de deux tables physiques avec preuves d'unicité indépendantes (M07)

Une CTE SQL Server peut désormais effectuer une seule **INNER JOIN** ou **LEFT JOIN** vers une autre table physique. Chacune des deux sources doit posséder sa propre clé unique physique vérifiée en base, composée d'une ou deux colonnes `INT`/`BIGINT` non nullables, sur un index actif et non filtré. Le prédicat `ON` doit lier toutes les colonnes par des égalités ordinaires obligatoires avec `AND`, avec correspondance exacte des types physiques à chaque position. Un catalogue virtuel, une conversion implicite, une partie de la clé ou un index filtré ne constituent pas une preuve. Les deux index sont liés au plan et à l'approbation puis revérifiés dans la transaction réelle lors du commit, y compris après une modification d'index postérieure à l'aperçu. Cette extension n'autorise ni troisième source physique, ni jointures plusieurs-à-plusieurs, ni `RIGHT`/`FULL JOIN`, ni conversion entre moteurs, ni jointures arbitraires.

### Filtrage EXISTS / NOT EXISTS corrélé par clé complète (M07, portée limitée)

Un UPDATE/DELETE avec CTE SQL Server peut utiliser **EXISTS** (semi-jointure) ou **NOT EXISTS** (anti-jointure) dans le WHERE de la première CTE, uniquement si la sous-requête relit **la même table physique dont la clé unique a déjà été vérifiée**, sous un autre alias. Elle ne projette qu'un littéral et n'admet ni JOIN supplémentaire, ni regroupement, ni tri, ni opération ensembliste. Elle doit corréler toutes les composantes (une ou deux) de la clé unique `INT`/`BIGINT` par des égalités ordinaires obligatoires reliées par `AND` ; des comparaisons directes entre une colonne interne et un littéral peuvent limiter davantage les lignes. Ce filtre ne multiplie jamais les lignes. Preuve réelle d'index, aperçu, identité de l'approbation et revérification dans la transaction restent obligatoires. **Ni sous-requête arbitraire, ni autre table non vérifiée, ni autorisation générale des anti-jointures ne sont ouvertes.**

### Clés physiques TINYINT et SMALLINT avec équivalence exacte (G9/M04, develop uniquement)

La preuve physique des mutations CTE `UPDATE`/`DELETE` de SQL Server accepte désormais les types natifs `TINYINT` (8 bits non signés) et `SMALLINT` (16 bits signés), en plus de `INT` et `BIGINT`. Pour une clé unique physique d'une ou deux colonnes, les colonnes correspondantes de la source, de la cible et de la table JOIN vérifiée indépendamment doivent avoir **exactement le même type SQL Server réel à chaque position de l'index**. Une conversion implicite, un type alias défini par l'utilisateur ou un catalogue virtuel ne constitue pas une preuve. La transmission bornée des clés dans les CTE, la vérification des JOIN sans multiplication de lignes, la prévisualisation, l'approbation distincte, l'empreinte immuable du plan et la revalidation de l'index dans la transaction de commit restent obligatoires. Les tests réels SQL Server 2022 couvrent UPDATE/DELETE, les types mixtes et la révocation d'index. DECIMAL, UUID, les clés uniques nullables, les JOIN arbitraires et les autres moteurs restent exclus.


### Preuve exacte des clés physiques DECIMAL / NUMERIC (G9/M04, develop uniquement)

La preuve physique des mutations CTE `UPDATE`/`DELETE` sur SQL Server prend désormais en charge `DECIMAL(p,s)` et `NUMERIC(p,s)` natifs (`1 ≤ p ≤ 38`, `0 ≤ s ≤ p`). Ces deux noms sont synonymes, mais les clés correspondantes de la source, de la cible et de la table JOIN vérifiée indépendamment doivent avoir **exactement la même précision et la même échelle à chaque position de l'index**. Une conversion implicite entre `DECIMAL(12,2)` et `DECIMAL(13,2)`, `DECIMAL(12,3)` ou une clé entière ne démontre pas l'unicité.

L'hôte lit les métadonnées réelles de `sys.columns` et `sys.types` et vérifie **toutes les colonnes clés** de l'index UNIQUE d'origine. Une colonne d'un type alias utilisateur non pris en charge ne doit jamais transformer `UNIQUE(a,b)` en preuve erronée de `UNIQUE(a)`. Le type fermé F# conserve précisément la précision et l'échelle. Les CTE limitées à trois étapes, les contrôles des JOIN sans multiplication de lignes, la prévisualisation, l'approbation indépendante, l'identité de preuve versionnée et la revalidation dans la même transaction de commit restent obligatoires. Les tests réels SQL Server 2022 couvrent les valeurs fractionnaires, les clés entières/décimales mixtes, les JOINs physiques, la révocation de l'index et les rejets pour précision ou échelle différente. Les clés UUID/texte, les contraintes UNIQUE nullables, les JOINs arbitraires et les cinq autres moteurs restent exclus.


## Règles fail closed

Une mutation n'est pas commit si l'approbation est refusée, expirée, stale, si le Fingerprint ne correspond plus, si l'autorisation est retirée, si la Policy courante la refuse ou si le Row Set approuvé ne peut pas être reproduit.
