## Compilation bornée et preuves de schéma

La compilation refuse toute entrée dépassant 4,194,304 unités UTF-16, 131,072 jetons lexicaux hors End, 8,192 niveaux de groupement ou 65,536 nœuds AST. Le parcours itératif et le rendu borné préservent l’ordre des paramètres et le refus en cas de preuve insuffisante pour les six fournisseurs. Ils ne garantissent pas une profondeur SQL arbitraire.

Les budgets sont de 8,000,000 unités de travail par étape, 32,000,000 par compilation, 30 secondes par étape, 90 secondes par compilation et 536,870,912 octets d’allocations managées cumulées par étape. Ce sont des limites de compilation, pas des délais de requête DB ni des limites de mémoire du processus. Des diagnostics de ressources typés signalent les refus.

Un instantané de schéma immuable, facultatif, résout les noms de tables et colonnes ainsi que les familles de types prouvables, y compris les projections ordonnées CTE/dérivées. Son condensat est lié à l’empreinte du plan. Ce n’est pas un vérificateur complet des types DB. Le DML avec preuve de schéma exige une vérification de fraîcheur réelle ; une preuve absente ou modifiée entraîne un refus. Aucun instantané n’est capturé par défaut. `AddHsSqlAgentNativeDmlSchemaFreshness()` active le support natif facultatif.

hs-sql-agent ne traite jamais le SQL généré comme une commande fiable. La frontière d’exécution repose sur l’analyse, la validation, la vérification des capacités, les politiques d’accès et la compilation propre au moteur de base de données.

## Chemin d’une requête

À haut niveau, une requête suit les étapes suivantes :

1. Authentifier la clé MCP et appliquer son périmètre de base de données, de tables, d’outils et d’exécution.
2. Analyser le SQL pris en charge pour produire une définition structurée / AST.
3. Valider l’instruction et la sémantique source prise en charge.
4. Vérifier les capacités de la cible nécessaires pour préserver cette sémantique.
5. Compiler et produire le SQL adapté au moteur configuré.
6. Exécuter dans les limites d’exécution configurées.

Le compilateur SQL contient des étapes explicites de validation de la source et de vérification des capacités de la cible. Une syntaxe non prise en charge, ou une capacité qui ne peut pas être démontrée, est refusée au lieu d’être remplacée silencieusement par une construction simplement similaire.

## Pourquoi refuser par défaut ?

Le SQL multi-base comporte de nombreuses constructions qui semblent équivalentes mais diffèrent par leur comportement avec `NULL`, leurs règles de type, la sémantique des opérateurs, la pagination, les identifiants, les fonctions ou encore le comportement DML.

Sur une surface d’exécution destinée à l’IA, une réécriture « au mieux » est dangereuse : une instruction peut rester syntaxiquement valide tout en changeant de sens. hs-sql-agent préfère donc un refus visible à une dégradation implicite de la sémantique. C’est le principe de fonctionnement fail-closed appliqué au compilateur.

## Sortie propre au moteur

L’interface MCP publique est commune, mais le SQL final dépend du moteur ciblé. Les moteurs actuellement pris en charge sont :

- PostgreSQL
- MySQL
- SQL Server
- Oracle
- SQLite
- Firebird

La prise en charge est volontairement bornée. Le fait qu’un moteur soit pris en charge ne signifie pas que toutes les syntaxes proposées par cette base sont acceptées ; les capacités du compilateur ne sont étendues que lorsque leur sémantique peut être représentée et validée.

## Cadres de fenêtre natifs GROUPS

Pour PostgreSQL 11 ou ultérieur et SQLite 3.28 ou ultérieur, le compilateur accepte un cadre comme `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW)`. `GROUPS` avance par groupes de lignes ayant la même clé de tri, et non par lignes individuelles (`ROWS`) ni par plages de valeurs (`RANGE`). Un `ORDER BY` explicite dans la fenêtre est obligatoire. Les bornes incorrectes et les versions de serveur explicitement trop anciennes sont refusées, sans conversion silencieuse vers un autre cadre. Cette capacité reste refusée pour MySQL, SQL Server, Oracle et Firebird. Le serveur d’hébergement doit vérifier la version réelle de la base avant toute exécution.

## EXCLUDE : appartenance au cadre de fenêtre

PostgreSQL 11 ou ultérieur et SQLite 3.28 ou ultérieur acceptent quatre formes après un cadre `ROWS`, `RANGE` ou `GROUPS`. `EXCLUDE CURRENT ROW` retire uniquement la ligne courante ; `EXCLUDE GROUP` retire aussi les lignes partageant sa clé de tri ; `EXCLUDE TIES` conserve la ligne courante, mais écarte ses homologues ; `EXCLUDE NO OTHERS` ne retire aucune ligne. Exemple : `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW EXCLUDE TIES)`. Même avec `ROWS`, l’exclusion tient compte des lignes de même rang. Le compilateur F# et `WindowFrameDefinition.Exclusion` préservent cette sémantique sans transformation implicite. Les versions explicitement trop anciennes et les quatre autres fournisseurs sont refusés. L’hôte doit contrôler la version réelle de la base avant exécution.

## SQL Server : décalages numériques dans les cadres RANGE

La syntaxe T-SQL de SQL Server interdit les décalages numériques `PRECEDING` et `FOLLOWING` dans un cadre de fenêtre `RANGE`. Ainsi, `RANGE BETWEEN 1 PRECEDING AND CURRENT ROW` est rejeté **comme syntaxe source SQL Server invalide**, même si PostgreSQL ou SQLite est choisi comme cible. Les décalages `ROWS` valides et `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` restent pris en charge. Les sémantiques `RANGE` numériques natives de PostgreSQL et de SQLite ne changent pas. Le compilateur vérifie séparément la validité du dialecte source et les capacités de la cible : la prise en charge par la cible ne prouve pas que la syntaxe source est valide.

## COUNT conditionnel limité vers MySQL et SQL Server

Une requête de dialecte source PostgreSQL comme `SELECT COUNT(*) FILTER (WHERE status = 1) FROM orders` peut désormais être compilée pour MySQL ou SQL Server sous la forme d'une agrégation conditionnelle équivalente. MySQL utilise `COUNT(CASE WHEN ... THEN 1 END)` ; SQL Server utilise `COUNT_BIG(CASE WHEN ... THEN 1 END)` pour préserver la plage de comptage sur 64 bits. `COUNT(colonne_directe)` est également accepté, tout en conservant l'exclusion des valeurs NULL, le résultat zéro lorsque rien ne correspond et les comptes par cadre de fenêtre.

**Ce n'est pas une prise en charge générale de FILTER.** Seuls `COUNT(*)`, le COUNT d'une colonne locale directe et `COUNT(DISTINCT colonne_directe)` hors fonctions de fenêtre, avec des conditions simples prouvées sur colonnes et constantes, sont admis. `SUM`, les arguments calculés, sous-requêtes, fonctions volatiles et références à une portée externe restent refusés. `FILTER` demeure invalide dans du SQL source MySQL/SQL Server : la traduction concerne un dialecte source valide, tel que PostgreSQL. SqlCore n'exécute pas de SQL et n'accorde aucun droit sur la base de données.

## COUNT DISTINCT conditionnel : compter les valeurs uniques

L'expression PostgreSQL source `COUNT(DISTINCT amount) FILTER (WHERE status = 1)` est désormais traduite en `COUNT(DISTINCT CASE WHEN status = 1 THEN amount END)` pour MySQL et en `COUNT_BIG(DISTINCT CASE WHEN status = 1 THEN amount END)` pour SQL Server. Une valeur répétée n'est comptée qu'une fois. Les valeurs NULL ainsi que les lignes dont la condition est fausse ou inconnue sont ignorées ; l'absence de valeurs admissibles donne zéro. Les résultats globaux et groupés sur des entiers ont été comparés sur PostgreSQL 16, MySQL 8.4 et SQL Server 2022 réels.

Un seul argument DISTINCT, correspondant à une colonne locale directe, et un prédicat local borné sont autorisés. Les arguments calculés ou multiples, les sous-requêtes, les fonctions volatiles et les références externes restent refusés. **Les agrégats DISTINCT avec `OVER (...)` ne sont pas pris en charge**, car MySQL et SQL Server ne proposent pas cette syntaxe. `FILTER` reste invalide dans le SQL source MySQL/SQL Server. Les essais sur entiers ne prouvent pas l'équivalence générale des collations ou des conversions de types. Cette fonction n'exécute pas de SQL et n'accorde aucune permission.
