## 3.0.0에 예정된 비밀 정보 보호 변경

**상태: [hs-sql-agent PR #302](https://github.com/tse-wei-chen/hs-sql-agent/pull/302)가 `main`에 병합되었습니다([병합 커밋 `78ec5f30`](https://github.com/tse-wei-chen/hs-sql-agent/commit/78ec5f30bd3bcd2200cb95131bd85ba2a6a34eb6)).** 다만 3.0.0은 아직 공식 출시되지 않았으며 문서 사이트의 게시 버전도 바뀌지 않았습니다. 이 페이지는 비밀 정보 보호 마이그레이션만 설명하며 **2.0.6 → 3.0.0의 전체 변경 사항 목록이 아닙니다**. 정식 출시 전에는 공개하지 마세요.

기존 HMAC 파생 암호화를 용도와 신뢰할 수 있는 레코드에 연결된 AES-256-GCM으로 교체합니다. 암호문은 `v2:<key-id>:<base64 nonce/tag/ciphertext>` 형식이며 버전, 키 ID, 용도, 레코드 ID를 인증합니다. **이전 형식의 복호화 대체 경로나 자동 변환은 없습니다.**

## 비호환 변경 사항

| 항목 | 필요한 조치 |
| --- | --- |
| 저장된 데이터베이스 비밀번호 | 새 런타임에서는 기존 암호문을 복호화할 수 없습니다. 관리 화면/API에서 비밀번호를 다시 입력하거나 초기 설정에 제공해야 합니다. |
| 영속 DML 승인 | 마이그레이션 전에 `Pending`을 모두 처리하고 `Executing`의 실제 결과를 확인해야 합니다. SQLite 및 PostgreSQL Admin Store 마이그레이션은 미완료 승인을 거부합니다. 과거 암호화된 재개 데이터도 읽을 수 없게 됩니다. |
| 비밀 키 설정 | 데이터베이스 비밀번호, DML 데이터, DML 지문에 대해 **서로 다른** 무작위 32바이트 Base64 키 세 개가 필요합니다. 누락, 잘못된 형식, 짧거나 재사용된 키는 시작 시 검증 오류가 됩니다. |
| 초기 MCP 키 | `Bootstrap:Databases:*:McpKeys:*:Key`(Docker 예시에서는 `BOOTSTRAP_MCP_KEY`)를 명시해야 합니다. 시작 시 키 자동 생성 및 로그 기록이 중단됩니다. 이전에 로그에 노출된 키는 폐기하세요. |
| `ExtraSettings` | JSON 불리언 `Encrypt`, `TrustServerCertificate` 필드만 허용합니다. 알 수 없거나 중복된 필드, 문자열 값, 잘못된 JSON은 거부됩니다. |
| 진단 | 연결 검사와 상태 탐색에서 드라이버 예외 대신 `DB_CONNECTION_FAILED`를 반환합니다. Runtime Doctor의 `security.secret-protection` 검사는 키 값을 노출하지 않습니다. |

## 필수 업그레이드 절차

1. Admin Store와 기존 배포의 비밀 키를 **백업**하고 복원 가능 여부를 확인합니다. 읽기 전용 조사에 사용할 이전 바이너리도 보관합니다.
2. **새 DML 승인 접수를 중단**합니다. 모든 `Pending`을 처리하고 `Executing`의 실제 데이터베이스 결과를 독립적으로 확인합니다. 마이그레이션을 통과하기 위해 불확실한 실행을 임의로 완료나 실패로 표시하지 마세요.
3. **과거 실행 증거를 먼저 확인**합니다. 종료된 기록을 포함한 이전 암호화 재개 데이터는 새 버전에서 복호화되지 않습니다.
4. `openssl rand -base64 32`를 **세 번 각각 실행**해 독립된 키를 생성합니다. 저장소에 커밋하지 말고 예시의 유효하지 않은 값을 사용하지 마세요.
5. **모든 노드의 키 구성을 일치**시킵니다. 유지해야 할 이전 키와 버전 관리되지 않는 DML 지문 키도 포함합니다. 기존 MCP 키를 유지하려면 `HMAC_KEY`를 보존하고 JWT 서명 키와 분리합니다.
6. 초기 프로비저닝이 켜져 있다면 MCP 키를 명시적으로 제공하거나, 인증된 관리 화면/API에서 발급합니다. 비밀 값은 발급할 때 한 번만 확인할 수 있습니다.
7. **모든 노드를 함께 배포**하고 SQLite/PostgreSQL Admin Store 마이그레이션을 적용합니다. 이전/새 바이너리를 혼용하지 마세요.
8. 기존 데이터베이스 비밀번호를 다시 입력하고 연결, 권한 있는 읽기 쿼리, DML 승인 흐름을 검증한 후 서비스를 재개합니다.

마이그레이션은 각 데이터베이스 연결에 고유하고 안정적인 `SecretBindingId`를 추가하고 PostgreSQL 암호문 열의 길이 제한을 제거합니다.`PasswordHash` 열에는 단방향 해시가 아닌 **복호화 가능한 암호화 자격 증명**이 저장됩니다.

## 암호화 키 설정

Docker 배포에서는 다음 환경 변수에 실제 키를 넣습니다.

```dotenv
# Replace every example value with a different output of openssl rand -base64 32
DB_ENCRYPTION_KEY_ID=db-1
DB_ENCRYPTION_KEY=REPLACE_WITH_32_BYTE_BASE64_VALUE_1
DML_ENCRYPTION_KEY_ID=dml-1
DML_ENCRYPTION_KEY=REPLACE_WITH_32_BYTE_BASE64_VALUE_2
DML_FINGERPRINT_KEY=REPLACE_WITH_32_BYTE_BASE64_VALUE_3
```

`REPLACE_WITH_...` 값은 **유효한 키가 아닙니다**. 다음 명령을 각각 실행해 서로 다른 값을 얻으세요.

```sh
openssl rand -base64 32
openssl rand -base64 32
openssl rand -base64 32
```

사용자 정의 .NET 호스트는 런타임을 등록하기 **전에** `HsSqlAgentRuntimeOptions.SecretProtection`(또는 기존 통합 옵션의 `SecretProtection`)을 설정합니다.

```json
{
  "SecretProtection": {
    "DatabasePasswords": { "ActiveKeyId": "db-1", "Keys": { "db-1": "<base64-key-1>" } },
    "DmlPayloads": { "ActiveKeyId": "dml-1", "Keys": { "dml-1": "<base64-key-2>" } },
    "DmlFingerprintKey": "<base64-key-3>"
  }
}
```

각 암호화 키 묶음은 `ActiveKeyId`와 `Keys`를 가집니다. 데이터베이스 암호는 `db-password:<SecretBindingId>`, 영속 DML 데이터는 `dml-payload:<RequestId>`에 연결됩니다. 암호문에서 추출한 값이 아니라 신뢰할 수 있는 레코드 ID를 사용해야 합니다.

## 키 교체

1. **모든 노드**에 서로 다른 ID로 지정한 이전 키와 새 암호화 키를 배포합니다.
2. 모든 노드에 두 키가 모두 있는지 확인한 다음 `ActiveKeyId`를 변경합니다. 새 데이터는 활성 키로 암호화하고, 읽을 때는 암호문에 표시된 키 ID를 사용합니다.
3. 데이터베이스 비밀번호를 다시 저장해 재암호화합니다. 필요한 DML 데이터와 과거 조사 자료를 읽을 수 있도록 이전 키를 보관합니다.
4. 필요한 암호문이 더 이상 이전 키를 참조하지 않을 때에만 제거합니다.

`DmlFingerprintKey`는 **버전 관리되지 않습니다**. 교체 전에 승인을 모두 처리하고 이전 배포의 비밀 키를 과거 조사용으로 보관하세요. Docker Compose 기본 변수는 활성 키만 나타내므로 유지 키는 구성 재정의나 마운트된 비밀 설정으로 지정합니다.

## 롤백 및 확인

**역방향 데이터베이스 마이그레이션은 지원되지 않습니다.** 롤백하려면 **업그레이드 이전 Admin Store 백업**, 이전 바이너리, 일치하는 구성과 키를 함께 복원해야 합니다. 마이그레이션이 끝난 데이터베이스에 이전 바이너리를 연결하는 것만으로는 안전하지 않습니다.

Runtime Doctor의 `security.secret-protection` 상태를 확인하세요. 공개 예시 키는 운영 환경에서 오류, 그 외 환경에서 경고이며, 변경하지 않은 자리표시자와 잘못된 설정은 시작에 실패합니다. 데이터베이스 비밀번호와 승인 자료의 복호화 및 연결 오류의 정보 노출 여부도 검증합니다.
