## 필수 비밀 정보 보호 설정

Docker를 시작하거나 런타임을 등록하기 전에 서로 독립적인 무작위 32바이트 Base64 비밀 값 세 개를 설정하세요. 모든 노드가 같은 키를 사용하고 재시작 후에도 유지해야 합니다. `HMAC_KEY`와 `JWT_KEY`는 별도의 서명 비밀 값입니다. `openssl rand -base64 32`를 각각 세 번 실행하세요.

| Docker 환경 변수 | ASP.NET Core 설정 |
| --- | --- |
| `DB_ENCRYPTION_KEY` | `SecretProtection:DatabasePasswords:Keys:db-1` |
| `DML_ENCRYPTION_KEY` | `SecretProtection:DmlPayloads:Keys:dml-1` |
| `DML_FINGERPRINT_KEY` | `SecretProtection:DmlFingerprintKey` |

`SecretProtection:DatabasePasswords:ActiveKeyId`는 `db-1`, `SecretProtection:DmlPayloads:ActiveKeyId`는 `dml-1`로 설정합니다. 누락되거나 잘못되거나 재사용된 키는 시작 실패를 일으킵니다. 예제의 자리표시자는 의도적으로 유효하지 않습니다.

`HsSqlAgent.Hosting`은 `SecretProtection`을 자동 바인딩합니다. 모듈형 호스트에서는 명시적으로 바인딩해야 합니다.

```csharp
hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
```

새 bootstrap MCP 키에는 `Bootstrap:Databases:*:McpKeys:*:Key` 값을 명시하세요. 시작 시 키를 생성하거나 로그에 기록하지 않습니다. 기존 암호화 DB 비밀번호는 다시 입력해야 합니다. 기존 배포를 변경하기 전에 [업그레이드 가이드](/ko/docs/reference/upgrade-guide)를 읽으세요.

여러 모듈이 같은 `IServiceCollection`에서 `AddHsSqlAgentCore()`를 호출할 수 있습니다. 각 기능의 설정은 최초 등록 때만 허용되며 이후 재정의는 실패합니다. 서로 다른 서비스 컬렉션은 격리됩니다.

ASP.NET Core 애플리케이션에는 두 개의 NuGet 진입점이 있습니다. 이름이 비슷한 패키지로 보지 말고, 호스트 애플리케이션이 어떤 경계를 직접 관리할지에 따라 선택하세요.

| 목적 | 패키지 | 책임 범위 |
| --- | --- | --- |
| 전체 제품 포함 | `HsSqlAgent.Hosting` | HsSqlAgent가 표준 런타임, Admin Store, 내장 인증, MCP, 관리 API/UI, 텔레메트리, 예외 처리와 승인 공급자 선택을 관리합니다. |
| 맞춤 통합 구성 | `HsSqlAgent.Server` | 애플리케이션이 기능을 선택하고 기존 인증, 권한 부여, UI, 미들웨어 순서, 텔레메트리 또는 승인 공급자를 유지할 수 있습니다. |

.NET 호스트에 포함하지 않고 독립 서비스로 실행하려면 공식 Docker 이미지를 사용합니다.

## HsSqlAgent.Hosting으로 전체 제품 포함

완전 구성 패키지를 설치합니다.

```bash
dotnet add package HsSqlAgent.Hosting
```

표준 호스트를 등록하고 사용합니다.

```csharp
using HsSqlAgent.Hosting;

var builder = WebApplication.CreateBuilder(args);
builder.AddHsSqlAgentStandardHost();

var app = builder.Build();
app.UseHsSqlAgentStandardHost();
await app.RunAsync();
```

공식 ToolBox / Docker 호스트와 동일한 공식 기능 구성 및 설정 계약을 사용합니다. URL 바인딩과 로깅은 일반적인 ASP.NET Core 호스트 책임으로 남습니다.

`HsSqlAgent.Hosting`에는 표준 `HsSqlAgent.Server` 런타임과 공식 `HsSqlAgent.Approvals.Webhook` 어댑터가 포함됩니다. 런타임 NuGet 또는 DLL 플러그인 로딩은 추가하지 않습니다.

### DML 승인 공급자 선택

기본 공식 승인 방식은 MCP Elicitation입니다.

```json
{
  "DmlApproval": {
    "Provider": "McpElicitation"
  }
}
```

공식 범용 Webhook 어댑터를 사용하려면:

```json
{
  "DmlApproval": {
    "Provider": "Webhook",
    "Webhook": {
      "Endpoint": "https://approval.example.com/hssqlagent/requests",
      "CallbackUrl": "https://sql-agent.example.com/api/hs-sql-agent/approvals/webhook",
      "SigningSecret": "replace-with-a-unique-secret-at-least-32-bytes"
    }
  }
}
```

환경 변수는 일반 ASP.NET Core 구성 이름을 사용합니다. 예: `DmlApproval__Provider=Webhook`. 알 수 없는 provider 이름은 시작 시 실패합니다.

사용자 정의 `IDmlApprovalProvider`가 필요하면 `HsSqlAgent.Server`를 사용하고 의존성 주입으로 등록하세요. 승인 시스템에 임의 SQL 실행 권한은 전달되지 않습니다. SQL 검증, 승인 fingerprint 결합, 현재 상태 재검증과 최종 commit은 계속 HsSqlAgent가 소유합니다.

## HsSqlAgent.Server로 맞춤 통합 구성

모듈형 패키지를 설치합니다.

```bash
dotnet add package HsSqlAgent.Server
```

기존 애플리케이션의 인증과 권한 부여를 유지하면서 필요한 HsSqlAgent 기능만 추가할 수 있습니다.

```csharp
var hs = builder.Services.AddHsSqlAgentCore();

hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
hs.AddHsSqlAgentAdminStore(options =>
{
    options.Provider = "Postgres";
    options.ConnectionString =
        builder.Configuration.GetConnectionString("HsSqlAgent")!;
});
hs.AddHsSqlAgentHostAuthorization("SqlAgentAdmin");
hs.AddHsSqlAgentAdminApi();
```

ASP.NET Core 파이프라인은 호스트가 관리합니다.

```csharp
var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();
app.UseHsSqlAgentAdminApi();
app.MapControllers();

app.Run();
```

호스트 권한 부여 모드에서는 `AddHsSqlAgentBuiltInAuth()`를 호출하지 않습니다. HsSqlAgent는 인증된 `HttpContext.User`를 사용하며 내장 인증 컨트롤러나 HsSqlAgent 인증 스키마를 설치하지 않습니다.

`/runtime/db-management.edit`, `/auth/role.view` 같은 canonical permission은 안정적인 권한 리소스 식별자이며 URL 경로가 아닙니다. 호스트 policy에서 기존 권한 모델로 매핑할 수 있습니다.

### 필요할 때만 MCP 추가

MCP는 별도의 기계 접근 보안 경계입니다.

```csharp
hs.AddHsSqlAgentMcp(options =>
{
    options.PublicEndpoint = "https://example.com/mcp";
    options.HmacSecretKey = builder.Configuration["HMAC_KEY"]!; // >= 32 bytes
});
```

애플리케이션을 만든 뒤 매핑합니다.

```csharp
app.UseHsSqlAgentMcp();
```

MCP 키, 도구 범위, 테이블 범위, 속도 제한과 HMAC 검증은 사람/관리자 권한 부여와 독립적입니다.

### 필요할 때만 내장 인증 사용

HsSqlAgent 자체 JWT/member/role 모델이 필요하다면 호스트 권한 부여 대신 내장 인증을 선택합니다.

```csharp
hs.AddHsSqlAgentBuiltInAuth(options =>
{
    options.Jwt.SecretKey = builder.Configuration["JWT_KEY"]!; // >= 32 bytes
});
```

내장 인증과 호스트 권한 부여는 함께 사용할 수 없습니다. 모듈형 호스트에서는 관리 UI도 생략할 수 있습니다.

## 기능별 설정 책임

| 기능 | 관리 내용 |
| --- | --- |
| `AddHsSqlAgentRuntime()` | 런타임, 운영 기능, 조정, SQL 동시 실행과 DML 승인 영속성 |
| `AddHsSqlAgentAdminStore()` | Admin database provider와 연결 문자열 |
| `AddHsSqlAgentBuiltInAuth()` | JWT, 비밀번호 재설정/SMTP, 기업 인증/OIDC |
| `AddHsSqlAgentHostAuthorization()` | 기존 ASP.NET Core 권한 policy로 위임 |
| `AddHsSqlAgentMcp()` | 공개 MCP 엔드포인트와 MCP key HMAC secret |
| `AddHsSqlAgentAdminApi()` | 관리 컨트롤러와 검증/예외 매핑 |
| `AddHsSqlAgentTelemetry()` | Prometheus와 OTLP 설정 |

선택하지 않은 기능의 설정은 할당되거나 검증되지 않습니다.

## G5: MySQL 8.4 스키마 변경(명시적 활성화 필요)

MySQL InnoDB의 **단일 DDL 원자성은 애플리케이션 트랜잭션으로 되돌릴 수 있다는 뜻이 아닙니다**. 일반 CREATE TABLE은 암묵적으로 커밋되며 ROLLBACK으로 취소할 수 없습니다. 기존 execute_ddl_sql 도구는 기본적으로 숨겨지고 거부됩니다. MySQL 전용 활성화, MCP 접근 키에 대한 명시적 도구 권한 및 독립적인 DDL 승인 서비스가 모두 필요합니다.

최초 지원 범위는 데이터베이스 접두사가 없는 단일 CREATE TABLE과 기본 부호 있는 INT 열 1~16개뿐입니다. 임시 테이블, 조회 결과로 테이블 만들기, 기본값, 제약 조건, ALTER, INDEX, DROP 및 여러 문장은 허용하지 않습니다. 미리보기는 실제 메타데이터만 읽습니다. 승인 후 새 연결에서 MySQL 8.4 서버 식별자, 허용된 데이터베이스, 대소문자 규칙, InnoDB 엔진 및 대상 부재를 다시 확인합니다. SqlCore가 컴파일한 원본 SQL을 한 번만 실행하고 실제 열을 검증합니다.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentMySqlDdl(new MySqlDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedDatabases = new HashSet<string>(StringComparer.Ordinal) { "app_database" },
    PolicyRevision = "mysql84-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
```

세션 잠금은 이 서비스의 요청끼리만 조정하며 **외부 클라이언트의 변경을 차단하지 않습니다**. 실행이 시작된 뒤 결과를 증명할 수 없으면 outcome_unknown을 반환합니다. 자동 재시도하지 말고 실제 데이터베이스 상태를 확인해야 합니다. DML 승인은 DDL 승인으로 대체할 수 없습니다. 기본 읽기 전용 도구 4개와 DML/DDL 미선택 상태는 그대로 유지됩니다.

## G5: Oracle 26ai 스키마 변경(명시적 활성화 필요)

Oracle은 DDL 문장 **실행 전후에 암묵적으로 커밋**합니다. 이후 작업이 실패하더라도 이미 생성된 테이블은 애플리케이션의 ROLLBACK으로 되돌릴 수 없습니다. `execute_ddl_sql` 도구는 기본적으로 숨김 및 거부 상태를 유지합니다. Oracle 전용 활성화, MCP 접근 키의 명시적 사용 권한, 별도의 DDL 승인자가 필요합니다.

지원 범위는 로그인한 사용자 자신의 스키마에 대한 **단일 CREATE TABLE**이며 스키마 접두사 없이 기본 INTEGER 열 1~16개만 허용합니다. 제약 조건, 기본값, ALTER, INDEX, DROP, 조회 기반 테이블 생성, 다중 문장은 거부합니다.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentOracleDdl(new OracleDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedPdbNames = new HashSet<string>(StringComparer.Ordinal) { "FREEPDB1" },
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "SQLCORE" },
    PolicyRevision = "oracle26ai-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Also explicitly grant execute_ddl_sql to the relevant MCP access key.
```

```sql
-- DBA-run setup for the designated SQLCORE account in the target PDB.
GRANT SELECT ON SYS.V_$DATABASE TO SQLCORE;
GRANT SELECT ON SYS.V_$PDBS TO SQLCORE;
GRANT SELECT ON SYS.DBA_TRIGGERS TO SQLCORE;
GRANT EXECUTE ON SYS.DBMS_LOCK TO SQLCORE;
```

실제 Oracle 26ai(커널 23.26 이상), 쓰기 가능한 기본 PDB, 허용된 PDB 및 사용자 스키마, 모든 DDL 트리거를 확인할 수 있는 데이터 사전 권한, 대상 이름의 부재를 검사해야 합니다. 미리보기는 쓰기를 수행하지 않습니다. 승인 후 서비스 내부 요청끼리만 조정하는 세션 잠금으로 재검증하고, SqlCore가 컴파일한 SQL을 한 번 실행한 뒤 실제 열을 검사합니다. **외부 클라이언트까지 차단하는 잠금은 아닙니다**.

DDL 전송 후 결과를 확인할 수 없다면 `outcome_unknown`이며 **자동 재시도해서는 안 됩니다**. 먼저 DBA가 실제 PDB 상태를 확인해야 합니다. 기본 읽기 전용 도구 4개는 선택 상태, DML/DDL은 미선택 상태를 유지합니다.

## G6: PostgreSQL 빈 테이블 삭제(고위험, 별도 활성화)

기존 `execute_ddl_sql` 도구에는 PostgreSQL 전용 파괴적 작업 한 가지만 추가됩니다. 독립 승인 후 스키마를 명시한 `DROP TABLE schema.table RESTRICT`를 실행할 수 있습니다. **기본적으로 비활성화**되어 있으며 기존 DDL 추가 권한이나 DML 권한을 상속하지 않습니다. 커밋 이후 테이블 정의는 영구 삭제되며, 데이터가 남은 테이블은 삭제할 수 없습니다.


```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

services.AddHsSqlAgentPostgresDdl(new PostgresDdlExecutionOptions
{
    Enabled = true,
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "staging_cleanup" },
    AllowDropEmptyTable = true, // false by default; separate destructive opt-in
    AllowedDropPrincipals = new HashSet<string>(StringComparer.Ordinal)
    {
        "mcp-key:123" // replace with authenticated MCP key identity
    },
    PolicyRevision = "postgres-g6-destructive-governance-v1"
});
services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Separately grant execute_ddl_sql on the target MCP access key.
```

인증된 MCP 키의 식별자가 `AllowedDropPrincipals`에도 포함되어야 합니다. 일반 `execute_ddl_sql` 권한만으로는 파괴적 삭제가 승인되지 않으며, 허용 목록 변경 시 진행 중인 승인은 무효화됩니다.

실행 전에는 허용된 스키마, 테이블의 직접 소유권, 1~16개 INTEGER 열을 가진 일반 영구 테이블인지 확인하고 **데이터 행, 인덱스, 제약조건, 종속 뷰, 트리거, 행 수준 보안, 기본값, 상속, 게시 또는 입증되지 않은 부작용이 없는지** 실제 데이터베이스에서 검사합니다. 미리보기는 읽기 전용입니다. 독립적인 사람의 승인 후 PostgreSQL 트랜잭션 내에서 `ACCESS EXCLUSIVE` 잠금을 획득하고 실제 테이블 OID와 모든 조건을 재확인한 다음 컴파일된 `RESTRICT` 명령만 실행합니다. 삭제 결과를 확인한 뒤 커밋하며, 롤백을 확인한 경우에만 미커밋으로 판단합니다. 커밋이나 롤백이 불확실하면 `outcome_unknown`을 반환하고 **자동 재시도하지 않습니다**. `CASCADE`, `IF EXISTS`, 데이터가 있는 테이블, 다른 DB 및 여러 DDL 문은 여전히 금지됩니다. 기본 선택은 기존의 읽기 전용 도구 네 개 그대로입니다.

## G6/S16: PostgreSQL 원자적 DDL 일괄 실행(별도 활성화)

기존 `execute_ddl_sql` 도구는 PostgreSQL 16에서 **서로 의존하지 않는 스키마 지정 CREATE TABLE 문 2~4개**를 하나의 순서가 보존되는 불변 계획, **한 번**의 독립적인 사람 승인 및 **하나**의 실제 데이터베이스 트랜잭션으로 실행합니다. 일반 단일 DDL 권한은 일괄 실행을 허용하지 않습니다. 임의 SQL 스크립트 실행을 지원하지 않습니다.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

services.AddHsSqlAgentPostgresDdl(new PostgresDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowCreateTableBatch = true, // false by default
    AllowedBatchPrincipals = new HashSet<string>(StringComparer.Ordinal)
    {
        "mcp-key:123" // authenticated MCP key ID
    },
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal)
    {
        "staging_cleanup"
    },
    PolicyRevision = "postgres-g6-atomic-batch-v1"
});
services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Separately grant execute_ddl_sql to the key.
```

```sql
CREATE TABLE staging_cleanup.import_a (id INTEGER NOT NULL);
CREATE TABLE staging_cleanup.import_b (id INTEGER NOT NULL);
```
인증된 MCP 키를 `AllowedBatchPrincipals`에 별도로 등록하고 `execute_ddl_sql`도 명시적으로 허용해야 합니다. 읽기 전용 미리보기는 순서대로 컴파일된 SQL, 각 대상의 실제 Before 상태, 일괄 변경 요약을 표시합니다. 한 번의 독립 승인 후 PostgreSQL 클러스터·스키마 신원과 모든 대상의 부재를 재검증하고 협조 잠금을 획득하여 컴파일된 문만 실행합니다. 각 새 테이블을 검증한 다음 **하나의 트랜잭션**을 커밋합니다. 확인된 롤백은 부분 적용을 남기지 않습니다. 커밋이나 롤백이 불확실하면 `outcome_unknown`을 반환하며 **자동 재시도하지 않습니다**. 문 간 ALTER／INDEX 의존, DROP, DML, CTAS, 중복·다른 스키마 이름, MySQL／Oracle 암묵적 커밋 배치와 다른 DB 배치는 차단됩니다. 읽기 전용 기본 도구 네 개만 선택됩니다.
