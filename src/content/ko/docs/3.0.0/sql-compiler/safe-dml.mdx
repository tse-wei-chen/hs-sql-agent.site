## 승인 수락, 불확실한 결과 및 대상 증거

선택적 조건이 필요한 경우 `WHERE 1=1`처럼 항상 참임이 입증되는 `UPDATE`/`DELETE` 필터는 거부됩니다. 사람의 승인은 여전히 정확한 계획과 행 집합 증거에 결합됩니다.

사용자 지정 challenge store는 단일 및 배치 작업 모두에 대해 `TryPromoteAsync`를 원자적으로 구현해야 합니다. Redis와 영속 재개는 버전이 있는 봉투 형식을 사용합니다. 호환되지 않는 challenge에는 새 미리 보기와 동의가 필요합니다. [업그레이드 가이드](/ko/docs/reference/upgrade-guide)를 참조하세요.

`dml.commit_outcome_unknown`과 `dml.rollback_outcome_unknown`은 서로 다르며 둘 다 재시도할 수 없는 결과입니다. 승인 및 대상 증거를 보관하고 독립적으로 조사하세요. witness나 Redis 키가 없다고 롤백이 입증되는 것은 아닙니다. 불확실한 변경을 자동 재실행하지 마세요. 커밋이 확인된 뒤 감사 저장에 실패하더라도 변경 실패로 보고하면 안 됩니다.

`AddHsSqlAgentTargetExecutionFence()`는 선택적 기능입니다. 대상 준비와 별도로 이전 worker의 DML 권한 철회를 입증해야 합니다. 등록된 커밋마다 실제 연결에서 롤백 전용 준비 검증 트랜잭션 두 개를 추가 실행하고, 커밋 후 Admission과 Witness를 독립적으로 읽습니다. Oracle의 witness 고유성 충돌 진단만 READ COMMITTED이며 나머지 검증은 SERIALIZABLE입니다. 증거가 모순되면 불확실한 결과를 반환합니다. 전체 worker 등록이나 실행 중 worker의 자동 조정을 보장하지 않습니다.

DML은 Query보다 더 엄격한 실행 경로를 사용합니다. 실제 commit 시점에도 승인 내용이**동일한 Mutation Evidence**를 설명해야 하기 때문입니다.

## 하나의 Tool로 단일·다중 Statement 지원

`execute_dml_sql`은 하나 이상의 지원 `UPDATE`, `DELETE`, `INSERT ... VALUES`를 받을 수 있으며 여러 Statement는 세미콜론으로 구분합니다. 제한된 SQLite `INSERT ... SELECT` 도 지원하지만 **단일 문장만** 허용되며 다중 문장 배치에는 포함할 수 없습니다.

별도 batch DML Tool은 없습니다. 여러 Statement는 하나의 Batch로 Parse되고 한 번 승인된 뒤 원래 순서대로 실행되며 하나의 서버 소유 Transaction에서 원자적으로 commit됩니다.

Client가 보내는 `BEGIN`, `COMMIT`, `ROLLBACK` 같은 Transaction-control SQL은 허용하지 않습니다. Transaction 경계는 서버가 소유합니다.

## 승인에 바인딩되는 Evidence

`UPDATE` / `DELETE` 승인은 Preview에서 관찰한 정확한 Primary Key Row Set에 바인딩됩니다. Commit Transaction 안에서 각 Statement의 실제 변경 직전에 다시 검증합니다.

`INSERT ... VALUES`는 불변 Literal Payload와 정확한 Compile Command에 바인딩됩니다.

### SQLite 단일 문장 소스 행 승인 (G9/M09, develop 전용)

제한된 `INSERT ... SELECT` 는 **SQLite에서만** 허용됩니다. 직접 읽는 원본과 삽입 대상은 스키마를 명시한 실제 `main` 테이블이어야 하며, 동일 테이블이거나 서로 다른 두 테이블일 수 있습니다. 서로 다른 경우 실제 스키마를 각각 검증합니다. 중복되지 않는 명시적 대상 열, 직접 원본 열 투영, `WHERE 열 = NULL이 아닌 리터럴`, 양수이면서 유한한 행 제한, `AddHsSqlAgentNativeDmlSchemaFreshness()` 가 필수입니다.

미리 보기는 **모든 원본 투영 값**에 승인을 묶으며 새 대상 ID를 미리 만들어 내지 않습니다. 커밋에서는 먼저 SQLite 쓰기 예약을 확보하고 동일 트랜잭션에서 실제 스키마와 원본 행을 재검증한 후 컴파일된 INSERT를 한 번 실행합니다. SQLite **3.35 이상**에서는 중복되지 않은 별칭 없는 직접 대상 열에 한정하여 `RETURNING` 을 허용합니다. 실제 삽입 결과는 **커밋 성공 후에만** 반환되며 원본 미리 보기와 구분됩니다. RETURNING의 와일드카드·표현식·별칭, CTE, JOIN, UPSERT, 첨부 DB, 다중 문장, 다른 DB는 계속 거부됩니다. DML 권한과 독립 승인은 그대로입니다.

앞선 Statement가 뒤 Statement의 승인된 Row Set을 바꾸면 Batch 전체가 fail closed로 rollback됩니다.

## 승인 Provider

기본 공식 Provider는 MCP Elicitation입니다. Host는 공식 `HsSqlAgent.Approvals.Webhook` adapter를 사용하거나 `HsSqlAgent.Server`에서 `IDmlApprovalProvider`를 구현할 수 있습니다.

승인 Provider는 transport-neutral Evidence를 받을 뿐 SQL 실행 primitive를 받지 않습니다. Database Connection, Transaction, 검증된 Plan, commit 권한은 제공되지 않습니다.

## Durable Pending Approval

비동기 Workflow의 Provider는 `Pending`을 반환할 수 있습니다. Admin Store가 있으면 hs-sql-agent는 보호된 Resume Intent와 Approval Fingerprint를 저장합니다.

나중에 완료 Decision이 오면 현재 권한과 DB 설정을 다시 읽고 DML을 재 Parse / Preview하며 승인 Evidence를 비교한 뒤 새로운 단기 Execution Challenge를 만듭니다. 권한, DB 설정, Policy, Plan, Row Set, affected-row Evidence가 바뀌면 stale로 처리하고 commit하지 않습니다.

재개되는 것은**실행 Intent**이지 오래된 Database Session이 아닙니다.

## SQL Server: CTE 기반 수정 작업의 복합 INT 키

SQL Server UPDATE 또는 DELETE는 실제 원본 테이블에 **NULL을 허용하지 않는 두 개의 INT 열로 구성된 기본 키 또는 고유 인덱스**가 확인된 경우에만 명시적 허가를 받아 1~3단계의 비재귀 선형 CTE를 사용할 수 있습니다. 두 키 열은 물리적 인덱스 순서를 유지하며 각 CTE를 통해 변경 없이 전달되어야 합니다. 대상 테이블의 해당 INT 열마다 필수 `AND` 조건과 일반 `=` 비교가 있어야 합니다. 실행 전에는 실제 시스템 카탈로그 확인, 변경 대상 행 미리보기, 승인 내용 연결 및 동일 트랜잭션 내 메타데이터 재검증이 필요합니다.

키 누락·순서 변경, `OR`, 형 변환, NULL 허용 또는 계산 열, 필터링되거나 비활성화된 인덱스, 행 수를 늘리는 조인은 거부됩니다. 다른 데이터베이스의 실행 범위는 확대되지 않습니다.

### 제한된 두 분기 CTE 합류 증명 (G9/M06, develop 전용)

SQL Server CTE `UPDATE`/`DELETE`는 **3개 노드의 분기·합류**를 한정적으로 지원합니다. 두 CTE가 **동일한 실제 UNIQUE 원본 테이블**에서 순서가 보존된 두 키 열을 직접 투영하고, 세 번째 CTE가 두 일반 등호를 사용한 `INNER JOIN`으로 합류합니다. 변경 대상 역시 두 키 열 모두와 비교해야 합니다.

임의의 CTE DAG를 허용하는 것은 아닙니다. F# 정적 카디널리티, F# 변경 실행 허용 검사, Host의 실제 인덱스 검증은 독립적으로 수행되며 미리 보기→독립 승인→동일 트랜잭션에서 잠금을 유지하는 `IsCurrent`가 필요합니다. 다른 원본 테이블, 키 조건 누락·중복, `OR`, `LEFT JOIN`, 필터, `CAST`, 계산 열, 추가 CTE 분기 및 모호한 별칭은 거부합니다. 나머지 5개 DB와 MCP 기본 설정은 변경되지 않습니다.

### 2단계 파생 테이블의 물리 UNIQUE 키 계보 검증 (G9/M06, develop 전용)

SQL Server의 제한된 CTE `UPDATE`/`DELETE`는 기존 1~3단계 CTE 앞에서 **비 LATERAL 직접 열 투영인 파생 테이블을 최대 2단계까지** 사용할 수 있습니다. 두 단계 모두 실제 UNIQUE 키의 전체 열과 순서를 보존해야 합니다. 예를 들어 `FROM (SELECT mid.x AS x, mid.y AS y FROM (SELECT s.k1 AS x, s.k2 AS y FROM dbo.Source AS s) AS mid) AS d`를 `SELECT d.x AS a, d.y AS b`로 이어갈 수 있습니다. 아래 단일 단계 기능의 확장이며 **임의의 다중 분기 CTE DAG는 지원하지 않습니다**.

F# 카디널리티, F# 변경 실행 승인 단계, Host의 실제 인덱스 검증이 독립적으로 키 계보를 확인합니다. 물리 UNIQUE 인덱스, 정확한 타입과 정렬 규칙, 대상 키 등호 조건, 미리 보기→독립 승인→커밋 및 같은 트랜잭션에서 잠금을 유지하는 `IsCurrent`가 계속 필요합니다. 세 번째 파생 단계, 추가 소스, JOIN, WHERE, DISTINCT, 그룹화, 정렬, 페이징, 계산/형변환 키, 중복 별칭, 키 누락이나 순서 변경은 거부합니다. 나머지 5개 DB, 기본 읽기 전용 도구 4개, DML 기본 비활성화는 유지합니다.

### 단일 Derived Table의 UNIQUE 키 보존 증명 (G9/M06, develop 전용)

SQL Server의 제한된 CTE `UPDATE`/`DELETE`는 기존 1~3단 CTE 앞에 **실제 물리 테이블 하나만 읽는 비 LATERAL Derived Table 한 단계**를 허용합니다. 파생 SELECT와 후속 CTE는 `FROM (SELECT s.k1 AS x, s.k2 AS y FROM dbo.Source AS s) AS d`, `SELECT d.x AS a, d.y AS b`처럼 정렬된 전체 UNIQUE 키 열을 직접 다시 이름 붙일 수 있습니다. F# 카디널리티 증명과 Host의 실제 인덱스 검증은 각자 열 출처를 독립적으로 확인합니다. 실행 권한에는 실제 전체 UNIQUE 인덱스 및 원본/대상 SQL 타입·NULL 비교·정렬 규칙 일치가 필요하며, 가상 Catalog나 별칭은 권한이 아닙니다.

이는 **임의의 Derived Table 또는 다중 분기 CTE DAG를 허용하지 않습니다**. 파생 계층의 JOIN, WHERE, DISTINCT, GROUP/HAVING, 집계, ORDER, LIMIT/TOP/OFFSET, UNION, 중첩 파생 테이블/CTE, LATERAL, CAST/계산 키, 중복 별칭 및 누락된 고유 키는 계속 거부합니다. 미리 보기→독립 승인→커밋, 정확한 행 집합과 동일 커밋 트랜잭션의 잠금 기반 `IsCurrent`가 필요하며 인덱스 철회 후 승인도 차단됩니다. 실제 SQL Server 2022 테스트는 1~3단 CTE, 정수/소수/UUID/텍스트 복합 키 및 UPDATE/DELETE를 다룹니다. 나머지 5개 DB 및 기본 MCP/DML 권한은 변경하지 않습니다.


### 언어별 정렬 규칙과 UNIQUE 동등 비교의 정확한 증명 (G9/M05, develop 전용)

SQL Server의 제한된 CTE UPDATE/DELETE는 길이가 지정된 기본 제공 `VARCHAR(n)`/`NVARCHAR(n)`에 대해 **서로 구분되는 네 가지 비교 계약**을 검증합니다. 기존 `Latin1_General_100_BIN2`(이진 코드 포인트)에 더해 `Latin1_General_100_CI_AS`(대소문자 무시, 악센트 구분), `Latin1_General_100_CI_AI`(모두 무시), `Latin1_General_100_CS_AS`(모두 구분)를 지원합니다. 원본 UNIQUE 인덱스, 대상 비교 열 및 별도로 검증한 두 번째 JOIN 테이블은 **모든 키 위치에서 네이티브 SQL 타입, 길이, 실제 열 정렬 규칙이 동일**해야 합니다. 단순한 Text 스냅샷은 실행 권한이 아니며, F# 폐쇄형 모델이 실제 열과 인덱스를 검증합니다.

실제 SQL Server 2022 테스트는 대소문자나 악센트가 다른 값의 **UNIQUE 충돌 결과**와 일반 `=` 동등 비교가 일치하는지 확인합니다. 기존 1~3단계 CTE, 완전한 AND 키 비교, 문자열/UUID/숫자 복합 키, 미리 보기→독립 승인→커밋 및 트랜잭션 내 `IsCurrent`는 유지됩니다. NULL 허용 원본 UNIQUE에는 여전히 `ANSI_NULLS ON`이 필요합니다. ProofIdentity는 **v9**로 올라가 이전 승인은 무효화됩니다. 정렬 규칙 불일치, 명시적 `COLLATE` 덮어쓰기, VARCHAR/NVARCHAR 암시적 변환, 검증하지 않은 CS_AI/_SC/_UTF8, CHAR/MAX, 필터/비활성 인덱스 및 누락된 동등 조건은 계속 차단합니다. 다른 다섯 DB와 MCP 권한은 변하지 않습니다.


### NULL 허용 SQL Server UNIQUE 키와 일반 동등 비교의 증명 (G9/M05, develop 전용)

SQL Server 원본 키에 NULL 허용 열을 포함할 수 있는 경우는 **순서가 지정된 전체 1~2개 키 열을 보호하는, 실제 활성 상태이며 필터가 없는 물리 UNIQUE 인덱스가 존재할 때뿐**입니다. 제한된 CTE `UPDATE`/`DELETE`에는 대상과 연결되는 모든 `AND`/일반 `=` 조건과 실제 접속의 `ANSI_NULLS ON`(`@@OPTIONS`로 검사)이 필요합니다. 원본 키에 NULL이 하나라도 포함되면 일반 동등 비교의 결과는 UNKNOWN이므로 **대상 행과 일치하지 않습니다**. NULL 안전 비교나 임의의 NULL 허용 테이블 스캔을 승인하는 것이 아닙니다. 복합 대상 키는 계속 NOT NULL이어야 하며, 대상 동등 비교가 없는 `VerifyLive`는 NULL 허용 원본 키를 증명할 수 없습니다.

F#의 폐쇄형 NULL 비교 증명은 전체 UNIQUE 인덱스, 실제 기본 제공 물리 타입, 원본 NULL 허용 정보, 변경할 수 없는 메타데이터 요약 및 **v8 ProofIdentity**에 결합됩니다. 실제 Commit 연결과 트랜잭션에서 잠금을 유지하면서 `ANSI_NULLS ON`, 인덱스 및 스키마를 다시 확인합니다. `WHERE key IS NOT NULL`을 포함하는 필터 UNIQUE, 비활성/비고유 인덱스, `OR`, `COALESCE`, 계산된 키, CAST, NULL 안전 연산자, 가상 Catalog는 실행 증명이 아닙니다. 실제 SQL Server 2022 테스트는 NULL 허용 BIGINT/DECIMAL/UUID/BIN2 VARCHAR 복합 키, 1~3단 CTE, UPDATE/DELETE, Preview→독립 승인→Commit, NULL 비일치 및 인덱스 철회 시 차단을 확인합니다. 다른 5개 DB와 MCP 기본 권한은 변경하지 않습니다.


### BIN2 VARCHAR／NVARCHAR 물리 문자열 키의 정확한 검증 (G9/M04, develop 전용)

SQL Server CTE `UPDATE`/`DELETE`의 물리 고유성 증명은 길이가 제한된 기본 제공 `VARCHAR(n)`과 `NVARCHAR(n)`을 지원합니다. 단, **실제 데이터베이스 정렬 규칙이 정확히 `Latin1_General_100_BIN2`인 경우에만** 허용합니다. 원본 UNIQUE 인덱스, 대상 비교 열 및 별도로 검증된 두 번째 JOIN 테이블의 키는 **모든 키 순서에서 네이티브 SQL 타입, 최대 길이 및 정렬 규칙이 동일**해야 합니다. `NVARCHAR`는 `sys.columns.max_length`의 바이트 수를 검증한 뒤 문자 길이로 환산합니다. `MAX`, `CHAR`/`NCHAR`, 길이 불일치, Unicode와 비 Unicode 간 암시적 변환, 다른 BIN2 또는 대소문자를 구분하지 않는 정렬 규칙, 사용자 정의 별칭, NULL 허용 원본 키는 거부됩니다.

Host는 실제 문자열을 기존 `SqlSchemaValueKind.Text`로 분류하지만 **스냅샷 분류 자체로 실행 권한을 부여하지 않습니다**. F# 폐쇄형 키 모델은 실제 열 길이와 정렬 규칙, 내장 타입, 전체 고유 인덱스 및 제한된 CTE/JOIN의 필수 일반 동등 비교를 독립적으로 검증합니다. Preview→독립 승인→Commit 시 실제 커밋 트랜잭션에서 잠금을 유지한 `IsCurrent` 재검증도 그대로 적용됩니다. ProofIdentity는 v7으로 올라가 이전 승인은 무효화됩니다. 실제 SQL Server 2022 테스트는 문자열과 UUID/정수/소수 복합 키, UPDATE/DELETE, 1~3단 CTE, 자체/별도 테이블 JOIN, 인덱스 철회, 길이 및 정렬 규칙 불일치 거부를 검증합니다. 나머지 5개 데이터베이스와 MCP 도구 및 기본 권한은 그대로입니다.


### CTE에 키가 아닌 열을 함께 투영하기（G8／M03）

1~3단계 CTE에서는 필수 1~2개 INT 키 열 외에 **원본 행에서 직접 가져온 다른 열**도 함께 선택할 수 있습니다(단계당 최대 32개 열). 예를 들어 `SELECT k1 AS a, payload AS extra, k2 AS b` 다음에 `SELECT a, extra, b`를 사용할 수 있습니다. 키는 모든 단계에서 한 번씩만 나타나고 실제 고유 인덱스의 상대 순서를 유지해야 하며, 최종 조건에서도 필수 `AND` 및 일반 `=` 비교가 필요합니다. 키 중복·변환·계산, 모호한 별칭, 다중 원본 및 행을 늘리는 JOIN은 여전히 거부됩니다. 실제 인덱스 검증, 미리 보기, 승인, 커밋 트랜잭션 재검증은 그대로이며 일반 JOIN이나 다른 데이터베이스의 실행 권한이 추가되는 것은 아닙니다.

### 단일 행 파생 JOIN의 안전성 증명（G8／M07, 제한된 범위）

SQL Server의 각 CTE 단계에서는 **행 수가 늘지 않는다고 증명된 JOIN을 최대 하나** 사용할 수 있습니다. 조인 대상은 `SELECT 1 AS marker`처럼 독립적인 파생 쿼리여야 하며 `FROM`, `WHERE`, `UNION`, 그룹화나 추가 행을 포함할 수 없습니다.`CROSS JOIN (SELECT 1 AS marker) AS one`은 원본 행 수를 유지하고, 상수 동등 비교 `ON 1 = 1`을 사용하는 `INNER JOIN`과 `LEFT JOIN`도 행 수를 늘리지 않습니다. 실제 INT 고유 키, 직접 키 투영, 미리 보기, 승인 및 커밋 트랜잭션의 실제 증명은 계속 필수입니다. **위의 단일 행·셀프 JOIN 증명만으로는 다른 물리 테이블과의 JOIN을 허용하지 않습니다. 아래에서 별도의 두 고유 인덱스 증명으로 제한적으로 허용합니다, APPLY, 상관 하위 쿼리, 여러 행을 반환하는 파생 소스나 임의 JOIN은 허용하지 않습니다.**

추가로 **동일한 물리 원본 테이블을 서로 다른 별칭으로 연결하는 INNER／LEFT 셀프 JOIN**을 제한적으로 허용합니다. 이 경우 ON 조건은 실제 DB에서 검증된 INT 고유 키의 **모든 구성 열**을 필수 AND와 일반 동등 비교로 연결해야 합니다. 그러면 두 번째 별칭은 원본 행마다 최대 한 행만 일치합니다. 일부 키 누락, OR만 있는 조건, 계산·형 변환 키나 다른 테이블과의 JOIN은 거부됩니다.

### 서로 다른 물리 테이블 JOIN의 이중 고유 키 증명（M07）

SQL Server CTE에서는 다른 물리 테이블에 대해 하나의 **INNER JOIN** 또는 **LEFT JOIN**을 사용할 수 있습니다. 두 원본 테이블 모두 실제 데이터베이스에서 각각 검증된, NULL을 허용하지 않는 1~2개 열의 `INT`／`BIGINT` 고유 키가 필요하며 인덱스는 활성화되고 필터가 없어야 합니다. `ON` 조건은 필수 `AND`와 일반 `=`로 모든 키 열을 연결하고 각 위치의 실제 자료형도 정확히 일치해야 합니다. 가상 카탈로그, 암시적 형 변환, 일부 키만 비교하거나 필터링된 인덱스는 증거가 되지 않습니다. 두 인덱스 식별 정보는 실행 계획·승인에 함께 결합되고 실제 커밋 트랜잭션에서 다시 확인됩니다. 미리 보기 후 어느 증명이든 무효화되면 커밋을 거부합니다. 세 번째 물리 원본, 다대다 JOIN, `RIGHT`／`FULL JOIN`, 다른 DB 방언으로의 변환이나 임의의 JOIN은 허용되지 않습니다.

### 전체 키 상관 EXISTS／NOT EXISTS 필터（M07, 제한 범위）

SQL Server의 CTE 기반 `UPDATE`／`DELETE`는 첫 번째 CTE의 `WHERE`에서 **`EXISTS`(세미 조인) 또는 `NOT EXISTS`(안티 조인)**을 사용할 수 있습니다. 단, 하위 쿼리는 실제 고유 키가 검증된 **동일한 원본 테이블을 다른 별칭으로** 읽어야 합니다. 리터럴만 선택하며 추가 JOIN, 그룹화, 정렬 또는 집합 연산은 금지됩니다. 1~2개 `INT`／`BIGINT` 고유 키 전체를 필수 `AND`와 일반 `=` 비교로 연결해야 하며, 내부 열과 상수의 비교를 추가해 결과를 줄일 수 있습니다. 이는 행을 필터링할 뿐 늘리지 않으며 실제 인덱스 증명, 미리 보기, 승인 바인딩 및 커밋 트랜잭션 재검증이 계속 필요합니다. **임의의 중첩 쿼리, 미검증 다른 테이블, 일반적인 EXISTS／안티 조인 실행 권한은 허용하지 않습니다.**

### TINYINT 및 SMALLINT 물리 키의 정확한 형식 검증 (G9/M04, develop 전용)

SQL Server의 CTE 기반 `UPDATE`/`DELETE` 실제 고유 키 검증은 기존 `INT`, `BIGINT` 외에도 기본 제공 `TINYINT`(부호 없는 8비트)와 `SMALLINT`(부호 있는 16비트)를 지원합니다. 1~2열 물리 고유 키에서 원본, 대상, 별도로 검증한 JOIN 테이블의 대응 열은 **인덱스의 각 키 위치에서 실제 SQL Server 자료형이 정확히 같아야** 합니다. 정수형 암시적 변환, 사용자 정의 별칭 형식, 가상 카탈로그는 실제 검증을 대신할 수 없습니다. 기존의 제한된 CTE 키 전달, 행을 늘리지 않는 JOIN 증명, 대상 행 미리 보기, 별도 승인, 변경 불가능한 계획 지문과 동일 트랜잭션에서의 인덱스 재검증은 계속 필수입니다. SQL Server 2022 실제 테스트는 수정·삭제, 혼합 키 형식, 인덱스 철회를 검증합니다. DECIMAL, UUID, NULL 허용 고유 키, 임의 JOIN 또는 다른 데이터베이스의 실행 권한은 추가되지 않습니다.


### UNIQUEIDENTIFIER 물리 키의 정확한 증명 (G9/M04, develop 전용)

SQL Server의 CTE `UPDATE`/`DELETE` 물리 고유성 증명은 이제 **기본 제공 128비트 `UNIQUEIDENTIFIER` 키**도 지원합니다. `Uuid`는 독립적인 스키마 값 종류이며 **숫자, 문자열 또는 이진 키로 위장하지 않습니다**. Host는 실제 `sys.tables`, `sys.columns`, `sys.types` 메타데이터를 읽어 원본, 대상, 별도로 검증된 두 번째 JOIN 테이블의 키 유형을 확인합니다. F#의 폐쇄형 키 모델은 전체 UNIQUE 인덱스 열과 스냅샷에 선언된 유형이 실제 물리 유형과 일치하는지 독립적으로 검증합니다. `UNIQUEIDENTIFIER`를 `INT`, `DECIMAL`, `VARCHAR`, `BINARY(16)`와 암시적으로 변환하여 실행 권한을 증명할 수 없습니다.

1~2개 구성요소의 키에서 UUID와 정확히 일치하는 정수/소수 키를 조합할 수 있습니다. 기존의 1~3단계 제한된 CTE, 행을 늘리지 않는 JOIN, 변경 미리 보기, 독립 승인, 커밋과 동일한 트랜잭션에서의 `IsCurrent` 재검증은 계속 필요합니다. ProofIdentity는 v6으로 갱신되어 이전 승인을 재사용할 수 없습니다. 실제 SQL Server 2022 테스트는 UUID UPDATE/DELETE, 기본/고유 인덱스, 자동 증명, 다른 물리 테이블 JOIN, 미리 보기 후 인덱스 철회 및 유형 불일치 거부를 검증합니다. MCP 도구, 기본 DML 선택, 임의 JOIN 권한이나 다른 5개 데이터베이스의 권한은 증가하지 않습니다.

### DECIMAL／NUMERIC 물리 키의 정확한 증명 (G9/M04, develop 전용)

SQL Server의 CTE 기반 `UPDATE`/`DELETE` 물리 고유 키 증명은 기본 제공 `DECIMAL(p,s)` 및 `NUMERIC(p,s)`도 지원합니다(`1 ≤ p ≤ 38`, `0 ≤ s ≤ p`). 두 이름은 SQL Server에서 동의어이지만 원본, 대상, 별도로 검증된 JOIN 테이블의 대응 키는 **각 인덱스 위치에서 정밀도와 소수 자릿수가 정확히 일치**해야 합니다. `DECIMAL(12,2)`를 `DECIMAL(13,2)`, `DECIMAL(12,3)` 또는 정수 키와 비교하는 암시적 형 변환은 고유성 증명이 아닙니다.

Host는 실제 `sys.columns` 및 `sys.types` 메타데이터를 읽고 원래 UNIQUE 인덱스의 **모든 키 열**을 확인합니다. 지원하지 않는 사용자 정의 별칭 형식이 포함되어도 `UNIQUE(a,b)`를 `UNIQUE(a)`로 잘못 판정하지 않습니다. F#의 폐쇄형 자료형은 정확한 정밀도와 소수 자릿수를 유지합니다. 기존의 1~3단계 제한된 CTE, 행 수가 증가하지 않는 JOIN, 대상 행 미리 보기, 독립 승인, 버전별 증명 식별 정보 및 동일 커밋 트랜잭션의 재검증은 그대로 유지됩니다. SQL Server 2022 실제 테스트는 소수값, 정수/소수 복합 키, 서로 다른 물리 테이블 JOIN, 인덱스 철회 및 정밀도 불일치 거부를 확인합니다. UUID/문자열 키, NULL 허용 고유 키, 임의 JOIN 및 다른 다섯 데이터베이스는 대상이 아닙니다.


## Fail-closed 규칙

승인 거절, 만료, stale, Fingerprint 불일치, 권한 철회, 현재 Policy 위반, 승인 Row Set 재현 실패 시 DML을 commit하지 않습니다.

[MCP Tools Reference](/ko/docs/mcp/tools-reference), [설정](/ko/docs/operations/configuration), [ASP.NET Core 통합](/ko/docs/integration/aspnet-core)을 참고하세요.

### 두 분기 CTE의 직접 데이터 열 (G9/M06, develop 전용)

두 분기와 합류 CTE는 완전하고 순서가 유지된 두 열의 UNIQUE 키 이외에 **직접 참조하는 데이터 열**을 전달할 수 있습니다. 각 투영은 최대 32열이며 중복 및 모호한 열 참조를 허용하지 않습니다. 합류 CTE는 왼쪽 분기에서만 직접 투영합니다. **데이터 열 자체는 유일성의 증거가 아닙니다**.

SQL Server에는 전체 INNER JOIN 키 조건, 변경 대상의 전체 키, 독립된 F# 증명, Host 실제 인덱스 검증, 미리 보기, 승인 및 같은 트랜잭션의 IsCurrent가 필요합니다. 계산/중복 열, 별칭 충돌, CAST, 오른쪽 분기의 직접 출력, 키 누락 및 다른 실제 원본 테이블은 거부됩니다. 다른 DB와 MCP 기본값은 그대로입니다.

### CTE 분기 내부의 상관 세미·안티 조인 필터 (M07, develop 전용)

SQL Server의 3개 CTE 분기·합류에서 각 실제 원본 분기는 `EXISTS` 또는 `NOT EXISTS`로 필터링할 수 있습니다. 단, 하위 쿼리는 **검증된 동일 실제 원본 테이블**을 읽고, 기존 두 UNIQUE 키 열 모두를 일반 동등 조건과 `AND`로 완전히 연결해야 합니다. 내부 열과 상수의 동등 조건을 추가할 수 있습니다. 합류 `INNER JOIN`과 DML 대상 비교에는 두 키가 모두 필요하며, 필터는 일치하는 행을 줄일 뿐 중복시키지 않습니다.

F# 카디널리티 증명, 독립 F# 쓰기 허용, Host 실제 인덱스 검증, 미리 보기와 승인 행 집합 일치, 같은 트랜잭션의 `IsCurrent`는 필수입니다. 다른 원본, 키 누락, `OR`, 계산 키, 추가 조인 및 모호한 별칭은 거부합니다. 임의 CTE DAG, 다중 원본 쓰기 또는 다른 DB의 기능을 여는 것은 아닙니다.

### M08: 독립적으로 검증된 두 실제 DML 원본 (develop 전용)

SQL Server 네이티브 `UPDATE ... FROM` 및 `DELETE ... FROM`은 완전한 키를 직접 보존하는 CTE와 **서로 다른 실제 테이블 한 개**를 동일한 `FROM`에서 참조할 수 있습니다. 대상→CTE 및 CTE→두 번째 테이블 모두에 두 열 전체 키의 일반 동등 조건이 필요합니다. 각 원본의 유효하고 필터 없는 실제 UNIQUE 인덱스, 열 순서, 자료형과 데이터 정렬 규칙을 독립적으로 검증합니다. 두 번째 원본은 첫 번째 인덱스의 증명을 빌릴 수 없습니다.

F# 정적 카디널리티 및 쓰기 승인 검사, Host의 실제 이중 인덱스 검증, 미리 보기→독립 승인→커밋 및 동일 트랜잭션의 `IsCurrent`가 필수입니다. 키 누락·순서 변경·계산 키·`OR`·검증되지 않은 세 번째 원본·인덱스 무효화·암묵적 형변환·교차 DB 변환은 거부됩니다. 임의 다중 원본 DML은 허용하지 않으며 기본 읽기 전용 도구 4개와 DML 비활성화 설정은 변하지 않습니다.

### M09: 다른 SQLite 실제 테이블을 읽는 INSERT SELECT (develop 전용)

SQLite는 **별도의 `main` 실제 원본 테이블**에서 직접 선택한 행을 명시된 `main` 대상 테이블에 삽입할 수 있습니다. 두 테이블의 실제 스키마·DDL·인덱스·트리거를**각각 검증**하며, 승인 증거는 양쪽 테이블, 컴파일된 INSERT와 미리 보기 SELECT, 전체 투영 값의 다중 집합, 최대 행 수 및 보안 정책에 결합됩니다. 커밋 전에 SQLite 쓰기 예약을 획득하고 동일 트랜잭션에서 두 테이블과 모든 투영 값을 다시 검증한 뒤 한 번만 삽입합니다.

예: `INSERT INTO main.users (name) SELECT name FROM main.other_users WHERE id = 1`. 양쪽은 모두 실제 `main` 테이블이어야 하고 명시적이며 중복되지 않는 대상 열은 별칭 없는 직접 원본 열과 연결되어야 합니다. WHERE는 ‘열 = NULL이 아닌 리터럴’만 허용합니다. CTE, JOIN, 집계, 계산식, 페이지, RETURNING 와일드카드·표현식·별칭, UPSERT, 첨부 DB, 다른 제공자, 다중 문, 승인 후 원본 변조는 거부합니다. 기본 읽기 전용 도구 4개와 DML 비활성화는 유지합니다.


SQLite 3.35 이상 예: `INSERT INTO main.users (name) SELECT name FROM main.other_users WHERE id = 1 RETURNING id, name`. 미리 보기에서 승인되는 것은 원본 `name` 과 행 수이며, 새 `id` 와 `name` 은 커밋 후에만 반환됩니다. 원본이 변경되면 롤백하고 결과 행은 반환하지 않습니다.

### M09: PostgreSQL 실제 테이블 INSERT SELECT (develop 전용)

PostgreSQL은 제한된 단일 문장 `INSERT INTO schema.target (열) SELECT 직접 열 FROM schema.source WHERE 열 = NULL이 아닌 리터럴` 을 실행할 수 있습니다. **소스와 삽입 대상이 동일한 실제 테이블인 경우도 새로 지원**하며, 기존처럼 같은 비시스템 Schema의 서로 다른 두 테이블도 허용합니다. 모두 일반 영구 테이블이어야 합니다. 명시적이며 중복되지 않는 대상 열, 직접 투영, 유한한 양의 행 제한, 소스 읽기 및 대상 쓰기 권한, `AddHsSqlAgentNativeDmlSchemaFreshness()`, 독립적인 DML 승인이 필요합니다. CTE, JOIN, 계산식, ON CONFLICT, 파티션·상속 테이블, RLS, 사용자 트리거, 재작성 규칙, Schema 생략 및 다른 DB는 계속 거부됩니다.

미리 보기는 **모든 소스 투영 값**, 행 수, 정책과 컴파일 명령을 승인에 묶고, 새로 생성될 대상 ID를 미리 만들어 내지 않습니다. 커밋 시 PostgreSQL SERIALIZABLE 트랜잭션은 **최초 Catalog 조회 이전에 SHARE ROW EXCLUSIVE NOWAIT 소스 잠금**을 획득합니다. **동일 테이블에는 한 개의 실제 스키마 증명과 한 개의 소스 잠금만 사용**하고, 잠금을 유지한 채 검증 후 삽입합니다. 서로 다른 테이블은 양쪽을 독립 검증하고 대상의 DDL 경쟁도 차단합니다. 소스 값·인덱스·구조 변경 또는 잠금 충돌은 거부나 롤백으로 이어지며 RETURNING 행을 반환하지 않습니다. 직접 대상 열 `RETURNING` 은 성공적인 커밋 후 실제 결과만 반환합니다.

동일 테이블 예: `INSERT INTO app.users (name) SELECT name FROM app.users WHERE id = 1 RETURNING id, name`. 서로 다른 테이블 예: `INSERT INTO app.users (name) SELECT name FROM app.import_users WHERE id = 1 RETURNING id, name`. DB 역할에는 필요한 PostgreSQL 잠금 권한이 있어야 합니다. MCP 도구나 공개 API는 추가하지 않고 읽기 전용 도구 네 개만 기본 선택되며 DML은 비활성화 상태입니다.

### M09: MySQL 8.4 InnoDB 소스 행 INSERT SELECT (develop 전용)

**MySQL 8.4／InnoDB에서만** 제한된 단일 문장 `INSERT INTO db.target (name) SELECT name FROM db.source WHERE id = 1` 을 허용합니다. 소스와 대상은 **동일한 비시스템 데이터베이스 내 같은 실제 InnoDB 테이블 한 개 또는 서로 다른 실제 테이블 두 개**이어야 합니다. 미리 보기에서 모든 소스 값과 행 수를 승인하고, 커밋에서 양쪽의 실제 테이블 구조·인덱스와 소스 행 전체를 다시 검증한 후 한 번만 삽입합니다. 소스 읽기와 대상 쓰기 권한은 별도로 필요하며 Approval 은 일회용이고 `AddHsSqlAgentNativeDmlSchemaFreshness()` 가 필수입니다.

커밋에서는 명시적 **SERIALIZABLE InnoDB 트랜잭션**과 잠금 읽기 및 트랜잭션 유지 메타데이터 잠금으로 소스와 DDL 변경을 보호합니다. 암묵적 커밋을 유발하는 `LOCK TABLES` 는 사용하지 않습니다. 숨겨진 Trigger 부재를 확인할 수 있도록 실행 계정에 **전역 Trigger 메타데이터 가시성**도 요구합니다. 양쪽 테이블에 Trigger·외래 키·MyISAM 같은 비트랜잭션 엔진이 있으면 거부합니다. 이 모드는 **`RETURNING` 미지원**이며 CTE, JOIN, UPSERT, 계산 투영, 다중 문장 및 미검증 데이터베이스도 거부합니다.

예: `INSERT INTO app.users (name) SELECT name FROM app.import_users WHERE id = 1`. MCP 도구는 늘리지 않고 기본 읽기 전용 도구 4개만 선택되며 DML 은 비활성화 상태입니다.

증명에는 실제 InnoDB `TABLE_ID` 와 MySQL `@@server_uuid` 도 묶습니다. 이름·DDL·원본 행이 같더라도 테이블이 재생성되면 이전 승인은 무효입니다. `INNODB_TABLES` 조회에는 `PROCESS` 권한이 필요하므로 전역 `PROCESS` 와 `TRIGGER` 메타데이터 가시성이 모두 필수이며 확인할 수 없으면 거부합니다.

#### 동일 테이블을 소스로 사용하는 경우: 하나의 실제 엔터티 증명 (develop 전용)

제한된 `INSERT INTO app.users (name) SELECT name FROM app.users WHERE id = 1` 도 허용합니다. 소스와 대상은 **같은 실제 InnoDB 테이블**이며 가짜 이중 스키마 증명을 만들지 않습니다. 미리 보기와 커밋은 하나의 `TABLE_ID`, `@@server_uuid`, 테이블 DDL 및 승인된 전체 소스 행 집합을 검증합니다. SERIALIZABLE 트랜잭션은 잠금 읽기와 메타데이터 잠금을 유지합니다. 소스 값·인덱스 변경, 동일 DDL로 테이블 재생성, 경합 쓰기, 약한 격리 수준, 승인 재사용은 모두 거부합니다. `RETURNING`, CTE, JOIN, UPSERT는 여전히 지원하지 않습니다.

### M09: 제한된 AND 소스 조건 (develop 전용)

**이전 범위:** 아래 AND 전용 조건은 M09 초기 제한입니다. 페이지 끝의 제한된 IN/OR 확장은 네 가지 네이티브 INSERT SELECT에만 이 제한을 대체합니다. 다른 CTE/JOIN의 OR 금지 조건은 유지됩니다.

기존 **SQLite, PostgreSQL, MySQL 8.4 InnoDB** 네이티브 `INSERT SELECT` 소스 행 승인에서 `WHERE` 절에 `AND` 로만 연결한 **1~4개**의 직접 `열 = NULL이 아닌 리터럴` 조건을 사용할 수 있습니다. 예: `INSERT INTO app.users (name) SELECT name FROM app.import_users WHERE id = 1 AND name = 'Carol'`. 소스/대상 실제 테이블 식별, 버전별 기능, 영향 행 수 제한, 권한, 승인 및 트랜잭션 요구 사항은 그대로 유지합니다. 커밋 전에 승인된 소스 행 전체와 실제 Catalog를 다시 검증합니다. 임의 SQL을 허용하는 것은 아닙니다.

조건 5개 이상, `OR`, `NOT`, 함수, 계산식, NULL 비교, 하위 쿼리, JOIN, CTE, UPSERT 및 검증되지 않은 Provider는 계속 거부됩니다. PostgreSQL/SQLite RETURNING은 기존에 증명된 제한을 따르며 MySQL RETURNING은 미지원입니다. 새 MCP 도구나 공개 API는 없고 DML은 기본 비활성화입니다.

### M09: SQL Server 2022 두 실제 테이블 INSERT SELECT 승인 (develop 전용)

SQL Server 2022는 동일 데이터베이스 내 **서로 다른 두 영구 실제 테이블**에서 제한된 단일 `INSERT INTO dbo.target (name) SELECT name FROM dbo.source WHERE id = 1` 을 승인할 수 있습니다. 소스 필터는 `AND` 로만 연결한 1~4개의 직접 `열 = NULL이 아닌 리터럴` 비교로 제한하며, 직접 열 투영과 유한한 양수 행 제한이 필요합니다. 소스 READ와 대상 INSERT 권한은 독립적으로 검사하고, 배타적 테이블 잠금 읽기에는 대상 SELECT 권한도 필요합니다. 네이티브 SqlCore 컴파일, 실제 Catalog 신원, 전체 소스 행 승인, 일회용 Challenge와 최신 스키마 증명이 필수입니다.

커밋은 실제 Catalog를 읽기 전에 같은 트랜잭션에서 **소스와 대상 모두에 트랜잭션 종료까지 유지되는 배타적 테이블 잠금**을 획득하여 경쟁 쓰기 및 DDL을 차단합니다. 승인된 모든 소스 값을 재검증한 후 한 번만 INSERT 합니다. 이 보수적 안전 방식은 다른 DML을 차단할 수 있습니다. `VIEW DEFINITION` 권한 부족, 검증 불가능한 제약 조건, 트리거, 외래 키, Temporal/Ledger/Graph 테이블, 행·인덱스 변경 및 잠금 경쟁은 거부·롤백합니다. SQL Server `OUTPUT` 와일드카드/별칭/식/`INTO`, CTE, JOIN, UPSERT, 계산 투영 및 미검증 Provider는 지원하지 않습니다. 새 MCP 도구 없이 읽기 전용 4개 기본 선택, DML 기본 비활성화는 유지합니다.

### M09: SQL Server 2022 동일 실제 테이블 INSERT SELECT (develop 전용)

이제 제한된 `INSERT INTO dbo.users (name) SELECT name FROM dbo.users WHERE id = 1` 처럼 **기존 일반 영구 실제 테이블 하나를 소스와 대상에 동시에 사용하는 경우**도 지원합니다. 미리 보기에서는 실제 SQL Server 개체 ID와 테이블·인덱스·제약 조건 전체 해시를 **한 번만** 검증하며 가짜 두 테이블 증명은 만들지 않습니다. 직접 열 투영과 `AND` 로만 연결한 1~4개 `열 = NULL이 아닌 리터럴` 조건, 유한한 양수 행 제한이 필요합니다. 테이블 SELECT／INSERT 및 `VIEW DEFINITION` 권한, 네이티브 스키마 재검증과 별도의 일회용 DML 승인은 필수입니다.

커밋에서는 SERIALIZABLE 트랜잭션을 시작하여 **최초 Catalog 조회 전에 같은 테이블의 TABLOCKX／HOLDLOCK 배타적 잠금을 하나만 획득하고 종료까지 유지**합니다. 실제 테이블 신원·DDL·승인된 전체 소스 열 값을 다시 검증한 후 한 번 INSERT하고 실제 행 수를 대조합니다. 자동 생성 대상 ID를 미리 보기에서 꾸며내지 않습니다. 소스 데이터/인덱스 변경, 동일 DDL 재생성, 동시 쓰기, 행 수 제한 초과와 승인 재사용은 거부·롤백합니다. 같은 테이블 잠금으로 다른 쓰기가 차단될 수 있습니다. `OUTPUT` 와일드카드/별칭/식/`INTO`, CTE, JOIN, UPSERT, 계산 투영, 미검증 Provider는 계속 거부합니다. 새 MCP 도구 없이 읽기 전용 네 개 기본 선택과 DML 기본 비활성화가 유지됩니다.

### M09: SQL Server 2022 승인된 INSERT SELECT의 네이티브 OUTPUT INSERTED (develop 전용)

기존에 실제 소스가 증명된 같은 테이블 또는 두 테이블 `INSERT SELECT` 에 INSERT 열 목록 뒤 `OUTPUT INSERTED.id` 또는 `OUTPUT INSERTED.id, INSERTED.name` 을 사용할 수 있습니다. 실제 삽입된 대상 값은 **커밋 성공 후** 반환되며 미리 보기에서 IDENTITY 생성 ID를 꾸며내지 않습니다. SERIALIZABLE 트랜잭션의 유지되는 배타적 테이블 잠금 아래 전체 소스 행과 스키마를 재확인하고 네이티브 INSERT 한 번의 행 수 일치를 확인합니다. 1~32개 중복 없는 직접 대상 열만 허용하며 와일드카드, 별칭, 계산식, 중복, `OUTPUT INTO`, 잘못된 행 이미지는 거부합니다. 실제 Catalog와 트리거 부재 확인, 소스 변경·행 제한·승인 재사용 거부가 필수입니다. MCP 도구 추가 없이 기본 읽기 전용 네 개 선택 및 DML 비활성화를 유지합니다.

### M09: 제한된 IN/OR 소스 행 조건 (develop 전용)

실제 테이블이 검증된 **SQLite, PostgreSQL, MySQL 8.4 InnoDB, SQL Server 2022** 네이티브 `INSERT SELECT` 에서 `WHERE id IN (1,2)`, `WHERE id = 1 OR id = 2`, `WHERE (id = 1 OR id = 2) AND name IN ('Carol','Dave')` 를 허용합니다. 직접 `열 = NULL이 아닌 리터럴` 과 `열 IN (NULL이 아닌 리터럴, ...)` 을 합산하여 **비교 리터럴 최대 네 개**, 불리언 트리 노드 최대 일곱 개입니다. 괄호로 `AND`/`OR`를 조합할 수 있지만 각 원자 조건은 한정자가 없는 직접 열만 참조해야 합니다. 이전 M09 AND 전용 범위는 이 확장으로 대체되며 다른 CTE/JOIN의 OR 금지는 변하지 않습니다.

`OR 1=1`, `NOT`/`NOT IN`, IN 내부 NULL, IN 하위 쿼리, 계산식, 다섯 개 이상의 비교 값, 임의 OR, CTE, JOIN, 다른 Provider DML은 계속 거부됩니다. 소스/대상의 실제 Catalog 증명과 유한한 양수 행 수 제한은 그대로입니다. 미리 보기는 **선택한 소스 행 전체**를 승인하고 커밋은 기존 트랜잭션 잠금 아래 스키마 및 모든 소스 값을 다시 검증한 뒤 실제 영향 행 수를 대조합니다. PostgreSQL/SQLite RETURNING 및 SQL Server OUTPUT INSERTED 는 커밋 성공 후 실제 생성된 대상 값을 반환하며 MySQL에는 RETURNING이 없습니다. MCP 도구나 공개 API 추가 없이 기본 읽기 전용 네 개 선택과 DML 비활성화를 유지합니다.

### M09: 제한된 BETWEEN 네이티브 소스 필터 (develop 전용)

실제 소스가 증명된 **SQLite, PostgreSQL, MySQL 8.4 InnoDB, SQL Server 2022** 네이티브 `INSERT SELECT` 에서 `WHERE id BETWEEN 1 AND 2`, `WHERE id BETWEEN 1 AND 2 AND name IN ('Carol','Dave')`, `WHERE id BETWEEN 1 AND 1 OR id = 2` 를 허용합니다. `BETWEEN` 양쪽 경계는 NULL이 아닌 직접 리터럴이어야 하며 왼쪽은 한정자 없는 직접 열만 허용됩니다. BETWEEN 하나는 비교값 **두 개**를 소모하며 기존 `=` 및 `IN` 과 **합계 최대 네 개**입니다. `AND`／`OR` 를 포함한 Boolean AST 노드는 최대 일곱 개입니다. F# 형식화 파서와 기존 Host 실제 소스 증명을 재사용합니다.

`NOT BETWEEN`, NULL/계산식 경계, 열 대 열 범위, 상수만의 항상 참 조건, 비교값 다섯 개 이상, 하위 쿼리, JOIN, CTE 및 미검증 소스는 계속 거부합니다. Preview는 전체 소스 행을 승인하고 양수 유한 행 제한을 지키며 실제 Catalog 및 개별 권한을 검증합니다. Commit은 기존 트랜잭션 잠금을 유지한 채 전체 소스 값과 스키마를 재검증하고 단일 승인과 정확한 영향 행 수를 확인합니다. SQLite／PostgreSQL RETURNING과 SQL Server OUTPUT INSERTED는 커밋 성공 후 실제 대상 행만 반환하며 MySQL RETURNING은 미지원입니다. MCP 도구·드라이버·공개 API 추가 없이 기본 읽기 전용 네 도구 선택과 DML 비활성화를 유지합니다.
