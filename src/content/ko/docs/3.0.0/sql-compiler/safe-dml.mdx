## 승인 수락, 불확실한 결과 및 대상 증거

선택적 조건이 필요한 경우 `WHERE 1=1`처럼 항상 참임이 입증되는 `UPDATE`/`DELETE` 필터는 거부됩니다. 사람의 승인은 여전히 정확한 계획과 행 집합 증거에 결합됩니다.

사용자 지정 challenge store는 단일 및 배치 작업 모두에 대해 `TryPromoteAsync`를 원자적으로 구현해야 합니다. Redis와 영속 재개는 버전이 있는 봉투 형식을 사용합니다. 호환되지 않는 challenge에는 새 미리 보기와 동의가 필요합니다. [업그레이드 가이드](/ko/docs/reference/upgrade-guide)를 참조하세요.

`dml.commit_outcome_unknown`과 `dml.rollback_outcome_unknown`은 서로 다르며 둘 다 재시도할 수 없는 결과입니다. 승인 및 대상 증거를 보관하고 독립적으로 조사하세요. witness나 Redis 키가 없다고 롤백이 입증되는 것은 아닙니다. 불확실한 변경을 자동 재실행하지 마세요. 커밋이 확인된 뒤 감사 저장에 실패하더라도 변경 실패로 보고하면 안 됩니다.

`AddHsSqlAgentTargetExecutionFence()`는 선택적 기능입니다. 대상 준비와 별도로 이전 worker의 DML 권한 철회를 입증해야 합니다. 등록된 커밋마다 실제 연결에서 롤백 전용 준비 검증 트랜잭션 두 개를 추가 실행하고, 커밋 후 Admission과 Witness를 독립적으로 읽습니다. Oracle의 witness 고유성 충돌 진단만 READ COMMITTED이며 나머지 검증은 SERIALIZABLE입니다. 증거가 모순되면 불확실한 결과를 반환합니다. 전체 worker 등록이나 실행 중 worker의 자동 조정을 보장하지 않습니다.

DML은 Query보다 더 엄격한 실행 경로를 사용합니다. 실제 commit 시점에도 승인 내용이**동일한 Mutation Evidence**를 설명해야 하기 때문입니다.

## 하나의 Tool로 단일·다중 Statement 지원

`execute_dml_sql`은 하나 이상의 지원 `UPDATE`, `DELETE`, `INSERT ... VALUES`를 받을 수 있으며 여러 Statement는 세미콜론으로 구분합니다.

별도 batch DML Tool은 없습니다. 여러 Statement는 하나의 Batch로 Parse되고 한 번 승인된 뒤 원래 순서대로 실행되며 하나의 서버 소유 Transaction에서 원자적으로 commit됩니다.

Client가 보내는 `BEGIN`, `COMMIT`, `ROLLBACK` 같은 Transaction-control SQL은 허용하지 않습니다. Transaction 경계는 서버가 소유합니다.

## 승인에 바인딩되는 Evidence

`UPDATE` / `DELETE` 승인은 Preview에서 관찰한 정확한 Primary Key Row Set에 바인딩됩니다. Commit Transaction 안에서 각 Statement의 실제 변경 직전에 다시 검증합니다.

`INSERT ... VALUES`는 불변 Literal Payload와 정확한 Compile Command에 바인딩됩니다. `INSERT ... SELECT`는 source Row Set 승인 의미론이 정의될 때까지 지원하지 않습니다.

앞선 Statement가 뒤 Statement의 승인된 Row Set을 바꾸면 Batch 전체가 fail closed로 rollback됩니다.

## 승인 Provider

기본 공식 Provider는 MCP Elicitation입니다. Host는 공식 `HsSqlAgent.Approvals.Webhook` adapter를 사용하거나 `HsSqlAgent.Server`에서 `IDmlApprovalProvider`를 구현할 수 있습니다.

승인 Provider는 transport-neutral Evidence를 받을 뿐 SQL 실행 primitive를 받지 않습니다. Database Connection, Transaction, 검증된 Plan, commit 권한은 제공되지 않습니다.

## Durable Pending Approval

비동기 Workflow의 Provider는 `Pending`을 반환할 수 있습니다. Admin Store가 있으면 hs-sql-agent는 보호된 Resume Intent와 Approval Fingerprint를 저장합니다.

나중에 완료 Decision이 오면 현재 권한과 DB 설정을 다시 읽고 DML을 재 Parse / Preview하며 승인 Evidence를 비교한 뒤 새로운 단기 Execution Challenge를 만듭니다. 권한, DB 설정, Policy, Plan, Row Set, affected-row Evidence가 바뀌면 stale로 처리하고 commit하지 않습니다.

재개되는 것은**실행 Intent**이지 오래된 Database Session이 아닙니다.

## SQL Server: CTE 기반 수정 작업의 복합 INT 키

SQL Server UPDATE 또는 DELETE는 실제 원본 테이블에 **NULL을 허용하지 않는 두 개의 INT 열로 구성된 기본 키 또는 고유 인덱스**가 확인된 경우에만 명시적 허가를 받아 1~3단계의 비재귀 선형 CTE를 사용할 수 있습니다. 두 키 열은 물리적 인덱스 순서를 유지하며 각 CTE를 통해 변경 없이 전달되어야 합니다. 대상 테이블의 해당 INT 열마다 필수 `AND` 조건과 일반 `=` 비교가 있어야 합니다. 실행 전에는 실제 시스템 카탈로그 확인, 변경 대상 행 미리보기, 승인 내용 연결 및 동일 트랜잭션 내 메타데이터 재검증이 필요합니다.

키 누락·순서 변경, `OR`, 형 변환, NULL 허용 또는 계산 열, 필터링되거나 비활성화된 인덱스, 행 수를 늘리는 조인은 거부됩니다. 다른 데이터베이스의 실행 범위는 확대되지 않습니다.

### 단일 Derived Table의 UNIQUE 키 보존 증명 (G9/M06, develop 전용)

SQL Server의 제한된 CTE `UPDATE`/`DELETE`는 기존 1~3단 CTE 앞에 **실제 물리 테이블 하나만 읽는 비 LATERAL Derived Table 한 단계**를 허용합니다. 파생 SELECT와 후속 CTE는 `FROM (SELECT s.k1 AS x, s.k2 AS y FROM dbo.Source AS s) AS d`, `SELECT d.x AS a, d.y AS b`처럼 정렬된 전체 UNIQUE 키 열을 직접 다시 이름 붙일 수 있습니다. F# 카디널리티 증명과 Host의 실제 인덱스 검증은 각자 열 출처를 독립적으로 확인합니다. 실행 권한에는 실제 전체 UNIQUE 인덱스 및 원본/대상 SQL 타입·NULL 비교·정렬 규칙 일치가 필요하며, 가상 Catalog나 별칭은 권한이 아닙니다.

이는 **임의의 Derived Table 또는 다중 분기 CTE DAG를 허용하지 않습니다**. 파생 계층의 JOIN, WHERE, DISTINCT, GROUP/HAVING, 집계, ORDER, LIMIT/TOP/OFFSET, UNION, 중첩 파생 테이블/CTE, LATERAL, CAST/계산 키, 중복 별칭 및 누락된 고유 키는 계속 거부합니다. 미리 보기→독립 승인→커밋, 정확한 행 집합과 동일 커밋 트랜잭션의 잠금 기반 `IsCurrent`가 필요하며 인덱스 철회 후 승인도 차단됩니다. 실제 SQL Server 2022 테스트는 1~3단 CTE, 정수/소수/UUID/텍스트 복합 키 및 UPDATE/DELETE를 다룹니다. 나머지 5개 DB 및 기본 MCP/DML 권한은 변경하지 않습니다.


### 언어별 정렬 규칙과 UNIQUE 동등 비교의 정확한 증명 (G9/M05, develop 전용)

SQL Server의 제한된 CTE UPDATE/DELETE는 길이가 지정된 기본 제공 `VARCHAR(n)`/`NVARCHAR(n)`에 대해 **서로 구분되는 네 가지 비교 계약**을 검증합니다. 기존 `Latin1_General_100_BIN2`(이진 코드 포인트)에 더해 `Latin1_General_100_CI_AS`(대소문자 무시, 악센트 구분), `Latin1_General_100_CI_AI`(모두 무시), `Latin1_General_100_CS_AS`(모두 구분)를 지원합니다. 원본 UNIQUE 인덱스, 대상 비교 열 및 별도로 검증한 두 번째 JOIN 테이블은 **모든 키 위치에서 네이티브 SQL 타입, 길이, 실제 열 정렬 규칙이 동일**해야 합니다. 단순한 Text 스냅샷은 실행 권한이 아니며, F# 폐쇄형 모델이 실제 열과 인덱스를 검증합니다.

실제 SQL Server 2022 테스트는 대소문자나 악센트가 다른 값의 **UNIQUE 충돌 결과**와 일반 `=` 동등 비교가 일치하는지 확인합니다. 기존 1~3단계 CTE, 완전한 AND 키 비교, 문자열/UUID/숫자 복합 키, 미리 보기→독립 승인→커밋 및 트랜잭션 내 `IsCurrent`는 유지됩니다. NULL 허용 원본 UNIQUE에는 여전히 `ANSI_NULLS ON`이 필요합니다. ProofIdentity는 **v9**로 올라가 이전 승인은 무효화됩니다. 정렬 규칙 불일치, 명시적 `COLLATE` 덮어쓰기, VARCHAR/NVARCHAR 암시적 변환, 검증하지 않은 CS_AI/_SC/_UTF8, CHAR/MAX, 필터/비활성 인덱스 및 누락된 동등 조건은 계속 차단합니다. 다른 다섯 DB와 MCP 권한은 변하지 않습니다.


### NULL 허용 SQL Server UNIQUE 키와 일반 동등 비교의 증명 (G9/M05, develop 전용)

SQL Server 원본 키에 NULL 허용 열을 포함할 수 있는 경우는 **순서가 지정된 전체 1~2개 키 열을 보호하는, 실제 활성 상태이며 필터가 없는 물리 UNIQUE 인덱스가 존재할 때뿐**입니다. 제한된 CTE `UPDATE`/`DELETE`에는 대상과 연결되는 모든 `AND`/일반 `=` 조건과 실제 접속의 `ANSI_NULLS ON`(`@@OPTIONS`로 검사)이 필요합니다. 원본 키에 NULL이 하나라도 포함되면 일반 동등 비교의 결과는 UNKNOWN이므로 **대상 행과 일치하지 않습니다**. NULL 안전 비교나 임의의 NULL 허용 테이블 스캔을 승인하는 것이 아닙니다. 복합 대상 키는 계속 NOT NULL이어야 하며, 대상 동등 비교가 없는 `VerifyLive`는 NULL 허용 원본 키를 증명할 수 없습니다.

F#의 폐쇄형 NULL 비교 증명은 전체 UNIQUE 인덱스, 실제 기본 제공 물리 타입, 원본 NULL 허용 정보, 변경할 수 없는 메타데이터 요약 및 **v8 ProofIdentity**에 결합됩니다. 실제 Commit 연결과 트랜잭션에서 잠금을 유지하면서 `ANSI_NULLS ON`, 인덱스 및 스키마를 다시 확인합니다. `WHERE key IS NOT NULL`을 포함하는 필터 UNIQUE, 비활성/비고유 인덱스, `OR`, `COALESCE`, 계산된 키, CAST, NULL 안전 연산자, 가상 Catalog는 실행 증명이 아닙니다. 실제 SQL Server 2022 테스트는 NULL 허용 BIGINT/DECIMAL/UUID/BIN2 VARCHAR 복합 키, 1~3단 CTE, UPDATE/DELETE, Preview→독립 승인→Commit, NULL 비일치 및 인덱스 철회 시 차단을 확인합니다. 다른 5개 DB와 MCP 기본 권한은 변경하지 않습니다.


### BIN2 VARCHAR／NVARCHAR 물리 문자열 키의 정확한 검증 (G9/M04, develop 전용)

SQL Server CTE `UPDATE`/`DELETE`의 물리 고유성 증명은 길이가 제한된 기본 제공 `VARCHAR(n)`과 `NVARCHAR(n)`을 지원합니다. 단, **실제 데이터베이스 정렬 규칙이 정확히 `Latin1_General_100_BIN2`인 경우에만** 허용합니다. 원본 UNIQUE 인덱스, 대상 비교 열 및 별도로 검증된 두 번째 JOIN 테이블의 키는 **모든 키 순서에서 네이티브 SQL 타입, 최대 길이 및 정렬 규칙이 동일**해야 합니다. `NVARCHAR`는 `sys.columns.max_length`의 바이트 수를 검증한 뒤 문자 길이로 환산합니다. `MAX`, `CHAR`/`NCHAR`, 길이 불일치, Unicode와 비 Unicode 간 암시적 변환, 다른 BIN2 또는 대소문자를 구분하지 않는 정렬 규칙, 사용자 정의 별칭, NULL 허용 원본 키는 거부됩니다.

Host는 실제 문자열을 기존 `SqlSchemaValueKind.Text`로 분류하지만 **스냅샷 분류 자체로 실행 권한을 부여하지 않습니다**. F# 폐쇄형 키 모델은 실제 열 길이와 정렬 규칙, 내장 타입, 전체 고유 인덱스 및 제한된 CTE/JOIN의 필수 일반 동등 비교를 독립적으로 검증합니다. Preview→독립 승인→Commit 시 실제 커밋 트랜잭션에서 잠금을 유지한 `IsCurrent` 재검증도 그대로 적용됩니다. ProofIdentity는 v7으로 올라가 이전 승인은 무효화됩니다. 실제 SQL Server 2022 테스트는 문자열과 UUID/정수/소수 복합 키, UPDATE/DELETE, 1~3단 CTE, 자체/별도 테이블 JOIN, 인덱스 철회, 길이 및 정렬 규칙 불일치 거부를 검증합니다. 나머지 5개 데이터베이스와 MCP 도구 및 기본 권한은 그대로입니다.


### CTE에 키가 아닌 열을 함께 투영하기（G8／M03）

1~3단계 CTE에서는 필수 1~2개 INT 키 열 외에 **원본 행에서 직접 가져온 다른 열**도 함께 선택할 수 있습니다(단계당 최대 32개 열). 예를 들어 `SELECT k1 AS a, payload AS extra, k2 AS b` 다음에 `SELECT a, extra, b`를 사용할 수 있습니다. 키는 모든 단계에서 한 번씩만 나타나고 실제 고유 인덱스의 상대 순서를 유지해야 하며, 최종 조건에서도 필수 `AND` 및 일반 `=` 비교가 필요합니다. 키 중복·변환·계산, 모호한 별칭, 다중 원본 및 행을 늘리는 JOIN은 여전히 거부됩니다. 실제 인덱스 검증, 미리 보기, 승인, 커밋 트랜잭션 재검증은 그대로이며 일반 JOIN이나 다른 데이터베이스의 실행 권한이 추가되는 것은 아닙니다.

### 단일 행 파생 JOIN의 안전성 증명（G8／M07, 제한된 범위）

SQL Server의 각 CTE 단계에서는 **행 수가 늘지 않는다고 증명된 JOIN을 최대 하나** 사용할 수 있습니다. 조인 대상은 `SELECT 1 AS marker`처럼 독립적인 파생 쿼리여야 하며 `FROM`, `WHERE`, `UNION`, 그룹화나 추가 행을 포함할 수 없습니다.`CROSS JOIN (SELECT 1 AS marker) AS one`은 원본 행 수를 유지하고, 상수 동등 비교 `ON 1 = 1`을 사용하는 `INNER JOIN`과 `LEFT JOIN`도 행 수를 늘리지 않습니다. 실제 INT 고유 키, 직접 키 투영, 미리 보기, 승인 및 커밋 트랜잭션의 실제 증명은 계속 필수입니다. **위의 단일 행·셀프 JOIN 증명만으로는 다른 물리 테이블과의 JOIN을 허용하지 않습니다. 아래에서 별도의 두 고유 인덱스 증명으로 제한적으로 허용합니다, APPLY, 상관 하위 쿼리, 여러 행을 반환하는 파생 소스나 임의 JOIN은 허용하지 않습니다.**

추가로 **동일한 물리 원본 테이블을 서로 다른 별칭으로 연결하는 INNER／LEFT 셀프 JOIN**을 제한적으로 허용합니다. 이 경우 ON 조건은 실제 DB에서 검증된 INT 고유 키의 **모든 구성 열**을 필수 AND와 일반 동등 비교로 연결해야 합니다. 그러면 두 번째 별칭은 원본 행마다 최대 한 행만 일치합니다. 일부 키 누락, OR만 있는 조건, 계산·형 변환 키나 다른 테이블과의 JOIN은 거부됩니다.

### 서로 다른 물리 테이블 JOIN의 이중 고유 키 증명（M07）

SQL Server CTE에서는 다른 물리 테이블에 대해 하나의 **INNER JOIN** 또는 **LEFT JOIN**을 사용할 수 있습니다. 두 원본 테이블 모두 실제 데이터베이스에서 각각 검증된, NULL을 허용하지 않는 1~2개 열의 `INT`／`BIGINT` 고유 키가 필요하며 인덱스는 활성화되고 필터가 없어야 합니다. `ON` 조건은 필수 `AND`와 일반 `=`로 모든 키 열을 연결하고 각 위치의 실제 자료형도 정확히 일치해야 합니다. 가상 카탈로그, 암시적 형 변환, 일부 키만 비교하거나 필터링된 인덱스는 증거가 되지 않습니다. 두 인덱스 식별 정보는 실행 계획·승인에 함께 결합되고 실제 커밋 트랜잭션에서 다시 확인됩니다. 미리 보기 후 어느 증명이든 무효화되면 커밋을 거부합니다. 세 번째 물리 원본, 다대다 JOIN, `RIGHT`／`FULL JOIN`, 다른 DB 방언으로의 변환이나 임의의 JOIN은 허용되지 않습니다.

### 전체 키 상관 EXISTS／NOT EXISTS 필터（M07, 제한 범위）

SQL Server의 CTE 기반 `UPDATE`／`DELETE`는 첫 번째 CTE의 `WHERE`에서 **`EXISTS`(세미 조인) 또는 `NOT EXISTS`(안티 조인)**을 사용할 수 있습니다. 단, 하위 쿼리는 실제 고유 키가 검증된 **동일한 원본 테이블을 다른 별칭으로** 읽어야 합니다. 리터럴만 선택하며 추가 JOIN, 그룹화, 정렬 또는 집합 연산은 금지됩니다. 1~2개 `INT`／`BIGINT` 고유 키 전체를 필수 `AND`와 일반 `=` 비교로 연결해야 하며, 내부 열과 상수의 비교를 추가해 결과를 줄일 수 있습니다. 이는 행을 필터링할 뿐 늘리지 않으며 실제 인덱스 증명, 미리 보기, 승인 바인딩 및 커밋 트랜잭션 재검증이 계속 필요합니다. **임의의 중첩 쿼리, 미검증 다른 테이블, 일반적인 EXISTS／안티 조인 실행 권한은 허용하지 않습니다.**

### TINYINT 및 SMALLINT 물리 키의 정확한 형식 검증 (G9/M04, develop 전용)

SQL Server의 CTE 기반 `UPDATE`/`DELETE` 실제 고유 키 검증은 기존 `INT`, `BIGINT` 외에도 기본 제공 `TINYINT`(부호 없는 8비트)와 `SMALLINT`(부호 있는 16비트)를 지원합니다. 1~2열 물리 고유 키에서 원본, 대상, 별도로 검증한 JOIN 테이블의 대응 열은 **인덱스의 각 키 위치에서 실제 SQL Server 자료형이 정확히 같아야** 합니다. 정수형 암시적 변환, 사용자 정의 별칭 형식, 가상 카탈로그는 실제 검증을 대신할 수 없습니다. 기존의 제한된 CTE 키 전달, 행을 늘리지 않는 JOIN 증명, 대상 행 미리 보기, 별도 승인, 변경 불가능한 계획 지문과 동일 트랜잭션에서의 인덱스 재검증은 계속 필수입니다. SQL Server 2022 실제 테스트는 수정·삭제, 혼합 키 형식, 인덱스 철회를 검증합니다. DECIMAL, UUID, NULL 허용 고유 키, 임의 JOIN 또는 다른 데이터베이스의 실행 권한은 추가되지 않습니다.


### UNIQUEIDENTIFIER 물리 키의 정확한 증명 (G9/M04, develop 전용)

SQL Server의 CTE `UPDATE`/`DELETE` 물리 고유성 증명은 이제 **기본 제공 128비트 `UNIQUEIDENTIFIER` 키**도 지원합니다. `Uuid`는 독립적인 스키마 값 종류이며 **숫자, 문자열 또는 이진 키로 위장하지 않습니다**. Host는 실제 `sys.tables`, `sys.columns`, `sys.types` 메타데이터를 읽어 원본, 대상, 별도로 검증된 두 번째 JOIN 테이블의 키 유형을 확인합니다. F#의 폐쇄형 키 모델은 전체 UNIQUE 인덱스 열과 스냅샷에 선언된 유형이 실제 물리 유형과 일치하는지 독립적으로 검증합니다. `UNIQUEIDENTIFIER`를 `INT`, `DECIMAL`, `VARCHAR`, `BINARY(16)`와 암시적으로 변환하여 실행 권한을 증명할 수 없습니다.

1~2개 구성요소의 키에서 UUID와 정확히 일치하는 정수/소수 키를 조합할 수 있습니다. 기존의 1~3단계 제한된 CTE, 행을 늘리지 않는 JOIN, 변경 미리 보기, 독립 승인, 커밋과 동일한 트랜잭션에서의 `IsCurrent` 재검증은 계속 필요합니다. ProofIdentity는 v6으로 갱신되어 이전 승인을 재사용할 수 없습니다. 실제 SQL Server 2022 테스트는 UUID UPDATE/DELETE, 기본/고유 인덱스, 자동 증명, 다른 물리 테이블 JOIN, 미리 보기 후 인덱스 철회 및 유형 불일치 거부를 검증합니다. MCP 도구, 기본 DML 선택, 임의 JOIN 권한이나 다른 5개 데이터베이스의 권한은 증가하지 않습니다.

### DECIMAL／NUMERIC 물리 키의 정확한 증명 (G9/M04, develop 전용)

SQL Server의 CTE 기반 `UPDATE`/`DELETE` 물리 고유 키 증명은 기본 제공 `DECIMAL(p,s)` 및 `NUMERIC(p,s)`도 지원합니다(`1 ≤ p ≤ 38`, `0 ≤ s ≤ p`). 두 이름은 SQL Server에서 동의어이지만 원본, 대상, 별도로 검증된 JOIN 테이블의 대응 키는 **각 인덱스 위치에서 정밀도와 소수 자릿수가 정확히 일치**해야 합니다. `DECIMAL(12,2)`를 `DECIMAL(13,2)`, `DECIMAL(12,3)` 또는 정수 키와 비교하는 암시적 형 변환은 고유성 증명이 아닙니다.

Host는 실제 `sys.columns` 및 `sys.types` 메타데이터를 읽고 원래 UNIQUE 인덱스의 **모든 키 열**을 확인합니다. 지원하지 않는 사용자 정의 별칭 형식이 포함되어도 `UNIQUE(a,b)`를 `UNIQUE(a)`로 잘못 판정하지 않습니다. F#의 폐쇄형 자료형은 정확한 정밀도와 소수 자릿수를 유지합니다. 기존의 1~3단계 제한된 CTE, 행 수가 증가하지 않는 JOIN, 대상 행 미리 보기, 독립 승인, 버전별 증명 식별 정보 및 동일 커밋 트랜잭션의 재검증은 그대로 유지됩니다. SQL Server 2022 실제 테스트는 소수값, 정수/소수 복합 키, 서로 다른 물리 테이블 JOIN, 인덱스 철회 및 정밀도 불일치 거부를 확인합니다. UUID/문자열 키, NULL 허용 고유 키, 임의 JOIN 및 다른 다섯 데이터베이스는 대상이 아닙니다.


## Fail-closed 규칙

승인 거절, 만료, stale, Fingerprint 불일치, 권한 철회, 현재 Policy 위반, 승인 Row Set 재현 실패 시 DML을 commit하지 않습니다.
