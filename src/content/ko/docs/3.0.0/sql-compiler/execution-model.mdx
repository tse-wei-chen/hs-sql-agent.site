## 제한된 컴파일 및 스키마 증거

입력이 4,194,304 UTF-16 단위, End를 제외한 131,072개 어휘 토큰, 8,192단계 그룹 중첩 또는 AST 노드 65,536개를 초과하면 거부됩니다. 반복형 AST 탐색과 크기 제한 렌더링은 여섯 공급자에서 매개변수 순서 및 안전성을 입증하지 못하면 거부하는 원칙을 유지합니다. 임의 깊이 SQL 지원을 보장하지 않습니다.

자원 한도는 단계당 8,000,000 작업 단위, 컴파일당 32,000,000 작업 단위, 단계당 30초, 컴파일당 90초, 단계당 누적 관리 메모리 할당 536,870,912바이트입니다. 이는 컴파일 예산이며 DB 쿼리 시간 제한이나 프로세스 메모리 한도가 아닙니다. 초과 시 형식화된 자원 진단을 반환합니다.

선택적으로 활성화하는 불변 스키마 스냅샷은 테이블·열 이름과 입증 가능한 유형 계열을 해석하며 순서가 있는 CTE/파생 투영도 포함합니다. 다이제스트는 계획 지문에 결합됩니다. 완전한 DB 유형 검사기는 아닙니다. 스키마 증거가 있는 DML에는 실제 최신 상태 검증이 필요하며, 증거가 누락되거나 스키마가 바뀌면 거부됩니다. 기본 런타임은 스냅샷을 수집하지 않습니다. `AddHsSqlAgentNativeDmlSchemaFreshness()`로 선택적 네이티브 지원을 활성화합니다.

hs-sql-agent는 AI가 생성한 SQL을 신뢰된 명령으로 바로 실행하지 않습니다. 실행 전에 파싱, 검증, 지원 기능 확인, 접근 정책 적용, 대상 데이터베이스용 컴파일을 거칩니다.

## 쿼리 실행 경로

쿼리는 대략 다음 순서로 처리됩니다.

1. MCP 키를 인증하고 해당 키에 설정된 데이터베이스, 테이블, 도구, 실행 한도를 적용합니다.
2. 지원하는 SQL을 구조화된 정의 / AST로 파싱합니다.
3. 문장과 입력 SQL의 의미가 지원 범위 안에 있는지 검증합니다.
4. 같은 의미를 유지하는 데 필요한 기능을 대상 데이터베이스에서 안전하게 표현할 수 있는지 확인합니다.
5. 설정된 데이터베이스용 SQL을 컴파일하고 생성합니다.
6. 설정된 실행 한도 안에서 SQL을 실행합니다.

SQL 컴파일러에는 입력 SQL의 의미를 검증하는 단계와 대상 데이터베이스의 지원 기능을 확인하는 단계가 명확히 구분되어 있습니다. 지원하지 않는 구문이나 같은 의미를 안전하게 보존할 수 있다고 확인되지 않은 기능은 겉보기만 비슷한 구문으로 바꾸지 않고 거부합니다.

## 왜 페일 클로즈 방식인가요?

여러 데이터베이스에서 SQL을 다루면 겉보기에는 비슷해도 NULL 처리, 형식 규칙, 연산자 의미, 페이지 처리, 식별자, 함수, DML 동작이 다른 경우가 많습니다.

AI가 SQL을 제출하는 실행 환경에서 "가능한 범위에서 알아서 바꾸는" 방식은 위험합니다. 문법상 올바른 SQL이더라도 의미가 달라질 수 있기 때문입니다. hs-sql-agent는 이런 암묵적 의미 변경보다 명확한 거부를 선택합니다.

## 데이터베이스별 SQL 출력

MCP 공개 인터페이스는 공통이지만 최종 SQL은 데이터베이스별로 생성됩니다. 현재 지원하는 데이터베이스는 다음과 같습니다.

- PostgreSQL
- MySQL
- SQL Server
- Oracle
- SQLite
- Firebird

지원 범위는 의도적으로 제한되어 있습니다. 데이터베이스가 지원 목록에 있다고 해서 해당 제품의 모든 SQL 구문을 허용하는 것은 아닙니다. 개별 기능은 그 의미를 내부 표현으로 나타내고 검증할 수 있을 때만 추가됩니다.

## GROUPS 윈도 프레임

PostgreSQL 11 이상과 SQLite 3.28 이상에서는 `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW)` 같은 윈도 프레임을 컴파일할 수 있습니다. `GROUPS`는 정렬 키가 같은 행들을 하나의 묶음으로 계산하며, 개별 행을 세는 `ROWS`나 값 범위를 기준으로 하는 `RANGE`와 의미가 다릅니다. 윈도 내부에 명시적인 `ORDER BY`가 있어야 합니다. 잘못된 프레임 경계와 지원 버전보다 오래된 것으로 명시된 데이터베이스는 거부하며, 다른 프레임 단위로 몰래 바꾸지 않습니다. MySQL, SQL Server, Oracle, Firebird에서는 이 기능이 허용되지 않습니다. 호스트는 실행 전에 실제 데이터베이스 버전을 확인해야 합니다.

## EXCLUDE: 윈도 프레임의 행 제외

PostgreSQL 11 이상과 SQLite 3.28 이상에서는 `ROWS`, `RANGE`, `GROUPS` 프레임 뒤에 네 가지 제외 조건을 지정할 수 있습니다. `EXCLUDE CURRENT ROW`는 현재 행만 제외하고, `EXCLUDE GROUP`은 현재 행 및 정렬 키가 같은 모든 행을 제외합니다. `EXCLUDE TIES`는 현재 행을 유지하면서 정렬 키가 같은 다른 행을 제외하며, `EXCLUDE NO OTHERS`는 제외하지 않습니다. 예: `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW EXCLUDE TIES)`. `ROWS` 프레임에서도 제외 조건은 정렬 키가 같은 행을 구분합니다. F# 컴파일러와 `WindowFrameDefinition.Exclusion`은 이 의미를 그대로 유지합니다. 명시된 구버전 및 나머지 네 데이터베이스 제공자는 거부합니다. 실행 전에 Host에서 실제 데이터베이스 버전을 확인해야 합니다.

## SQL Server RANGE 프레임의 숫자 오프셋 제한

SQL Server의 T-SQL 문법에서는 `RANGE` 윈도 프레임에 숫자가 있는 `PRECEDING` 또는 `FOLLOWING` 오프셋을 지정할 수 없습니다. 예를 들어 대상 데이터베이스가 PostgreSQL이나 SQLite여도 `RANGE BETWEEN 1 PRECEDING AND CURRENT ROW`는 **SQL Server 원본 문법에 맞지 않으므로** 거부됩니다. 유효한 `ROWS` 오프셋과 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`는 계속 지원합니다. PostgreSQL 및 SQLite의 고유한 숫자 `RANGE` 의미는 변경되지 않습니다. 컴파일러는 원본 방언의 유효성과 대상의 지원 기능을 따로 검증하며, 대상이 지원하는 구문을 원본 구문의 유효성에 대한 증거로 사용하지 않습니다.

## MySQL 및 SQL Server 대상으로 제한된 조건부 COUNT

PostgreSQL을 원본 방언으로 사용하는 `SELECT COUNT(*) FILTER (WHERE status = 1) FROM orders`는 MySQL 또는 SQL Server용 조건부 집계로 안전하게 컴파일할 수 있습니다. MySQL은 `COUNT(CASE WHEN ... THEN 1 END)`를, SQL Server는 64비트 집계 범위를 유지하는 `COUNT_BIG(CASE WHEN ... THEN 1 END)`를 사용합니다. 직접 지정한 열의 `COUNT(열)`도 지원하며 NULL 제외, 일치하는 행이 없을 때 0 반환, 윈도 프레임별 집계 의미를 유지합니다.

**FILTER 전반을 허용하는 기능은 아닙니다.** 한정 이름이 없는 `COUNT(*)`, 로컬 열 COUNT 및 윈도 집계가 아닌 `COUNT(DISTINCT 직접 열)`에 한해 검증 가능한 단순 열·상수 조건을 허용합니다. `SUM`, 계산식 인수, 하위 쿼리, 비결정적 함수, 외부 범위 참조는 계속 거부합니다. MySQL/SQL Server 원본 SQL의 `FILTER` 구문은 여전히 유효하지 않습니다. 이 변환은 PostgreSQL처럼 원본 구문이 적법한 경우에만 적용됩니다. SqlCore는 SQL을 실행하거나 데이터베이스 권한을 부여하지 않습니다.

## 조건부 DISTINCT COUNT: 중복 없이 값 세기

PostgreSQL 원본 구문의 `COUNT(DISTINCT amount) FILTER (WHERE status = 1)`를 MySQL의 `COUNT(DISTINCT CASE WHEN status = 1 THEN amount END)` 또는 SQL Server의 `COUNT_BIG(DISTINCT CASE WHEN status = 1 THEN amount END)`로 변환할 수 있습니다. 같은 값은 한 번만 세고, NULL 및 조건이 거짓이거나 알려지지 않은 행은 제외합니다. 일치하는 값이 없으면 0을 반환합니다. PostgreSQL 16, MySQL 8.4, SQL Server 2022 실제 데이터베이스에서 그룹별 및 전체 정수 집계를 검증했습니다.

DISTINCT의 인수는 직접 참조하는 로컬 열 하나여야 하며 조건은 제한된 범위에서 검증할 수 있어야 합니다. 계산식, 복수 DISTINCT 인수, 하위 쿼리, 비결정적 함수 및 외부 범위 참조는 거부합니다. **`OVER (...)`를 사용하는 DISTINCT 윈도 집계는 지원하지 않습니다.** MySQL과 SQL Server 모두 해당 구문을 지원하지 않습니다. MySQL/SQL Server 원본의 `FILTER` 구문도 계속 유효하지 않습니다. 정수 검증으로 문자열 정렬 규칙이나 형 변환의 완전한 호환성을 주장하지 않습니다. SQL 실행이나 데이터베이스 권한 부여는 포함하지 않습니다.

## SQL Server／Oracle LAG·LEAD: NULL 무시

SQL Server 2022 CU4(16.0.4035.4) 이상과 Oracle 12.1 이상에서 `LAG(amount) IGNORE NULLS OVER (PARTITION BY grp ORDER BY id)` 및 대응하는 `LEAD` 구문을 유지할 수 있습니다. `IGNORE NULLS`는 앞뒤 값을 찾을 때 NULL을 건너뛰고, 명시적 `RESPECT NULLS`는 NULL을 포함하는 원래 동작을 유지합니다. 수정자는 **함수 호출과 OVER 사이**에 놓이며 윈도 프레임 안에 넣지 않습니다. F#은 이를 형식이 지정된 윈도 NULL 처리 값으로 저장하여 컴파일 중 임의로 제거하거나 바꾸지 않습니다.

SQL Server 2022 RTM에서도 명시적 `RESPECT NULLS`는 지원됩니다. 그러나 LAG／LEAD `IGNORE NULLS`의 결과 오류가 CU4에서 수정되었으므로 해당 기능에는 CU4 이상 빌드 증명이 필요합니다. `16.0`만 선언한 프로필로는 이 수정 사항을 증명할 수 없습니다.

원본과 대상 모두 명시적인 `ServerVersion` 기능 설정이 있어야 하고, 실제 실행 시에는 Host가 데이터베이스 버전을 확인해야 합니다. PostgreSQL, MySQL, SQLite, Firebird는 이 수정자를 허용하지 않으며 지원하지 않는 윈도 함수, 중복·잘못된 수정자, `OVER` 누락도 거부합니다. 수정자 없는 기존 `LAG/LEAD`는 변경되지 않습니다. `WindowSpec.NullTreatment`와 `WindowDefinition.NullTreatment`는 같은 검증 경로를 사용하며, 실제 SQL Server／Oracle 결과 행과 비교해 NULL 건너뛰기를 확인합니다. 컴파일러는 SQL 실행이나 DB 권한을 부여하지 않습니다.
