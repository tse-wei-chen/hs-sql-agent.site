ドキュメントのバージョン管理は **2.0.1** から始まります。サイト上には意図的に 2.0.1 より前のアップグレードマトリクスを置いていません。このページでは 2.0.1 基準から離れる際の運用チェックリストを定義します。移行先固有の破壊的変更は、その後続バージョンのドキュメントを正とします。

<Callout type="warning" title="将来リリースの移行要件をこのページから推測しないでください">
アップグレード前に、移行先リリースの release note とバージョン付きドキュメントを確認してください。後続リリースで storage schema、設定、SQL capability、API contract が変更されている場合は、そのリリースの情報が基準です。
</Callout>

  <Step title="連携を棚卸し" description="MCP client、Custom Tool、OIDC、SMTP、Webhook/SIEM、Prometheus/OTLP、Redis/shared state、reverse proxy、外部 Admin API consumer を一覧化します。" />
</Steps>

## 安易に再生成してはいけない状態

### HMAC / JWT secret

`HMAC_KEY` は MCP キー検証を保護し、`JWT_KEY` は Admin 認証 token に署名します。secret rotation は、新しい image をデプロイした副作用ではなく、意図したセキュリティ移行として扱ってください。

### Data-protection key ring

保護された ID／MFA 状態で ASP.NET Core data protection を利用している場合は、`DATA_PROTECTION_KEY_PATH` を永続ストレージ上に維持します。key ring を置き換えると、以前に保護された値を読み取れなくなる場合があります。

### Admin database

Admin database はコントロールプレーンそのものを保持します。ID／ロール、データベース登録、MCP key record、policy、semantic metadata、Custom Tool の定義／revision、audit data、その他運用状態が含まれます。永続化方式を変更する可能性のあるアップグレード前には、SQLite または PostgreSQL に適した手順でバックアップしてください。

## 設定差分チェックリスト

空の新しい `.env` から始めないでください。次のカテゴリを明示的に比較します。

- application host と public MCP endpoint
- Admin database provider / connection
- HMAC/JWT と ID 設定
- bootstrap 設定
- OIDC/MFA/data protection
- audit retention と outbound delivery
- rate limiting と security-policy sync
- cache / SQL concurrency / その他 Redis-backed coordination
- Prometheus と OTLP

2.0.1 基準については [設定リファレンス](/ja/docs/operations/configuration) を参照してください。

## Custom Tools とセマンティックメタデータ

公開済み Custom Tool ごとに、移行先 compiler/policy でも引き続き検証を通過し、意図した database/key exposure が維持されているか確認します。セマンティックメタデータでは、table/column description、relationship、metric がスキーマ探索に期待どおり表示されることを確認してください。

## API 利用者

2.0.1 の Admin controller は versioned `/v1` contract 配下にありません。外部自動化が Admin HTTP route を直接呼び出している場合、route/request/response compatibility を明示的なアップグレードテスト項目にしてください。

[Admin HTTP API リファレンス](/ja/docs/reference/api-reference) も参照してください。

## ロールバック計画

<Callout type="danger" title="Binary のロールバックは、データのロールバックとは限りません">
新しい release が永続 control-plane schema や state を変更した場合、変更済み database に古い binary をそのまま起動するのは安全とは限りません。アップグレード前の database backup を保持し、移行先 release の rollback guidance に従ってください。
</Callout>

安全な rollout では、新しいバージョンが機能面・運用面の smoke test を通過するまで、旧 deployment artifact/configuration、アップグレード前 Admin database backup、保護 key material を利用可能な状態で保持します。
