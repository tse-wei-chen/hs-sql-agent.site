## コンパイル制限とスキーマ証拠

4,194,304 UTF-16 単位、131,072 個の End 以外の字句トークン、8,192 段のグループ化、65,536 AST ノードのいずれかを超える入力は拒否されます。反復型 AST 走査と上限付きレンダリングは、6 プロバイダーでパラメーター順序と安全性を証明できない場合の拒否を維持します。任意の SQL 深度を保証するものではありません。

上限はステージごとに 8,000,000 作業単位、コンパイル全体で 32,000,000 作業単位、ステージごとに 30 秒、全体で 90 秒、ステージごとの累積マネージド割り当て 536,870,912 バイトです。DB クエリのタイムアウトやプロセスメモリ上限ではなく、コンパイル予算です。超過は型付きリソース診断で報告されます。

任意で有効にする不変スキーマスナップショットは、テーブル・列名、証明可能な型ファミリー、順序付き CTE／派生投影を解決し、ダイジェストを計画フィンガープリントに結び付けます。完全な DB 型チェッカーではありません。スキーマ証拠付き DML にはライブの鮮度検証が必要で、証拠の欠落・変更時は拒否されます。既定ではスナップショットを取得しません。`AddHsSqlAgentNativeDmlSchemaFreshness()` でネイティブサポートを明示的に有効化できます。

hs-sql-agent は、AI が生成した SQL をそのまま信頼済みコマンドとして扱いません。実行前に解析、検証、対応能力の確認、アクセスポリシーの適用、接続先データベース向けのコンパイルを行います。

## クエリの実行経路

クエリは大きく次の順序で処理されます。

1. MCP キーを認証し、そのキーに設定されたデータベース、テーブル、ツール、実行上限を適用する。
2. 対応している SQL を構造化された定義 / AST へ解析する。
3. 文と入力側 SQL の意味がサポート範囲内にあるか検証する。
4. 同じ意味を保つために必要な機能を、接続先データベースが安全に表現できるか確認する。
5. 設定されたデータベース向けに SQL をコンパイルして出力する。
6. 設定された実行上限の範囲内で SQL を実行する。

SQL コンパイラには、入力側の意味を検証する段階と、出力先の対応能力を確認する段階が明示的に分かれています。対応していない構文や、安全に同じ意味を表現できると確認できない機能は、見た目だけ似た別の構文へ置き換えずに拒否します。

## なぜフェイルクローズなのか

複数のデータベースで SQL を扱うと、見た目が似ていても NULL の扱い、型規則、演算子の意味、ページング、識別子、関数、DML の動作が異なる構文が数多くあります。

AI から SQL を受け付ける実行基盤で「可能な範囲で書き換える」方式を採ると、構文としては正しくても意味が変わる危険があります。hs-sql-agent はそのため、暗黙の意味変更よりも明示的な拒否を選びます。

## データベースごとの SQL 出力

MCP の公開インターフェースは共通ですが、最終的に生成される SQL はデータベースごとに異なります。現在対応しているデータベースは次のとおりです。

- PostgreSQL
- MySQL
- SQL Server
- Oracle
- SQLite
- Firebird

対応範囲は意図的に限定されています。データベース自体が対応一覧にあるからといって、その製品が提供するすべての SQL 構文を受け付けるわけではありません。個々の機能は、その意味を内部表現として保持し、検証できるようになった段階で追加されます。

## GROUPS によるウィンドウフレーム

PostgreSQL 11 以降と SQLite 3.28 以降では、`SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW)` のようなウィンドウフレームをコンパイルできます。`GROUPS` は並び替えキーが等しい行の集まりを単位として数えます。個々の行を数える `ROWS` や値の範囲を扱う `RANGE` とは意味が異なります。ウィンドウ内の明示的な `ORDER BY` が必須です。不正なフレーム境界や、対応開始バージョンより古いと明示されたデータベースは拒否し、別のフレーム単位には暗黙変換しません。MySQL、SQL Server、Oracle、Firebird ではこの機能を許可しません。実行前にホスト側で実際のデータベースのバージョンを検証する必要があります。

## EXCLUDE：ウィンドウフレームからの行の除外

PostgreSQL 11 以降と SQLite 3.28 以降では、`ROWS`、`RANGE`、`GROUPS` のフレームに四種類の除外指定を追加できます。`EXCLUDE CURRENT ROW` は現在行のみ、`EXCLUDE GROUP` は現在行と同じ並び替えキーの行すべてを除外します。`EXCLUDE TIES` は現在行を残して同じキーの他の行を除外し、`EXCLUDE NO OTHERS` は何も除外しません。例：`SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW EXCLUDE TIES)`。`ROWS` を指定した場合も、除外時には同じ並び替えキーの行を考慮します。F# コンパイラーと `WindowFrameDefinition.Exclusion` は意味を変えずに扱います。明示された旧バージョンや他の四種類のデータベースは拒否されます。実行前には Host が実際のデータベースバージョンを確認する必要があります。

## SQL Server の RANGE フレームにおける数値オフセット制限

SQL Server の T-SQL 構文では、`RANGE` ウィンドウフレームに数値付きの `PRECEDING` または `FOLLOWING` を指定できません。たとえば `RANGE BETWEEN 1 PRECEDING AND CURRENT ROW` は、出力先を PostgreSQL や SQLite に指定していても、**SQL Server の入力構文として無効**なため拒否されます。有効な `ROWS` のオフセットと `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` は引き続き利用できます。PostgreSQL と SQLite 固有の数値 `RANGE` の意味は維持されます。コンパイラーは入力方言の適合性と出力先の対応能力を別々に検証し、出力先で使える構文を入力構文の有効性の根拠にはしません。

## MySQL／SQL Server 向けの限定的な条件付き COUNT

PostgreSQL を入力方言とする `SELECT COUNT(*) FILTER (WHERE status = 1) FROM orders` は、MySQL または SQL Server 向けに条件付き集計へ安全に変換できます。MySQL は `COUNT(CASE WHEN ... THEN 1 END)`、SQL Server は 64 ビットの件数を保つ `COUNT_BIG(CASE WHEN ... THEN 1 END)` を使用します。直接指定した列の `COUNT(列)` も対象で、NULL の除外、該当行がない場合のゼロ、ウィンドウフレーム単位の集計結果を維持します。

**FILTER 全般を解禁するものではありません。** 修飾されていない `COUNT(*)`、ローカル列の COUNT、およびウィンドウ集計ではない `COUNT(DISTINCT 直接列)` と、検証可能な単純な列・定数条件に限定します。`SUM`、計算式の引数、サブクエリ、非決定的関数、外部スコープの参照は拒否します。MySQL／SQL Server の入力 SQL に書かれた `FILTER` は依然として無効な構文です。この変換は PostgreSQL など有効な入力方言にのみ適用します。SqlCore 自体は SQL を実行せず、DB 権限も付与しません。

## 条件付き DISTINCT COUNT：重複を除いた値の集計

PostgreSQL を入力方言とする `COUNT(DISTINCT amount) FILTER (WHERE status = 1)` を、MySQL の `COUNT(DISTINCT CASE WHEN status = 1 THEN amount END)`、または SQL Server の `COUNT_BIG(DISTINCT CASE WHEN status = 1 THEN amount END)` に変換できます。同じ値は一度だけ数え、NULL や条件が偽・不明の行は数えません。該当値がない場合はゼロです。PostgreSQL 16、MySQL 8.4、SQL Server 2022 の実際のデータベースで、グループ別・全体の整数集計を検証しています。

DISTINCT の引数は直接参照するローカル列一つに限り、条件には有界な検証が必要です。計算式、複数の DISTINCT 引数、サブクエリ、非決定的関数、外側のスコープ参照は拒否します。**`OVER (...)` を伴う DISTINCT ウィンドウ集計は非対応**です。MySQL／SQL Server はこの構文をサポートしていません。入力方言が MySQL／SQL Server の `FILTER` も引き続き無効です。整数の検証結果を、文字列の照合順序や型変換の完全な互換性に拡大解釈することはできません。SQL の実行や DB 権限の付与は行いません。

## SQL Server／Oracle の LAG・LEAD：NULL を無視する処理

SQL Server 2022 CU4（16.0.4035.4）以降および Oracle 12.1 以降で、`LAG(amount) IGNORE NULLS OVER (PARTITION BY grp ORDER BY id)` と対応する `LEAD` の構文を保持できます。`IGNORE NULLS` は直前・直後の値を探す際に NULL を飛ばし、明示的な `RESPECT NULLS` は NULL を含む標準の動作を維持します。修飾子は**関数呼び出しと OVER の間**に置き、ウィンドウフレーム内には置きません。F# は NULL の扱いを型付きのウィンドウ情報として保持し、勝手に削除・変更しません。

SQL Server 2022 RTM でも明示的な `RESPECT NULLS` は使用できます。一方、LAG／LEAD の `IGNORE NULLS` には Microsoft が修正した結果の不具合があるため CU4 以降の証明が必要です。`16.0` のみのバージョン指定では CU4 を証明できません。

入力と出力の両方に明示的な `ServerVersion` 能力設定が必要です。実行時には Host がデータベースの実際のバージョンを検証します。PostgreSQL、MySQL、SQLite、Firebird の入力・出力ではこれらの修飾子を拒否し、対象外のウィンドウ関数、重複・不正な修飾子、`OVER` の欠落も拒否します。修飾子なしの既存の `LAG/LEAD` は変わりません。`WindowSpec.NullTreatment` と `WindowDefinition.NullTreatment` は同じ検証に従い、実際の SQL Server／Oracle の結果行との比較で NULL 無視を確認します。コンパイラーによる SQL 実行や権限付与は行いません。

## SQL Server／Oracle の FIRST_VALUE・LAST_VALUE：NULL の明示的な扱い

SQL Server 2022 以降と Oracle 12.1 以降では、`FIRST_VALUE`／`LAST_VALUE` の直後、`OVER` の前に `IGNORE NULLS` または `RESPECT NULLS` を指定できます。例えば `LAST_VALUE(amount) IGNORE NULLS OVER (PARTITION BY grp ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)` は、現在行までで終わりがちな既定のフレームではなく、**パーティション全体**を対象にします。`IGNORE NULLS` はフレーム内の最初／最後の非 NULL 値を選択し、`RESPECT NULLS` は NULL を考慮します。

入力側と出力側の両方に対応する `ServerVersion`（SQL Server 16.0 以降、または Oracle 12.1 以降）が必要です。SQL Server 2022 CU4 の結果正当性条件は **LAG／LEAD の IGNORE NULLS に限られ**、FIRST／LAST には適用しません。両者は別々に能力を検証します。残る 4 種のデータベース、対象外のウィンドウ関数、不正な修飾子は拒否されます。C# の構造化 DTO も F# の型付き検証とネイティブ SQL 出力を共有し、コンパイラーが SQL を実行したり権限を与えたりすることはありません。

SQL Server と Oracle の間の変換は引き続き拒否します。NULL の既定の並び順とウィンドウフレームの同等性が証明されていないためです。

## PostgreSQL クエリの読み取り専用トランザクション（3.1）

PostgreSQL の `SELECT` は必ずしも書き込みを伴わないとは限りません。`VOLATILE` 関数やユーザー定義関数が実データを変更する場合があります。Host は `execute_query_sql` のコンパイルと権限検証を行った後、コンパイル済みコマンドを、**検証済みの同じ接続上で `READ ONLY` を明示した PostgreSQL トランザクション**により実行します。結果をすべて取得してからロールバックします。F# SqlCore は引き続き DB 接続を行いません。

PostgreSQL 16 の実データベース試験では、修正前に許可済みの `SELECT` がユーザー定義関数経由で行を更新できることを確認しました。32 通りの複数文攻撃、5 種類のテーブル権限回避、シーケンスの変更、適切にパラメーター化された文字列、正当な OR／CTE クエリも回帰試験の対象です。拒否された要求は結果行を返さず、DB の実状態を変えてはいけません。

追加の PostgreSQL 16 実データベース RED テストでは、トランザクションが `READ ONLY` でも `pg_catalog.query_to_xml` から許可リスト外のテーブルを読み出せることが判明しました。そのため、テーブル許可リストを指定したクエリでは、F# のポリシーが安全性を証明できないユーザー定義・ネイティブ関数を拒否し、限定された `pg_catalog` 組み込み関数だけを許可します。許可された関数名は `pg_catalog` で明示的に修飾し、`search_path` による同名関数のすり替えを防ぎます。`LOWER` や `COUNT` などの基本機能は維持します。この対策は読み取り専用トランザクションとは別のものです。実 DB 権限には引き続き最小権限を適用してください。

保護対象は**現時点では PostgreSQL のクエリ実行のみ**です。DML／DDL の権限は付与されず、残る 5 種類の DB で同等の保護が証明されたわけでもありません。アドバイザリーロックなどの外部副作用までは隔離できないため、最小権限と実行制限を引き続き適用してください。
