## 承認の受け入れ、不確定な結果、ターゲット証拠

選択的な条件が必要な場合、`WHERE 1=1` のように常に真と証明できる `UPDATE`／`DELETE` 条件は拒否されます。人間の承認は正確な計画と行集合の証拠に結び付けられます。

カスタム challenge store は、単文・バッチともに `TryPromoteAsync` をアトミックに実装する必要があります。Redis と永続再開にはバージョン付きエンベロープを使います。互換性のない challenge は新しいプレビューと承認が必要です。[アップグレードガイド](/ja/docs/reference/upgrade-guide)を参照してください。

`dml.commit_outcome_unknown` と `dml.rollback_outcome_unknown` は異なる、再試行不可の結果です。承認とターゲット証拠を保存し、独立して調査してください。witness や Redis キーがなくてもロールバックの証明にはなりません。不確定な変更を自動再実行してはいけません。コミット確認後の監査保存エラーを変更失敗として報告してはいけません。

`AddHsSqlAgentTargetExecutionFence()` は任意機能です。ターゲットの準備と、旧 worker に DML 権限がないことの別途検証が必要です。対象コミットごとに実接続で追加のロールバック専用検証トランザクションを 2 回実行し、コミット後に Admission と Witness を独立して読み取ります。Oracle は witness の一意性衝突診断のみ READ COMMITTED、それ以外の検証は SERIALIZABLE です。証拠の矛盾は不確定な結果になります。全 worker の登録証明や稼働中 worker の自動照合は提供しません。

DML は Query より厳格な実行経路を使います。実際の commit 時にも、承認内容が**同じ Mutation Evidence**を示している必要があるためです。

## 1 つの Tool で単一・複数 Statement に対応

`execute_dml_sql` は、1 つ以上の対応 `UPDATE`、`DELETE`、`INSERT ... VALUES` を受け取れます。複数 Statement はセミコロンで区切ります。

専用の batch DML Tool はありません。複数 Statement は 1 つの Batch として Parse され、1 回だけ承認され、元の順序で実行され、1 つのサーバー所有 Transaction で原子的に commit されます。

Client から `BEGIN`、`COMMIT`、`ROLLBACK` などの Transaction-control SQL は受け付けません。Transaction 境界はサーバーが所有します。

## 承認が結び付く Evidence

`UPDATE` / `DELETE` は Preview で観測した正確な Primary Key Row Set に承認を結び付けます。Commit Transaction 内で各 Statement の変更直前に再検証します。

`INSERT ... VALUES` は不変な Literal Payload と正確な Compile 済み Command に結び付けます。`INSERT ... SELECT` は source Row Set の承認意味論が定義されるまで未対応です。

前の Statement が後続 Statement の承認済み Row Set を変えた場合、Batch 全体が fail closed となり rollback します。

## 承認 Provider

第一方の既定は MCP Elicitation です。Host は公式 `HsSqlAgent.Approvals.Webhook` adapter を利用することも、`HsSqlAgent.Server` で `IDmlApprovalProvider` を実装することもできます。

承認 Provider が受け取るのは transport-neutral な Evidence であり、SQL 実行 primitive ではありません。Database Connection、Transaction、検証済み Plan、commit 権限は渡されません。

## Durable Pending Approval

非同期 Workflow の Provider は `Pending` を返せます。Admin Store がある場合、hs-sql-agent は保護された Resume Intent と Approval Fingerprint を保存します。

後から完了 Decision が届くと、現在の認可と DB 設定を再読み込みし、DML を再 Parse / Preview し、承認 Evidence を比較して、新しい短命 Execution Challenge を作成します。認可、DB 設定、Policy、Plan、Row Set、affected-row Evidence のいずれかが変われば stale として扱い commit しません。

再開されるのは**実行 Intent**であり、古い Database Session ではありません。

## SQL Server：CTE を使う更新・削除の複合 INT キー

SQL Server の UPDATE／DELETE では、実在するソース表に**NULL 不可の INT 2 列で構成された主キーまたは一意インデックス**が確認できた場合に限り、明示的な許可の下で 1～3 段の非再帰・直列 CTE を利用できます。両キー列は物理インデックスの順序を保ち、各 CTE で加工せずに引き継ぐ必要があります。更新先の対応する INT 列それぞれに、必須の `AND` と通常の `=` による比較が必要です。実行前には実データベースのメタデータ確認、対象行のプレビュー、承認との結合、同一トランザクション内での再検証を行います。

キーの欠落・順序入れ替え、`OR`、型変換、NULL 許容・計算列、フィルター付き／無効なインデックス、行数を増やす結合は拒否されます。他のデータベースでの実行能力は変わりません。

### CTE に非キー列を追加して投影する（G8／M03）

1～3 段の CTE では、必須の 1～2 列の INT キーに加えて、**ソース行から直接取得する非キー列**も投影できます（各段最大 32 列）。たとえば `SELECT k1 AS a, payload AS extra, k2 AS b` の結果を次の段で `SELECT a, extra, b` として引き継げます。キーは各段でそれぞれ一度だけ投影し、物理一意インデックスでの相対順序を保ち、最終条件では必須の `AND` と通常の `=` で照合します。キーの重複・変換・計算、曖昧な別名、複数ソースや行数を増やす JOIN は引き続き拒否します。実インデックス検証、プレビュー、承認、コミット時の再検証は変わらず、一般的な JOIN や他のデータベースの実行権限は追加されません。

### 単一行の派生テーブルとの JOIN の安全性（G8／M07、限定機能）

SQL Server の各 CTE 段では、**行数が増えないことを構文から証明できる JOIN を最大 1 つ**利用できます。結合先は `SELECT 1 AS marker` のような独立した派生クエリに限り、`FROM`、`WHERE`、`UNION`、集約や追加の行を含められません。`CROSS JOIN (SELECT 1 AS marker) AS one` は元の行数を保ち、定数等式 `ON 1 = 1` を使う `INNER JOIN` と `LEFT JOIN` も行数を増やしません。物理 INT 一意キー、キー列の直接投影、プレビュー、承認、コミット時の実証明は引き続き必須です。**ここまでの単一行・自己 JOIN 証明のみでは別の実テーブルとの JOIN は許可されません。以下の独立した二重一意キー証明で限定的に許可します、APPLY、相関クエリ、複数行の派生ソースや任意の JOIN は許可しません。**

もう一つの限定機能として、**同じ物理ソース表を別名で参照する INNER／LEFT 自己 JOIN**を許可します。ただし ON 条件は、実データベースで検証済みの INT 一意キーの**全構成列**を必須の AND と通常の等号で照合する必要があります。これにより 2 番目の別名は元の各行に対して最大 1 行だけ一致します。キーの欠落、OR のみの条件、計算・型変換されたキーや別の物理表への JOIN は拒否します。

### 異なる実テーブル間の JOIN と二重の一意キー証明（M07）

SQL Server の CTE は、別の物理テーブルに対して 1 つの **INNER JOIN** または **LEFT JOIN** を利用できます。両方のソース表にそれぞれ、実データベースで確認済みの 1～2 列からなる NULL 不可の `INT`／`BIGINT` 一意キーが必要です。インデックスは有効かつフィルターなしでなければなりません。`ON` 条件ではすべてのキー列を必須の `AND` と通常の `=` で照合し、列ごとの実際の型も完全一致させます。仮想カタログ、暗黙の型変換、部分キー比較やフィルター付きインデックスは証明になりません。両インデックスの識別情報を実行計画・承認に結び付け、コミット時の実トランザクションでも再確認します。プレビュー後にいずれかの証明が失効すると変更を拒否します。3 つ目の物理ソース、多対多 JOIN、`RIGHT`／`FULL JOIN`、異なる DB 方言への変換や任意の JOIN は許可しません。

### 全キー相関 EXISTS／NOT EXISTS フィルター（M07、限定段階）

SQL Server の CTE を用いた `UPDATE`／`DELETE` では、最初の CTE の `WHERE` に **`EXISTS`（セミ結合）または `NOT EXISTS`（アンチ結合）**を指定できます。ただし副問い合わせは、実データベースで一意キーを検証済みの**同一ソース表を別名で再参照**する場合に限ります。投影はリテラルのみ、追加 JOIN・集約・並べ替え・集合演算は禁止です。1～2 列の `INT`／`BIGINT` 一意キーを必須の `AND` と通常の `=` ですべて相関させ、内側の列とリテラルの比較でさらに絞り込めます。この条件は行を除外するだけで増やしません。実インデックスの証明、プレビュー、承認の識別情報、コミット時のトランザクション内での再検証は従来どおり必須です。**任意の入れ子問い合わせ、未検証の別テーブル、一般的な EXISTS／アンチ結合の実行権限は許可しません。**

### TINYINT と SMALLINT の物理キー型の厳密な検証（G9／M04、develop のみ）

SQL Server の CTE を用いた `UPDATE`／`DELETE` の実キー検証では、従来の `INT` と `BIGINT` に加え、組み込みの `TINYINT`（符号なし 8 ビット）と `SMALLINT`（符号付き 16 ビット）を扱えます。1～2 列の物理一意キーについて、ソース、更新先、独立して検証された JOIN 先の対応する列は、**インデックス上の各キー位置で実際の SQL Server 型が完全一致**しなければなりません。暗黙の整数型変換、ユーザー定義の別名型、仮想カタログは実証の代わりになりません。従来の限定 CTE キー伝播、行数を増やさない JOIN の検証、対象行プレビュー、独立承認、不変の計画指紋、コミット時の同一トランザクション内でのインデックス再検証は引き続き必須です。SQL Server 2022 の実テストで更新・削除、混合型のキー、インデックス失効を確認します。DECIMAL、UUID、NULL を許す一意キー、任意の JOIN、他のデータベースには拡張されません。


### UNIQUEIDENTIFIER の物理キーを厳密に検証（G9／M04、develop のみ）

SQL Server の CTE `UPDATE`／`DELETE` の物理的な一意性検証で、**組み込みの 128 ビット `UNIQUEIDENTIFIER` キー**を扱えるようにしました。`Uuid` は独立したスキーマ値型であり、**数値・文字列・バイナリ型に置き換えません**。Host は実際の `sys.tables`、`sys.columns`、`sys.types` を参照して、ソース・更新先・独立して確認した 2 番目の JOIN テーブルのキー型を取得します。F# の閉じた型が UNIQUE インデックス全体と、スナップショットに記載された型と物理型の一致を独立して検証します。`UNIQUEIDENTIFIER` と `INT`、`DECIMAL`、`VARCHAR`、`BINARY(16)` の暗黙変換を実行許可の根拠にすることはできません。

1～2 列のキーでは UUID と厳密に一致する整数・小数型を組み合わせられます。従来の 1～3 段の限定 CTE、行を増やさない JOIN、更新前プレビュー、独立承認、コミットと同じトランザクション内の `IsCurrent` 再検証は継続します。ProofIdentity は v6 に更新され、以前の承認を再利用できません。SQL Server 2022 の実テストで UUID の UPDATE／DELETE、主キーと一意インデックス、自動検出、別テーブルとの JOIN、プレビュー後のインデックス失効、型不一致の拒否を確認します。MCP ツール、DML の初期選択、任意 JOIN、他 5 種類のデータベースの権限は増えません。

### DECIMAL／NUMERIC の物理キーを厳密に検証（G9／M04、develop のみ）

SQL Server の CTE `UPDATE`／`DELETE` の物理的一意キー検証では、組み込みの `DECIMAL(p,s)` と `NUMERIC(p,s)` も扱います（`1 ≤ p ≤ 38`、`0 ≤ s ≤ p`）。両者は SQL Server では同義ですが、ソース、更新先、独立して確認した JOIN 先のキーは、**インデックスの各位置で精度と小数点以下の桁数が完全一致**しなければなりません。`DECIMAL(12,2)` と `DECIMAL(13,2)`、`DECIMAL(12,3)`、整数型の間の暗黙変換では一意性を証明できません。

Host は実際の `sys.columns`／`sys.types` を参照し、元の UNIQUE インデックスを構成する**すべてのキー列**を検証します。未対応のユーザー定義別名型があっても、`UNIQUE(a,b)` を `UNIQUE(a)` と誤認しません。F# の閉じた型に精度と小数桁数を保持します。従来の 1～3 段の限定 CTE、行を増加させない JOIN、対象行のプレビュー、独立承認、バージョン付き証明、同一コミットトランザクション内の再検証は変わりません。SQL Server 2022 の実テストでは小数値、整数と小数の複合キー、別の実テーブルとの JOIN、インデックス失効、精度不一致の拒否を確認します。UUID・文字列キー、NULL 可の一意キー、任意の JOIN、他の 5 種類のデータベースは対象外です。


## Fail-closed ルール

承認拒否、期限切れ、stale、Fingerprint 不一致、権限失効、現在の Policy 違反、承認 Row Set の再現失敗では DML は commit されません。
