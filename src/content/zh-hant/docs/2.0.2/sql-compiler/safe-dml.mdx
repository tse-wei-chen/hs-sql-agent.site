DML 比 query 使用更嚴格的流程，因為真正 commit 時，人工核准的內容仍必須描述**同一個 mutation**。

  <DocCard title="Approval 有綁定證據" icon="02" description="One-time challenge 會綁定 validated plan、policy version、affected-row count 與 row-set fingerprint。" />
  <DocCard title="Commit 會重新確認現況" icon="03" description="Commit transaction 重新查 row set；只要與核准時 facts 不一致就取消。" />

<Callout type="danger" title="核准不是允許日後執行另一個 mutation">
Approval challenge 綁定的是已驗證 operation 與當下觀察到的 impact。若 commit 前 plan、policy、challenge、affected-row count 或 row-set fingerprint 有任何改變，hs-sql-agent 會取消，而不是照樣執行。
</Callout>

## UPDATE 與 DELETE

<Steps>
  <Step title="Compile mutation">
在要求 approval 前，先完成 parse、validation、authorization 與 compile。
  </Step>
  <Step title="Preview affected row set">
開啟 preview transaction，只讀目前 matching rows，不執行 mutation。
  </Step>
  <Step title="建立 one-time approval evidence">
把 validated compiled plan、policy version、affected-row count 與 row-set fingerprint 綁到 challenge。
  </Step>
  <Step title="透過 MCP Elicitation 請真人核准">
送出 `elicitation/create`，要求 MCP client 明確完成 form approval。
  </Step>
  <Step title="Consume approved challenge">
Accept 後驗證並 consume one-time challenge，避免它被當成 generic permission token 重放。
  </Step>
  <Step title="在 commit transaction 重新查詢">
再次讀取 matching rows，比較目前 fingerprint/count 與 approval preview 是否一致。
  </Step>
  <Step title="全部一致才 commit">
只有 plan、policy、challenge、row count 與 row set 都未改變，才執行原本那個 compiled mutation。
  </Step>
</Steps>

## INSERT VALUES

`INSERT ... VALUES` 沒有既存 matching row set，因此 approval protocol 會綁定 immutable insert payload 與 exact compiled plan，而不是 row-set preview。

<Callout type="info" title="Mutation shape 不同，但 invariant 相同">
Row-set mutation 與 insert payload 所核准的 evidence 不同，但核心原則一樣：只 commit approval 所描述的 exact validated mutation。
</Callout>

## Elicitation 是必要條件

`execute_dml_sql` 與 published DML Custom Tools 都需要 MCP client 支援 **form Elicitation**。無法完成 approval interaction 的 client 不能使用這些 mutation paths。

這不是單純 UI confirmation：approval challenge 是 server-side mutation protocol 的一部分，執行前還會再次被驗證。
