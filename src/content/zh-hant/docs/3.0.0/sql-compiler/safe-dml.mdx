## 核准准入、不確定結果與目標證據

要求選擇性條件時，能證明恆真的 `UPDATE`／`DELETE` 條件（例如 `WHERE 1=1`）會被拒絕。人工核准仍須繫結精確的計畫與資料列集合證據。

自訂 challenge store 必須為單一與批次操作原子實作 `TryPromoteAsync`。Redis 與持久化續行使用版本化封套；不相容的 challenge 須重新預覽與核准。詳見[升級指南](/zh-hant/docs/reference/upgrade-guide)。

`dml.commit_outcome_unknown` 與 `dml.rollback_outcome_unknown` 是不同且不可重試的結果。請保留核准與目標證據，進行獨立釐清。缺少 witness 或 Redis key 都無法證明已回復，不可自動重播結果不明的變更。已確認提交後，即使稽核儲存失敗，也不能回報為變更失敗。

`AddHsSqlAgentTargetExecutionFence()` 須明確啟用，先準備目標資料表與權限，並另外證明舊 worker 已失去 DML 權限。每次納管提交都在實際連線上執行兩個額外的僅回復 readiness 交易，提交後獨立讀取 Admission 與 Witness 各一次。Oracle 只在 witness 唯一鍵衝突診斷使用 READ COMMITTED，其餘 readiness 階段使用 SERIALIZABLE。證據矛盾會回報不確定結果；這不提供整個叢集的節點納管證明，也不會自動處置仍存活的 worker。

DML 比 Query 使用更嚴格的執行路徑，因為真正 commit 時，核准內容仍必須描述**同一份 Mutation Evidence**。

## 一個 Tool，同時支援單語句與多語句

`execute_dml_sql` 可接受一個或多個受支援的 `UPDATE`、`DELETE`、`INSERT ... VALUES`，多個 Statement 以分號分隔。

沒有額外的 batch DML Tool。多語句輸入會解析成一個 Batch，只核准一次，依原始順序執行，最後在一個由伺服器掌握的 Transaction 中原子提交。

Client 不可送入 `BEGIN`、`COMMIT`、`ROLLBACK` 等 Transaction-control SQL；交易邊界由伺服器掌握。

## 核准綁定的內容

`UPDATE` / `DELETE` 的核准綁定 Preview 時觀察到的精確 Primary Key Row Set。Commit Transaction 內每個 Statement 在真正修改前都會立即重新驗證。

`INSERT ... VALUES` 的核准綁定不可變的 Literal Payload 與精確的編譯 Command。`INSERT ... SELECT` 在來源 Row Set 核准語意定義完成前仍不開放。

若前一個 Statement 改變了後一個 Statement 原先核准的 Row Set，整個 Batch 會 fail closed 並 rollback。

## 核准 Provider

MCP Elicitation 仍是第一方預設 Provider。Host 也可以使用官方 `HsSqlAgent.Approvals.Webhook` adapter，或在 `HsSqlAgent.Server` 實作 `IDmlApprovalProvider`。

核准 Provider 收到的是與傳輸方式無關的 Evidence，不是 SQL 執行 primitive；不會取得 Database Connection、Transaction、已驗證 Plan 或 commit 權限。

## Durable Pending Approval

Provider 可以對非同步流程回傳 `Pending`。有 Admin Store 時，hs-sql-agent 會保存受保護的 Resume Intent 與 Approval Fingerprint。

之後收到完成決策時，伺服器會重新載入目前授權與資料庫設定、重新 Parse / Preview DML、比對核准 Evidence，再建立新的短效 Execution Challenge。授權、資料庫設定、Policy、Plan、Row Set 或 affected-row Evidence 只要改變，就會視為 stale 而不是 commit。

完成流程恢復的是**執行意圖**，不是舊的 Database Session。

## SQL Server：CTE 更新與刪除的複合 INT 鍵

SQL Server 的 UPDATE／DELETE 在明確授權下，可透過 1～3 層線性、非遞迴 CTE 讀取實體來源資料表，但必須先確認來源具有**由兩個不可為 NULL 的 INT 欄位組成的主鍵或唯一索引**。兩個鍵欄位必須依實體索引順序，在每一層 CTE 原樣投影。最終修改語句須使用必要的 `AND` 與一般 `=`，分別匹配目標資料表的兩個 INT 欄位。執行前還需要驗證實體資料庫中繼資料、預覽受影響資料列、綁定核准內容，並在實際提交交易內再次檢查中繼資料。

缺少或交換鍵欄位、僅靠 `OR` 匹配、型別轉換、可為 NULL 或計算欄位、篩選或停用的索引，以及造成匹配資料列倍增的 JOIN，都會被拒絕。這項能力不會擴大其他資料庫的可執行範圍。

### CTE 投影可包含非鍵欄位（G8／M03）

1～3 層 CTE 除了必要的 1～2 欄 INT 鍵，也能同時投影**直接來自來源資料列的其他欄位**，每層最多 32 欄。例如先使用 `SELECT k1 AS a, payload AS extra, k2 AS b`，再使用 `SELECT a, extra, b`。鍵欄位在每一層都必須各出現一次，維持實體唯一索引的相對順序，最終仍須以必要的 `AND` 和一般 `=` 比對。鍵值重複、轉換或計算、別名歧義、多來源及可能增加資料列的 JOIN 一律拒絕。實體唯一索引驗證、預覽、核准與提交交易內的再次檢查均不變；這項擴充不代表支援一般 JOIN，也不影響其他資料庫。

### 單一資料列 JOIN 的安全證明（G8／M07，受限子集）

SQL Server 的每一層 CTE 現在最多可額外使用一個**可證明不會增加資料列數的 JOIN**：連接來源必須是完全獨立的 `SELECT 1 AS marker` 衍生查詢，不含 `FROM`、`WHERE`、`UNION`、分組或其他資料列。`CROSS JOIN (SELECT 1 AS marker) AS one` 保持來源列數；使用常值等式 `ON 1 = 1` 的 `INNER JOIN`／`LEFT JOIN` 也不會增加列數。實體 INT 唯一鍵、原樣鍵欄位投影、預覽、核准及提交交易內的實體證明仍不可省略。**這不代表開放與其他實體資料表的 JOIN、APPLY、相關子查詢、多資料列衍生來源或任意 JOIN。**

另一個受限形式允許**同一張實體來源表以不同別名進行 INNER／LEFT self-JOIN**，前提是 ON 條件以必要的 AND 與一般等式完整比對**已在實體資料庫驗證的每一個 INT 唯一鍵欄位**。因此第二個別名對每筆來源資料最多只會匹配一列。缺少鍵欄位、僅靠 OR、計算或轉型後的鍵，以及與其他資料表的 JOIN 都會拒絕。

### 跨實體資料表 JOIN 的雙重唯一鍵證明（M07）

SQL Server CTE 現在可使用一次 **INNER** 或 **LEFT JOIN** 連接另一張實體資料表。兩張來源表都必須各自通過實際資料庫的唯一鍵驗證：1～2 欄不可為 NULL 的 `INT`／`BIGINT`，索引必須已啟用、未篩選。JOIN 的 `ON` 條件須以必要的 `AND` 和一般 `=` 完整比對兩邊每一個鍵欄位，且各位置的實體型別必須精確相同。虛擬目錄、隱含型別轉換、只比對部分鍵或篩選索引都不能構成證明。兩份索引身分均會綁定執行計畫與核准，提交時在實際交易內再次驗證；預覽後撤銷任一證明會拒絕提交。這不代表開放第三張來源表、多對多 JOIN、`RIGHT`／`FULL JOIN`、跨資料庫方言轉譯或任意 JOIN。

## Fail-closed 規則

核准被拒絕、過期、stale、Fingerprint 不符、權限被撤銷、違反目前 Policy，或無法重現核准 Row Set 時，都不會提交 DML。
