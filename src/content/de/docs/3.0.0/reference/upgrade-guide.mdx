## Geplante Änderung für 3.0.0: Versionierter Geheimnisschutz

**Status: noch in Prüfung unter [hs-sql-agent PR #302](https://github.com/tse-wei-chen/hs-sql-agent/pull/302), nicht Teil der veröffentlichten Version 2.0.6.** Diese Seite beschreibt ausschließlich die Migration des Geheimnisschutzes und **nicht** sämtliche Änderungen von 2.0.6 auf 3.0.0.

Die bisherige HMAC-abgeleitete Verschlüsselung wird durch AES-256-GCM ersetzt, das an Verwendungszweck und vertrauenswürdigen Datensatz gebunden ist. Das Format lautet `v2:<key-id>:<base64 nonce/tag/ciphertext>` und authentifiziert Version, Schlüssel-ID, Zweck und Datensatzkennung. **Es gibt weder eine Entschlüsselung für das alte Format noch eine automatische Umwandlung.**

## Inkompatible Änderungen

| Bereich | Erforderliche Maßnahme |
| --- | --- |
| Gespeicherte Datenbankpasswörter | Die neue Laufzeit kann alte Chiffrate nicht lesen. Passwörter über die Verwaltungsoberfläche/API erneut eingeben oder bei der Erstkonfiguration bereitstellen. |
| Dauerhafte DML-Freigaben | Vor der Migration `Pending`-Anfragen abschließen und tatsächliche Ergebnisse von `Executing` prüfen. SQLite-/PostgreSQL-Migrationen des Admin Stores weisen noch aktive Freigaben zurück. Historische verschlüsselte Fortsetzungsdaten werden ebenfalls unlesbar. |
| Schutzschlüssel | Drei **voneinander unabhängige** zufällige 32-Byte-Schlüssel in Base64 sind erforderlich: für Datenbankpasswörter, DML-Nutzdaten und DML-Fingerabdrücke. Fehlende, ungültige, zu kurze oder mehrfach verwendete Schlüssel verhindern den Start. |
| Bootstrap-MCP-Schlüssel | `Bootstrap:Databases:*:McpKeys:*:Key` (im Docker-Beispiel `BOOTSTRAP_MCP_KEY`) explizit setzen. Beim Start werden keine Schlüssel mehr automatisch erzeugt oder protokolliert. Früher in Logs offengelegte Schlüssel widerrufen. |
| `ExtraSettings` | Nur die JSON-Booleschen Felder `Encrypt` und `TrustServerCertificate` sind erlaubt. Unbekannte oder doppelte Felder, Zeichenfolgen und ungültiges JSON werden abgewiesen. |
| Diagnose | Verbindungstests und Health-Probes liefern `DB_CONNECTION_FAILED` statt roher Treiberfehler. Runtime Doctor prüft `security.secret-protection` ohne Schlüsselwerte auszugeben. |

## Erforderliche Upgrade-Schritte

1. **Sichern** Sie den Admin Store und die bisherigen Geheimnisse. Prüfen Sie die Wiederherstellbarkeit und behalten Sie die alte Anwendung für schreibgeschützte Untersuchungen.
2. **Stoppen Sie die Annahme neuer DML-Freigaben.** Bearbeiten Sie alle `Pending`-Vorgänge und prüfen Sie die tatsächlichen Datenbankergebnisse der `Executing`-Vorgänge unabhängig. Kennzeichnen Sie unklare Ausführungen niemals nur zur Umgehung der Migrationssperre als erfolgreich oder fehlgeschlagen.
3. **Prüfen Sie historische Ausführungsnachweise vorher.** Alte verschlüsselte Fortsetzungsdaten können danach auch bei abgeschlossenen Vorgängen nicht mehr entschlüsselt werden.
4. **Erzeugen Sie drei unabhängige Schlüssel**, indem Sie `openssl rand -base64 32` dreimal getrennt ausführen. Geben Sie diese niemals ins Repository und verwenden Sie keine absichtlich ungültigen Beispielwerte.
5. **Konfigurieren Sie sämtliche Knoten identisch**, einschließlich benötigter alter Schlüssel und des nicht versionierten DML-Fingerabdruckschlüssels. Behalten Sie `HMAC_KEY` für bestehende MCP-Schlüssel bei; JWT-Signaturschlüssel bleiben separat.
6. Hinterlegen Sie Bootstrap-MCP-Schlüssel ausdrücklich, falls Provisionierung aktiv ist, oder stellen Sie sie über die authentifizierte Verwaltungsoberfläche/API aus. Das Geheimnis wird nur einmal angezeigt.
7. **Aktualisieren Sie sämtliche Knoten gemeinsam** und führen Sie die SQLite-/PostgreSQL-Migration durch. Alte und neue Binärdateien dürfen nicht gleichzeitig betrieben werden.
8. Geben Sie bestehende Datenbankpasswörter erneut ein. Prüfen Sie Verbindungen, autorisierte Leseabfragen und DML-Freigaben, bevor Sie den Datenverkehr wieder zulassen.

Die Migration ergänzt pro Datenbankverbindung eine eindeutige, stabile `SecretBindingId` und entfernt die PostgreSQL-Längenbegrenzung für Chiffrate. Die Spalte `PasswordHash` enthält **entschlüsselbare Zugangsdaten** und keinen Einweg-Hash.

## Schlüssel konfigurieren

Für Docker müssen die folgenden Umgebungsvariablen mit echten Werten belegt werden:

```dotenv
# Replace every example value with a different output of openssl rand -base64 32
DB_ENCRYPTION_KEY_ID=db-1
DB_ENCRYPTION_KEY=REPLACE_WITH_32_BYTE_BASE64_VALUE_1
DML_ENCRYPTION_KEY_ID=dml-1
DML_ENCRYPTION_KEY=REPLACE_WITH_32_BYTE_BASE64_VALUE_2
DML_FINGERPRINT_KEY=REPLACE_WITH_32_BYTE_BASE64_VALUE_3
```

Die `REPLACE_WITH_...`-Werte sind **keine gültigen Schlüssel**. Erzeugen Sie drei getrennte Werte:

```sh
openssl rand -base64 32
openssl rand -base64 32
openssl rand -base64 32
```

Bei einem eigenen .NET-Host muss `HsSqlAgentRuntimeOptions.SecretProtection` (bzw. `SecretProtection` in den bisherigen Gesamtoptionen) **vor** der Registrierung der Laufzeit gesetzt werden:

```json
{
  "SecretProtection": {
    "DatabasePasswords": { "ActiveKeyId": "db-1", "Keys": { "db-1": "<base64-key-1>" } },
    "DmlPayloads": { "ActiveKeyId": "dml-1", "Keys": { "dml-1": "<base64-key-2>" } },
    "DmlFingerprintKey": "<base64-key-3>"
  }
}
```

Jeder Verschlüsselungsschlüsselring besitzt `ActiveKeyId` und `Keys`. Datenbankkennwörter sind an `db-password:<SecretBindingId>`, dauerhafte DML-Daten an `dml-payload:<RequestId>` gebunden. Verwenden Sie die Kennung des vertrauenswürdigen Datensatzes, niemals eine aus dem Chiffrat entnommene Kennung.

## Schlüsselrotation

1. Verteilen Sie alte und neue Verschlüsselungsschlüssel unter unterschiedlichen IDs an **alle** Knoten.
2. Stellen Sie sicher, dass beide Schlüssel überall vorhanden sind, bevor Sie `ActiveKeyId` umstellen. Neue Schreibvorgänge nutzen den aktiven Schlüssel; beim Lesen bestimmt die Schlüssel-ID im Chiffrat den aufzubewahrenden Schlüssel.
3. Speichern Sie Datenbankpasswörter erneut, um sie neu zu verschlüsseln. Alte DML-Schlüssel bleiben erhalten, solange Nutzdaten oder historische Nachweise noch entschlüsselt werden müssen.
4. Entfernen Sie Schlüssel erst, wenn keine noch benötigten Chiffrate auf sie verweisen.

`DmlFingerprintKey` ist **nicht versioniert**. Vor einem Wechsel müssen Freigaben abgearbeitet und frühere Geheimnisse für Untersuchungen aufbewahrt werden. Die einfachen Docker-Compose-Variablen legen aktive Schlüssel fest; weitere aufbewahrte IDs sind über Konfigurationsüberschreibungen oder eingebundene Geheimnisse bereitzustellen.

## Rollback und Prüfung

**Eine Rückwärtsmigration ist nicht vorgesehen.** Ein Rollback erfordert die Wiederherstellung des **vorherigen Admin-Store-Backups**, der alten Binärdateien sowie der zugehörigen Konfiguration und Schlüssel. Nur die alte Anwendung gegen die migrierte Datenbank zu starten, ist nicht sicher.

Prüfen Sie `security.secret-protection` in Runtime Doctor. Öffentliche Beispielschlüssel erzeugen außerhalb der Produktion eine Warnung, in der Produktion einen Fehler. Unveränderte Platzhalter oder ungültige Einstellungen verhindern den Start. Prüfen Sie die Entschlüsselung von Passwörtern und Freigabedaten sowie den Schutz vor rohen Datenbanktreibermeldungen.
