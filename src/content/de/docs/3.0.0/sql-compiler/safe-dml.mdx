## Zulassung, ungewisse Ergebnisse und Zielnachweise

Wenn ein selektives Prädikat erforderlich ist, werden nachweislich immer wahre `UPDATE`-/`DELETE`-Filter wie `WHERE 1=1` abgewiesen. Die menschliche Genehmigung bleibt an den exakten Plan und die Zeilenmengennachweise gebunden.

Eigene Challenge-Stores müssen `TryPromoteAsync` für einzelne Anweisungen und Stapel atomar implementieren. Redis und dauerhafte Fortsetzung verwenden versionierte Hüllen. Inkompatible Challenges benötigen eine neue Vorschau und Zustimmung. Siehe [Upgrade-Leitfaden](/de/docs/reference/upgrade-guide).

`dml.commit_outcome_unknown` und `dml.rollback_outcome_unknown` sind unterschiedliche, nicht wiederholbare Ergebnisse. Bewahren Sie Genehmigungs- und Zielnachweise zur unabhängigen Klärung auf. Fehlende Witnesses oder Redis-Schlüssel beweisen keinen Rollback. Wiederholen Sie ungewisse Änderungen niemals automatisch. Ein Audit-Speicherfehler nach bestätigtem Commit darf nicht als fehlgeschlagene Änderung gemeldet werden.

`AddHsSqlAgentTargetExecutionFence()` ist optional und setzt Zielvorbereitung sowie einen separaten Nachweis entzogener DML-Rechte alter Worker voraus. Jeder eingebundene Commit führt auf der tatsächlichen Verbindung zwei zusätzliche, stets zurückgerollte Bereitschaftstransaktionen und danach zwei unabhängige Leseprüfungen von Admission und Witness aus. Oracle verwendet READ COMMITTED nur zur Diagnose des Witness-Eindeutigkeitskonflikts; sonst gilt SERIALIZABLE. Widersprüchliche Beweise ergeben ein ungewisses Ergebnis. Dies zertifiziert weder die Einbindung aller Worker noch eine automatische Klärung laufender Worker.

DML verwendet einen strengeren Ausführungspfad als Queries, weil die Freigabe beim tatsächlichen Commit weiterhin **dieselbe Mutation Evidence** beschreiben muss.

## Ein Tool für einzelne und mehrere Statements

`execute_dml_sql` akzeptiert eine oder mehrere unterstützte `UPDATE`-, `DELETE`- oder `INSERT ... VALUES`-Anweisungen. Mehrere Statements werden durch Semikolons getrennt. Ein begrenztes SQLite-`INSERT ... SELECT` ist ebenfalls zulässig, aber **nur als einzelne Anweisung**, niemals innerhalb eines Stapels.

Es gibt kein separates Batch-DML-Tool. Mehrere Statements werden als ein Batch geparst, einmal freigegeben, in Originalreihenfolge ausgeführt und innerhalb einer serverseitig kontrollierten Transaction atomar committet.

Vom Client geliefertes Transaction-control SQL wie `BEGIN`, `COMMIT` oder `ROLLBACK` wird nicht akzeptiert. Die Transaction-Grenzen gehören dem Server.

## Woran die Freigabe gebunden ist

Bei `UPDATE` und `DELETE` bindet die Freigabe an das exakte Primary-Key-Row-Set aus dem Preview. Jedes Statement wird in der Commit Transaction unmittelbar vor seiner Mutation erneut geprüft.

Bei `INSERT ... VALUES` bindet die Freigabe an den unveränderlichen Literal Payload und die exakte kompilierte Command.

### SQLite: Freigabe der Quellzeilen für eine Einzelanweisung (G9/M09, nur develop)

Ein streng begrenztes `INSERT ... SELECT` ist **nur mit SQLite** zulässig. Die direkte Quelle und das Einfügeziel müssen echte, explizit qualifizierte `main`-Tabellen sein (dieselbe oder zwei unterschiedliche Tabellen); unterschiedliche physische Schemas werden unabhängig geprüft. Ausdrückliche eindeutige Zielspalten, direkte Quellspalten, `WHERE Spalte = Nicht-NULL-Literal`, ein positiver endlicher Zeilengrenzwert und `AddHsSqlAgentNativeDmlSchemaFreshness()` bleiben Pflicht.

Die Vorschau bindet **alle projizierten Quellwerte**, ohne automatisch erzeugte Ziel-IDs vorzutäuschen. Beim Commit wird zuerst die SQLite-Schreibreservierung erworben, dann werden in derselben Transaktion die echten Schemas und Quellzeilen erneut geprüft und der kompilierte INSERT einmal ausgeführt. SQLite **ab 3.35** erlaubt zusätzlich `RETURNING` mit eindeutigen, unqualifizierten direkten Zielspalten ohne Alias. Die tatsächlichen eingefügten Zeilen werden **erst nach erfolgreichem Commit** zurückgegeben und gehören nicht zu den Quellvorschauzeilen. Wildcards, Ausdrücke und Aliase bei RETURNING, CTE, JOIN, UPSERT, angehängte Datenbanken, mehrere Anweisungen und andere Provider bleiben gesperrt. DML-Rechte und gesonderte Freigabe bleiben unverändert.

Verändert ein früheres Statement das freigegebene Row Set eines späteren Statements, schlägt der gesamte Batch fail closed fehl und wird zurückgerollt.

## Freigabe-Provider

MCP Elicitation bleibt der offizielle Standard-Provider. Hosts können außerdem den offiziellen Adapter `HsSqlAgent.Approvals.Webhook` verwenden oder mit `HsSqlAgent.Server` einen eigenen `IDmlApprovalProvider` implementieren.

Der Provider erhält transportneutrale Evidence, keine SQL-Ausführungs-Primitives. Er erhält weder Database Connection noch Transaction, validierten Plan oder Commit-Autorität.

## Durable Pending Approvals

Ein Provider kann für asynchrone Workflows `Pending` zurückgeben. Mit Admin Store speichert hs-sql-agent einen geschützten Resume Intent und Approval Fingerprints.

Bei einer späteren Entscheidung lädt der Server aktuelle Autorisierung und DB-Konfiguration neu, parst und previewt das DML erneut, vergleicht die freigegebene Evidence und erstellt einen neuen kurzlebigen Execution Challenge. Änderungen an Autorisierung, DB-Konfiguration, Policy, Plan, Row Set oder affected-row Evidence machen den Request stale, statt ihn zu committen.

Fortgesetzt wird der**Ausführungs-Intent**, nicht eine alte Database Session.

## SQL Server: zusammengesetzte INT-Schlüssel bei CTE-Mutationen

Ein ausdrücklich freigegebenes UPDATE oder DELETE in SQL Server darf eine physische Quelltabelle über ein bis drei lineare, nicht rekursive CTEs lesen, wenn ein tatsächlich geprüfter **zweispaltiger, nicht nullbarer INT-Primärschlüssel oder eindeutiger Index** existiert. Beide Schlüsselspalten müssen unverändert und in der Reihenfolge des physischen Index durch alle CTEs weitergegeben werden. Zwei zwingende Vergleiche mit `AND` und normalem `=` müssen die entsprechenden INT-Zielspalten binden. Vor der Ausführung sind eine Prüfung des echten SQL-Server-Katalogs, eine begrenzte Vorschau der betroffenen Zeilen, eine Freigabe und die erneute Prüfung innerhalb derselben Transaktion erforderlich.

Fehlende oder vertauschte Schlüssel, `OR`, Typumwandlungen, nullbare oder berechnete Schlüssel, gefilterte/deaktivierte Indizes und vervielfachende Joins bleiben ausgeschlossen. Andere Datenbanken erhalten dadurch keine neue Ausführungsberechtigung.

### Begrenzte Zusammenführung zweier CTE-Zweige (G9/M06, nur develop)

SQL-Server-CTE-`UPDATE`/`DELETE` lässt eine eng begrenzte **Verzweigung mit drei CTEs** zu: Zwei unabhängige CTEs projizieren die vollständigen zwei UNIQUE-Schlüsselspalten **derselben physischen Quelltabelle** direkt und in ursprünglicher Reihenfolge. Eine dritte CTE führt sie ausschließlich mit `INNER JOIN` und beiden gewöhnlichen Schlüsselgleichheiten zusammen. Das Ziel wird ebenfalls über beide Schlüsselspalten abgeglichen.

Dies ist keine allgemeine Unterstützung beliebiger CTE-DAGs. Statische F#-Kardinalitätsprüfung, geschlossene F#-Schreibzulassung und Host-Prüfung des echten Indexes bleiben unabhängig. Vorschau→unabhängige Freigabe→`IsCurrent` mit Sperren in derselben Transaktion sind weiterhin Pflicht. Andere Quellen, fehlende/doppelte Schlüsselbedingungen, `OR`, `LEFT JOIN`, Filter, `CAST`, berechnete Spalten, zusätzliche Zweige und mehrdeutige Aliase werden abgelehnt. Die anderen fünf Datenbanken und MCP-Standards bleiben unverändert.

### Physische UNIQUE-Schlüssel über zwei Derived-Table-Stufen (G9/M06, nur develop)

SQL-Server-CTE-`UPDATE`/`DELETE` darf vor den bisherigen 1–3 CTE-Stufen nun **höchstens zwei nicht-laterale Derived Tables mit direkter Spaltenprojektion** durchlaufen. Der vollständige physische UNIQUE-Schlüssel muss in derselben Reihenfolge erhalten bleiben, z. B. mit `FROM (SELECT mid.x AS x, mid.y AS y FROM (SELECT s.k1 AS x, s.k2 AS y FROM dbo.Source AS s) AS mid) AS d` und anschließend `SELECT d.x AS a, d.y AS b`. Dies erweitert den unten beschriebenen einstufigen Fall, **nicht** beliebige mehrzweigige CTE-DAGs.

F#-Kardinalitätsprüfung, F#-Ausführungsfreigabe und Host-Prüfung des realen Indexes bestätigen die Herkunft unabhängig. Ein echter UNIQUE-Index, identische Typen und Kollationen, vollständige Zielgleichheiten, Vorschau→unabhängige Freigabe→Commit sowie `IsCurrent` unter Sperren derselben Transaktion bleiben zwingend. Eine dritte Ableitungsstufe, zusätzliche Quellen, JOIN, WHERE, DISTINCT, Gruppierung, Sortierung, Paging, berechnete oder konvertierte Schlüssel, doppelte Aliase sowie fehlende/vertauschte Schlüssel werden abgelehnt. Die anderen fünf Datenbanken, vier standardmäßig lesenden Werkzeuge und die deaktivierte DML-Vorgabe bleiben unverändert.

### Schlüsselbewahrende Ableitung einer einstufigen Derived Table (G9/M06, nur develop)

SQL-Server-CTE-`UPDATE`/`DELETE` erlaubt vor den bisherigen 1–3 CTE-Stufen nun **eine nicht-laterale Derived Table über genau einer physischen Quelltabelle**. Die abgeleitete SELECT-Projektion und die folgenden CTEs können jede Spalte des vollständigen geordneten UNIQUE-Schlüssels direkt umbenennen, etwa `FROM (SELECT s.k1 AS x, s.k2 AS y FROM dbo.Source AS s) AS d`, gefolgt von `SELECT d.x AS a, d.y AS b`. F#-Kardinalitätsanalyse und Host-Katalogprüfung verfolgen die Schlüsselherkunft unabhängig. Für DML sind weiterhin der vollständige echte UNIQUE-Index sowie identische physische Typen, NULL-Semantik und Kollationen erforderlich. Ein Alias oder virtueller Catalog begründet keine Ausführungsbefugnis.

Dies ist **keine allgemeine Freigabe für Derived Tables oder mehrzweigige CTE-DAGs**. JOIN, WHERE, DISTINCT, GROUP/HAVING, Aggregate, ORDER, LIMIT/TOP/OFFSET, UNION, verschachtelte Derived Tables/CTEs, LATERAL, CAST/berechnete Schlüssel, doppelte Aliasnamen oder fehlende UNIQUE-Spalten sind ausgeschlossen. Vorschau→unabhängige Freigabe→Commit, die exakte Zeilenmenge und `IsCurrent` mit Sperren in derselben Commit-Transaktion bleiben Pflicht; ein entzogener Index verhindert den Commit. Echte SQL-Server-2022-Tests decken 1–3 CTE-Stufen, zusammengesetzte Ganzzahl-/Dezimal-/UUID-/Textschlüssel und UPDATE/DELETE ab. Die anderen fünf Datenbanksysteme und Standard-MCP-/DML-Rechte ändern sich nicht.


### Exakter Nachweis sprachabhängiger Kollationen und UNIQUE-Gleichheit (G9/M05, nur develop)

Der begrenzte SQL-Server-CTE-UPDATE/DELETE-Nachweis unterstützt nun **vier getrennte Vergleichsverträge** für integrierte `VARCHAR(n)`- und `NVARCHAR(n)`-Schlüssel mit fester Länge: das bisherige `Latin1_General_100_BIN2` (binär), `Latin1_General_100_CI_AS` (ohne Groß-/Kleinschreibung, mit Akzenten), `Latin1_General_100_CI_AI` (beides ignoriert) und `Latin1_General_100_CS_AS` (beides unterschieden). Quell-UNIQUE-Index, Zielvergleichsspalte und unabhängig nachgewiesene zweite JOIN-Tabelle müssen **an jeder Schlüsselposition dieselben nativen SQL-Typen, Längen und tatsächlichen Spaltenkollationen** verwenden. Ein Text-Snapshot allein autorisiert keine Änderung; geschlossene F#-Typen und echte Index- und Spaltenmetadaten bestimmen die Vergleichssemantik.

Reale SQL-Server-2022-Tests vergleichen **UNIQUE-Konflikte bei Varianten in Groß-/Kleinschreibung und Akzenten** mit dem Verhalten des gewöhnlichen `=`. Die begrenzten 1–3 CTE-Stufen, vollständigen AND-Schlüsselvergleiche, zusammengesetzten Text-/UUID-/Zahlenschlüssel, Vorschau→unabhängige Freigabe→Commit und `IsCurrent` in derselben Transaktion bleiben erforderlich. Für nullable UNIQUE-Quellschlüssel gilt weiterhin `ANSI_NULLS ON`. ProofIdentity steigt auf **v9**, wodurch alte Freigaben verfallen. Unterschiedliche Kollationen, explizite `COLLATE`-Überschreibungen, implizite VARCHAR/NVARCHAR-Umwandlungen, nicht nachgewiesene CS_AI/_SC/_UTF8, CHAR/MAX, gefilterte/deaktivierte Indizes und unvollständige Gleichheitsbedingungen bleiben gesperrt. Keine neuen MCP-Werkzeuge, Berechtigungen oder Rechte für die übrigen fünf Datenbanken.


### Nullable SQL-Server-UNIQUE-Schlüssel mit gewöhnlicher Gleichheit (G9/M05, nur develop)

Nullable Spalten in einem SQL-Server-Quellschlüssel sind nur dann zulässig, wenn **ein tatsächlich aktiver, ungefilterter physischer UNIQUE-Index das vollständige geordnete Tupel aus 1–2 Schlüsselspalten schützt**. Für die begrenzte CTE-`UPDATE`-/`DELETE`-Ausführung bleiben vollständige `AND`-/gewöhnliche `=`-Vergleiche mit dem Ziel sowie `ANSI_NULLS ON` auf der tatsächlichen Verbindung erforderlich (über `@@OPTIONS` geprüft). Sobald eine Quellkomponente NULL ist, ergibt der gewöhnliche Vergleich UNKNOWN und **passt zu keiner Zielzeile**. Dies berechtigt weder zu NULL-sicherer Gleichheit noch zu beliebigen Scans nullable Tabellen. Zusammengesetzte Zielschlüssel müssen weiterhin NOT NULL sein; das `VerifyLive` ohne nachgewiesene Zielgleichheit darf keine nullable Quelle bestätigen.

Der geschlossene F#-Beweis für NULL-Vergleiche bindet sämtliche UNIQUE-Indexpositionen, integrierte physische Schlüsseltypen, Quell-Nullbarkeit, einen unveränderlichen Metadaten-Digest und **v8 ProofIdentity**. Die tatsächliche Commit-Verbindung und Transaktion prüfen `ANSI_NULLS ON`, Index und Schema erneut unter gehaltenen Sperren. Gefilterte UNIQUE-Indizes (auch `WHERE key IS NOT NULL`), deaktivierte/nicht eindeutige Indizes, `OR`, `COALESCE`, berechnete Schlüssel, CAST, NULL-sichere Operatoren oder ein virtueller Catalog reichen nicht aus. Reale SQL-Server-2022-Tests prüfen nullable BIGINT-/DECIMAL-/UUID-/BIN2-VARCHAR-Tupel, 1–3 CTE-Stufen, UPDATE/DELETE, Vorschau und unabhängige Freigabe, nicht passende NULL-Werte sowie die Ablehnung nach Indexentzug. Andere fünf Datenbanken und MCP-Standardberechtigungen bleiben unverändert.


### Exakter Nachweis physischer BIN2-VARCHAR-/NVARCHAR-Schlüssel (G9/M04, nur develop)

Die Eindeutigkeitsprüfung für SQL-Server-CTE-`UPDATE`/`DELETE` unterstützt integrierte `VARCHAR(n)`- und `NVARCHAR(n)`-Schlüssel mit begrenzter Länge, **ausschließlich bei der tatsächlich hinterlegten Kollation `Latin1_General_100_BIN2`**. Quell-UNIQUE-Index, Zielvergleichsspalte und unabhängig bestätigter zweiter JOIN-Schlüssel müssen **an jeder Indexposition denselben nativen SQL-Typ, dieselbe Maximallänge und dieselbe Kollation** aufweisen. Bei `NVARCHAR` werden zunächst die Bytes aus `sys.columns.max_length` geprüft und dann in Zeichen umgerechnet. `MAX`, `CHAR`/`NCHAR`, unterschiedliche Längen, implizite Unicode-Umwandlungen, andere BIN2- oder sprachabhängige Kollationen, benutzerdefinierte Alias-Typen und nullable Quellschlüssel bleiben ausgeschlossen.

Der Host kennzeichnet echte Textspalten mit `SqlSchemaValueKind.Text`; **diese Snapshot-Kategorie alleine erteilt jedoch keine Ausführungsberechtigung**. Das geschlossene F#-Modell prüft reale Spaltenlänge und Kollation, integrierte Typidentität, sämtliche Positionen eines aktivierten ungefilterten UNIQUE-Index und die verpflichtenden gewöhnlichen Gleichheitsbedingungen des begrenzten CTE-/JOIN-Graphen. Preview→unabhängige Freigabe→Commit verlangen weiterhin die `IsCurrent`-Neubewertung unter gehaltenen Sperren in derselben Transaktion. ProofIdentity steigt auf v7 und macht alte Freigaben ungültig. Reale SQL-Server-2022-Tests decken gemischte Text-/UUID-/Zahlenschlüssel, UPDATE/DELETE, 1–3 CTE-Stufen, Selbst- und Tabellen-JOINs, Indexentzug und abweichende Kollation oder Länge ab. Andere fünf Datenbanksysteme, MCP-Tools und Standardberechtigungen bleiben unverändert.


### Zusätzliche Nichtschlüsselspalten in CTE-Projektionen (G8 / M03)

Die ein bis drei CTE-Stufen dürfen neben dem erforderlichen ein- oder zweispaltigen INT-Schlüssel auch **weitere direkt gelesene Quellspalten** projizieren (höchstens 32 Spalten je Stufe). Beispielsweise kann auf `SELECT k1 AS a, payload AS extra, k2 AS b` ein `SELECT a, extra, b` folgen. Jeder Schlüssel muss in jeder Stufe genau einmal vorkommen, die relative Reihenfolge des physischen eindeutigen Index bewahren und durch zwingende `AND`- und normale `=`-Vergleiche gebunden sein. Doppelte, berechnete oder umgewandelte Schlüssel, mehrdeutige Aliase, mehrere Quellen und zeilenvervielfachende JOINs bleiben ausgeschlossen. Physische Indexprüfung, Vorschau, Freigabe und erneute Prüfung in der Commit-Transaktion bleiben unverändert. Allgemeine JOINs oder weitere Datenbanken werden dadurch nicht freigeschaltet.

### Sichere JOINs mit genau einer abgeleiteten Zeile (G8 / M07, begrenzt)

Pro SQL-Server-CTE-Stufe ist nun **höchstens ein JOIN mit nachweislich nicht steigender Zeilenzahl** zulässig. Die JOIN-Quelle muss eine unabhängige abgeleitete Abfrage wie `SELECT 1 AS marker` ohne `FROM`, `WHERE`, `UNION`, Gruppierung oder weitere Zeilen sein. `CROSS JOIN (SELECT 1 AS marker) AS one` erhält die Kardinalität; `INNER JOIN` und `LEFT JOIN` mit einem literalen Vergleich `ON 1 = 1` können sie nicht vergrößern. Physischer eindeutiger INT-Schlüssel, direkte Schlüsselprojektion, Vorschau, Freigabe und erneute Transaktionsprüfung bleiben erforderlich. **Allein der obige Singleton-/Selbst-JOIN-Nachweis autorisiert keine andere physische Tabelle; der separate Nachweis beider eindeutiger Indexe weiter unten ermöglicht nur den ausdrücklich begrenzten Fall. JOINs mit anderen physischen Tabellen, APPLY, korrelierte Abfragen, mehrzeilige Quellen und allgemeine JOINs werden nicht freigeschaltet.**

Als zweite eng begrenzte Form ist ein **INNER-/LEFT-Selbst-JOIN derselben physischen Quelltabelle** unter zwei verschiedenen Aliasnamen möglich. Im ON-Prädikat müssen dabei **alle Komponenten des in der echten Datenbank bestätigten eindeutigen INT-Schlüssels** durch gewöhnliche Gleichheiten mit AND verknüpft werden. Der zweite Alias kann so pro Quellzeile höchstens eine Zeile liefern. Fehlende Schlüssel, ausschließlich OR-verknüpfte Vergleiche, berechnete/konvertierte Schlüssel und JOINs zu anderen Tabellen bleiben gesperrt.

### JOIN zwischen zwei physischen Tabellen mit unabhängig geprüften UNIQUE-Schlüsseln (M07)

Eine SQL-Server-CTE kann nun genau einen **INNER JOIN** oder **LEFT JOIN** mit einer zweiten, anderen physischen Tabelle ausführen. Beide Quelltabellen benötigen jeweils einen eigenständig am echten Datenbankkatalog bestätigten eindeutigen Schlüssel aus ein oder zwei nicht nullbaren `INT`-/`BIGINT`-Spalten; der Index muss aktiv und ungefiltert sein. Die `ON`-Bedingung muss alle Schlüsselspalten über erforderliche gewöhnliche Gleichheiten mit `AND` verbinden, wobei die physischen Typen je Position exakt übereinstimmen. Ein virtueller Katalog, implizite Umwandlung, unvollständige Schlüsselgleichheit oder gefilterter Index ist kein Nachweis. Beide Indexidentitäten werden an Plan und Freigabe gebunden und in der tatsächlichen Commit-Transaktion erneut geprüft; der Wegfall eines Nachweises nach der Vorschau verhindert den Commit. Eine dritte physische Quelle, Viele-zu-viele-JOINs, `RIGHT`-/`FULL JOIN`, Cross-Provider-Übersetzung und beliebige JOINs bleiben gesperrt.

### Vollständig schlüsselkorrelierte EXISTS-/NOT-EXISTS-Filter (M07, begrenzt)

Ein SQL-Server-UPDATE/DELETE mit CTE darf in der WHERE-Klausel der ersten CTE **EXISTS** (Semi-JOIN) oder **NOT EXISTS** (Anti-JOIN) verwenden, wenn die Unterabfrage **dieselbe bereits physisch geprüfte Quelltabelle** mit einem anderen Alias liest. Die Unterabfrage darf nur ein Literal projizieren und weder zusätzliche JOINs, Gruppierungen, Sortierungen noch Mengenoperationen enthalten. Alle ein oder zwei `INT`-/`BIGINT`-Komponenten des eindeutigen Schlüssels müssen über verpflichtende gewöhnliche `AND`-/`=`-Vergleiche korreliert sein; weitere direkte Vergleiche einer inneren Spalte mit einem Literal dürfen das Ergebnis einschränken. Der Filter kann Zeilen entfernen, aber nie vervielfachen. Physischer Indexnachweis, Vorschau, Freigabeidentität und erneute Transaktionsprüfung bleiben erforderlich. **Beliebige Unterabfragen, ungeprüfte andere Tabellen und allgemeine Anti-JOIN-Ausführungsrechte werden nicht freigeschaltet.**

### Exakte physische TINYINT- und SMALLINT-Schlüssel (G9/M04, nur develop)

Die physisch verifizierte CTE-`UPDATE`-/`DELETE`-Ausführung in SQL Server unterstützt jetzt neben `INT` und `BIGINT` auch die integrierten Typen `TINYINT` (vorzeichenlos, 8 Bit) und `SMALLINT` (vorzeichenbehaftet, 16 Bit). Bei einem physischen eindeutigen Schlüssel mit einer oder zwei Spalten müssen Quell-, Ziel- und unabhängig verifizierte JOIN-Schlüssel **an jeder Indexposition exakt denselben tatsächlichen SQL-Server-Typ** besitzen. Implizite Ganzzahlkonvertierung, benutzerdefinierte Alias-Typen oder ein virtueller Katalog liefern keinen Nachweis. Die begrenzte CTE-Schlüsselweitergabe, JOIN-Kardinalitätsprüfung, Vorschau betroffener Zeilen, separate Freigabe, unveränderlicher Plan-Fingerabdruck und erneute Indexprüfung in derselben Commit-Transaktion bleiben vorgeschrieben. SQL-Server-2022-Tests prüfen UPDATE/DELETE, gemischte Schlüsseltypen und Indexentzug. DECIMAL, UUID, nullbare eindeutige Schlüssel, beliebige JOINs und andere Datenbanken werden nicht freigeschaltet.


### Exakter Nachweis physischer UNIQUEIDENTIFIER-Schlüssel (G9/M04, nur develop)

Der physische Eindeutigkeitsnachweis für CTE-`UPDATE`/`DELETE` in SQL Server unterstützt nun auch **integrierte 128-Bit-`UNIQUEIDENTIFIER`-Schlüssel**. `Uuid` ist eine eigenständige Schemawert-Kategorie, **weder Numeric noch Text oder Binary**. Der Host liest echte `sys.tables`-, `sys.columns`- und `sys.types`-Metadaten für Quelle, Ziel und eine unabhängig geprüfte zweite JOIN-Quelle. Das geschlossene F#-Schlüsselmodell prüft den vollständigen UNIQUE-Index und die Übereinstimmung von deklariertem Snapshot-Typ mit dem physischen Typ. Eine implizite Konvertierung von `UNIQUEIDENTIFIER` in `INT`, `DECIMAL`, `VARCHAR` oder `BINARY(16)` liefert keine Ausführungsberechtigung.

Ein- oder zweiteilige Schlüssel können UUID mit exakt geprüften Ganzzahl- und Dezimaltypen kombinieren. Die bisherigen maximal drei begrenzten CTE-Stufen, nicht vervielfachenden JOINs, Änderungsvorschau, unabhängige Freigabe sowie erneute `IsCurrent`-Prüfung innerhalb der Commit-Transaktion bleiben zwingend. ProofIdentity steigt auf v6; ältere Freigaben sind nicht wiederverwendbar. Echte SQL-Server-2022-Tests umfassen UUID-UPDATE/DELETE, Primär- und UNIQUE-Index, automatische Prüfung, JOINs mit einer zweiten Tabelle, Indexentzug nach Vorschau und Typkonflikte. Weder MCP-Werkzeuge noch DML-Vorauswahl, beliebige JOIN-Rechte oder Berechtigungen für die anderen fünf Datenbanken werden erweitert.

### M09: begrenzte IN/OR-Quellzeilenprädikate (nur develop)

### M09: begrenzte NULL-Prüfung für native Quellzeilen (nur develop)

Für **SQLite, PostgreSQL, MySQL 8.4 InnoDB und SQL Server 2022** mit bereits verifizierten physischen Tabellen darf natives `INSERT SELECT` jetzt direkt `IS NULL` oder `IS NOT NULL` auf eine unqualifizierte Quellspalte anwenden. Keine neuen MCP-Tools, Treiber oder öffentlichen APIs; die vier Lese-Tools bleiben standardmäßig ausgewählt und DML bleibt deaktiviert.

### M10: SQL Server MERGE mit nativer Sperre des Zielschlüsselbereichs (nur develop)

Der bestehende F#-Compiler für SQL Server `MERGE` mit **genau einer Quellzeile** erzeugt jetzt `MERGE INTO dbo.target WITH (HOLDLOCK) AS t USING (VALUES (...)) AS s (...) ON ...`. Zugelassen sind nur eine explizite VALUES-Zeile, direkte Spaltenwerte, ein vollständiger Abgleich des durch reale Metadaten bestätigten PRIMARY-/UNIQUE-Schlüssels und die bereits modellierten begrenzten UPDATE-/DELETE-/INSERT-Aktionen. Die native serialisierbare Schlüsselbereichssperre gilt auch, wenn für den Quellschlüssel noch keine Zielzeile existiert; die Transaktionsverwaltung bleibt Aufgabe des Ausführenden.

Tests gegen einen echten SQL Server 2022 überprüfen Primär- oder zusammengesetzte eindeutige Schlüssel, UPDATE/INSERT/DELETE, die Isolation zusammengesetzter Schlüssel und das Blockieren konkurrierender Einfügungen in einen bisher nicht vorhandenen Schlüsselbereich während der MERGE-Transaktion. Nicht vorhandene oder nicht eindeutige Schlüssel liefern keinen Compiler-Nachweis. **Dies ist eine SqlCore-Compilerfähigkeit, keine MERGE-/Upsert-Ausführungsfreigabe im Host**: Die typisierte DML-Freigabe bleibt gesperrt, bis bestehende Zeilen, Änderungen und deren gesonderte Genehmigung sicher nachgewiesen sind. Andere Datenbanken, mehrzeilige/abfragebasierte MERGE-Quellen, datenbankübergreifende Übersetzungen und nicht attestierte Aktionen bleiben abgelehnt. Keine zusätzlichen MCP-Tools oder öffentlichen APIs; standardmäßig bleiben vier Lese-Tools ausgewählt und DML deaktiviert.

### M10: SQLite Host-Freigabe für einzeiliges `ON CONFLICT (PRIMARY KEY) DO NOTHING` (nur develop)

Der typisierte Host kann genau ein natives SQLite-`INSERT ... VALUES (...) ON CONFLICT (id) DO NOTHING` anzeigen, freigeben und ausführen. Voraussetzungen sind, dass `id` der **einzige tatsächlich erzwungene Primär-/Unique-Schlüssel** der physischen Tabelle ist, ein expliziter nicht-NULL-Integerliteral mit exakten 64 Bit vorliegt, die Richtlinie höchstens **1 betroffene Zeile** erlaubt und die eingebaute physische Schemaprüfung aktiv ist. Anders als bei der bisherigen Freigabe reiner INSERT-Werte wird der echte Schlüsselkonflikt vor der Freigabe geprüft: **1 einzufügende Zeile**, wenn der Schlüssel fehlt, oder **0 geänderte Zeilen**, wenn der Konflikt übersprungen wird. Dieses Ergebnis wird an den Freigabe-Fingerabdruck gebunden.

Beim Ausführen wird die einmalige Freigabe verbraucht. Innerhalb der SQLite-Schreibtransaktion werden Schema und Schlüssel erneut geprüft; anschließend wird genau das von F# kompilierte parametrisierte SQL ausgeführt und die tatsächliche Zeilenzahl verglichen. Geänderter Konfliktstatus, Index oder Schema führt zur Ablehnung oder zum Rollback und erfordert eine neue Vorschau. **DO UPDATE, fehlendes Konfliktziel, mehrere VALUES-Zeilen, RETURNING, andere/zusammengesetzte Schlüssel, zusätzliche UNIQUE-Keys, datenbankübergreifende Übersetzung und atomare Batches** bleiben gesperrt. Allgemeines Upsert und SQL Server MERGE werden nicht freigegeben; keine neuen MCP-Tools, und die standardmäßig ausgewählten vier Lese-Tools sowie deaktiviertes DML bleiben unverändert.

**Sicherheit bei Triggern:** Tabellen mit SQLite-Triggern sind von dieser Einzeilenfreigabe ausgeschlossen, weil zusätzliche Trigger-Schreibvorgänge nicht in der Änderungszahl der Hauptanweisung enthalten sind. Der Host setzt den integrierten SQLite-Provider voraus.

### M10: SQLite-Freigabe mit eindeutigem Einzelschlüssel (nur develop)

Die bestehende Vorschau, Genehmigung und Ausführung von `ON CONFLICT (id) DO NOTHING` für **eine Zeile** lässt jetzt auch einen tatsächlich erzwungenen, einfachen **UNIQUE-Schlüssel mit einer Spalte** zu, wenn `id` kein Primärschlüssel ist. Dieser Schlüssel muss die **einzige** erzwungene Eindeutigkeitsbedingung bzw. der einzige eindeutige Index der Tabelle sein und genau zur Konfliktspalte passen; der eingefügte Schlüsselwert muss ein explizites, nicht-NULL-Ganzzahlliteral mit exakt 64 Bit sein. Der integrierte SQLite-Anbieter überprüft die echte Datenbank. Die Vorschau bindet **1 einzufügende** oder **0 zu überspringende Zeilen**; bei der Ausführung werden Schema und Schlüssel in derselben Schreibtransaktion erneut geprüft. Ein entfernter oder geänderter Index macht die Genehmigung ungültig.

**Weiterhin gesperrt:** mehrere oder partielle/ausdrucksbasierte UNIQUE-Indizes, zusammengesetzte Schlüssel, nicht eindeutige Indizes, Konflikt-UPDATE, fehlendes Konfliktziel, mehrere INSERT-Zeilen, RETURNING, Trigger, datenbankübergreifende Ausführung und atomare Batches. Keine allgemeine Upsert-Freigabe; vier Lese-Tools und deaktiviertes DML bleiben die Vorgabe.

### M10: PostgreSQL-Freigabe für einzeiliges `ON CONFLICT DO NOTHING` (nur develop)

Der Host kann genau eine PostgreSQL-Anweisung `INSERT ... VALUES (...) ON CONFLICT (id) DO NOTHING` voranzeigen, genehmigen und ausführen. Die Konfliktspalte muss in der echten Tabelle als NOT NULL und INT2/INT4/INT8 definiert sein und durch den **einzigen einfachen, sofort geprüften (NOT DEFERRABLE) einspaltigen PRIMARY-/UNIQUE-Schlüssel** abgesichert werden. Der Schlüsselwert muss ein explizites, nicht-NULL-Ganzzahlliteral mit exakten 64 Bit sein. Der integrierte PostgreSQL-Anbieter prüft die physische Tabelle sowie Spalten-, Index- und Einschränkungsdefinitionen vollständig; Tabellen mit Triggern, Umschreibregeln, Partitionierung, Vererbung oder Sicherheit auf Zeilenebene werden abgelehnt. Die Vorschau bindet **1 einzufügende oder 0 zu überspringende Zeilen** an eine einmalige Genehmigung. Bei der Ausführung bleibt eine Tabellensperre `SHARE ROW EXCLUSIVE NOWAIT` bis zum Transaktionsende bestehen, damit andere Schreibvorgänge die erneute Prüfung von Schema und Schlüssel nicht stören. Ein entfernter Index oder geänderter Konfliktzustand führt zur Ablehnung. Die starke Sperre begrenzt bewusst parallele Schreibvorgänge.

**Weiterhin gesperrt:** DO UPDATE, RETURNING, mehrere Zeilen, fehlendes Konfliktziel, mehrere UNIQUE-Schlüssel, partielle/ausdrucksbasierte/zusammengesetzte Schlüssel, NULL-/Text-/UUID-Schlüssel, nicht geprüfte Anbieter, Datenbankübergreifendes, Trigger und atomare Batches. Keine allgemeine Upsert-Freigabe, kein weiteres MCP-Tool; vier Lese-Tools und deaktiviertes DML bleiben der Standard.

### M11: PostgreSQL-Konflikt-UPDATE mit Vorher-/Nachher-Genehmigung (nur develop)

Der Typed Host lässt ein streng begrenztes PostgreSQL `INSERT INTO users (id, name) VALUES (7, 'new') ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name` zu. Ziel ist eine echte permanente gewöhnliche Tabelle mit **genau zwei Spalten**: einem NOT NULL BIGINT-Einzelschlüssel PRIMARY/UNIQUE und einer NOT NULL TEXT-Wertespalte. Es muss der **einzige einfache sofort wirksame (NOT DEFERRABLE) Eindeutigkeitsschlüssel** sein; zusätzliche Indizes/Spalten, Standardwerte, CHECK-/Fremdschlüsselbedingungen, Nutzer-Trigger, Umschreibregeln, Partitionierung/Vererbung und Sicherheit auf Zeilenebene sind unzulässig. Der integrierte PostgreSQL-Anbieter prüft die physische Definition; ein virtueller Catalog berechtigt nicht zur Ausführung.

Die Vorschau zeigt **eine betroffene Zeile**: ohne Konflikt `INSERT` mit leerem Vorher-Wert, bei Konflikt `UPDATE` mit tatsächlichem altem und vorgeschlagenem neuem Wert. Der vollständige Fingerabdruck der alten Zeile und die neuen Werte werden an eine einmalige Genehmigung gebunden. Beim Commit bleibt die Tabellensperre `SHARE ROW EXCLUSIVE NOWAIT` bis Transaktionsende bestehen; Schema, Index und alte Werte werden vor Ausführung des F#-kompilierten SQL erneut geprüft. Veränderte Konflikte, alte Werte oder Indizes brechen den Vorgang ab. Diese starke Sperre begrenzt bewusst parallele Schreibvorgänge.

**Weiterhin gesperrt:** allgemeines UPSERT, Änderung des Schlüssels, beliebige SET-Ausdrücke, UPDATE WHERE, mehrere Spalten/Zeilen, RETURNING, NULL-/Nicht-TEXT-Werte, Nebenwirkungen auf andere Tabellen, andere Anbieter und atomare DML-Batches. Vier Lese-MCP-Tools und deaktiviertes DML bleiben voreingestellt.
