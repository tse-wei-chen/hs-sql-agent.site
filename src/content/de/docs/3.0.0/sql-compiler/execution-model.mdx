## Begrenzte Kompilierung und Schemanachweise

Die Kompilierung weist Eingaben über 4,194,304 UTF-16-Einheiten, 131,072 lexikalischen Token ohne End, 8,192 Gruppierungsebenen oder 65,536 AST-Knoten ab. Iterative AST-Traversierung und begrenzte Ausgabe bewahren Parameterreihenfolge und Ablehnung bei unzureichendem Sicherheitsnachweis für alle sechs Provider. Beliebige SQL-Tiefe wird nicht garantiert.

Die Budgets betragen 8,000,000 Arbeitseinheiten je Phase, 32,000,000 je Kompilierung, 30 Sekunden je Phase, 90 Sekunden insgesamt und 536,870,912 kumulativ allokierte verwaltete Bytes je Phase. Dies sind Compilerbudgets, keine DB-Abfragezeitlimits oder Prozessspeichergrenzen. Typisierte Ressourcendiagnosen melden Überschreitungen.

Ein optionaler unveränderlicher Schemasnapshot löst Tabellen-/Spaltennamen und nachweisbare Typfamilien auf, einschließlich geordneter CTE-/abgeleiteter Projektionen. Sein Digest wird an den Planfingerabdruck gebunden. Das ist kein vollständiger DB-Typprüfer. DML mit Schemanachweis benötigt eine aktuelle Frischeprüfung; fehlende oder geänderte Nachweise führen zur Ablehnung. Standardmäßig wird kein Snapshot erfasst. `AddHsSqlAgentNativeDmlSchemaFreshness()` aktiviert die optionale native Unterstützung.

hs-sql-agent behandelt generiertes SQL nicht als vertrauenswürdigen Befehl. Die Ausführungsgrenze ist um Parsing, Validierung, Fähigkeitsprüfungen, Zugriffsrichtlinien und datenbankspezifische Kompilierung aufgebaut.

## Abfragepfad

Auf hoher Ebene durchläuft eine Abfrage diese Schritte:

1. MCP-Schlüssel authentifizieren und seinen Datenbank-, Tabellen-, Werkzeug- und Ausführungsumfang anwenden.
2. Unterstütztes SQL in eine strukturierte Definition / AST parsen.
3. Die Anweisung und ihre unterstützte Quellsemantik validieren.
4. Die Zielfähigkeiten prüfen, die zum Erhalt dieser Semantik erforderlich sind.
5. SQL für die konfigurierte Datenbank kompilieren und ausgeben.
6. Innerhalb der konfigurierten Laufzeitgrenzen ausführen.

Die Implementierung des SQL-Compilers enthält explizite Stufen für Quellvalidierung und Zielfähigkeiten. Nicht unterstützte Syntax oder eine Fähigkeit, deren Gleichwertigkeit nicht nachgewiesen werden kann, wird abgelehnt, statt stillschweigend durch eine oberflächlich ähnliche Konstruktion ersetzt zu werden.

## Warum bei Unsicherheit ablehnen?

Datenbankübergreifendes SQL enthält viele Konstruktionen, die gleich aussehen, sich aber bei `NULL`, Typregeln, Operatorsemantik, Pagination, Bezeichnern, Funktionen oder DML-Verhalten unterscheiden.

Für eine KI-nahe Ausführungsoberfläche ist ein Umschreiben nach dem Prinzip „best effort“ gefährlich: Eine Anweisung kann syntaktisch gültig bleiben und trotzdem ihre Bedeutung ändern. hs-sql-agent bevorzugt deshalb eine sichtbare Ablehnung gegenüber einer stillen semantischen Abschwächung. Dieses Verhalten entspricht dem Fail-Closed-Prinzip.

## Datenbankspezifische Ausgabe

Die öffentliche MCP-Schnittstelle ist gemeinsam, das endgültige SQL jedoch datenbankspezifisch. Derzeit werden folgende Datenbanken unterstützt:

- PostgreSQL
- MySQL
- SQL Server
- Oracle
- SQLite
- Firebird

Der unterstützte Umfang ist absichtlich begrenzt. Dass eine Datenbank unterstützt wird, bedeutet nicht, dass jede von ihr angebotene SQL-Syntax akzeptiert wird; einzelne Compiler-Fähigkeiten werden erst erweitert, wenn ihre Semantik repräsentiert und validiert werden kann.

## Native Fensterrahmen mit GROUPS

Für PostgreSQL ab Version 11 und SQLite ab 3.28 kann der Compiler Fensterrahmen wie `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW)` erstellen. `GROUPS` zählt Gruppen von Zeilen mit gleichem Sortierschlüssel, nicht einzelne Zeilen (`ROWS`) oder Wertebereiche (`RANGE`). Erforderlich ist ein ausdrückliches `ORDER BY` im Fenster. Ungültige Grenzen und ausdrücklich deklarierte ältere Datenbankversionen werden abgewiesen; der Compiler ersetzt `GROUPS` niemals stillschweigend durch eine andere Einheit. Für MySQL, SQL Server, Oracle und Firebird ist diese Funktion nicht freigegeben. Die tatsächliche Serverversion muss der Host vor der Ausführung prüfen.

## EXCLUDE: native Zugehörigkeit zum Fensterrahmen

PostgreSQL ab Version 11 und SQLite ab 3.28 unterstützen vier ausdrückliche Ausschlussformen nach einem `ROWS`-, `RANGE`- oder `GROUPS`-Rahmen. `EXCLUDE CURRENT ROW` entfernt nur die aktuelle Zeile; `EXCLUDE GROUP` entfernt sie samt allen Zeilen mit gleichem Sortierschlüssel; `EXCLUDE TIES` behält die aktuelle Zeile und entfernt nur ihre gleichsortierten Nachbarn; `EXCLUDE NO OTHERS` schließt keine Zeile aus. Beispiel: `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW EXCLUDE TIES)`. Auch bei `ROWS` berücksichtigt der Ausschluss gleichsortierte Zeilen. Der F#-Compiler und `WindowFrameDefinition.Exclusion` erhalten diese Bedeutung ohne stillschweigende Umschreibung. Ältere ausdrücklich deklarierte Versionen und die anderen vier Datenbankanbieter werden abgewiesen. Der Host muss die tatsächliche Serverversion vor der Ausführung prüfen.

## SQL Server: numerische Offsets in RANGE-Fensterrahmen

Die T-SQL-Syntax von SQL Server erlaubt in einem `RANGE`-Fensterrahmen keine numerischen `PRECEDING`- oder `FOLLOWING`-Offsets. `RANGE BETWEEN 1 PRECEDING AND CURRENT ROW` wird daher **als ungültige SQL-Server-Quellsyntax** zurückgewiesen, selbst wenn PostgreSQL oder SQLite als Ziel ausgewählt wurde. Gültige `ROWS`-Offsets und `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` bleiben möglich. Die nativen numerischen `RANGE`-Semantiken von PostgreSQL und SQLite bleiben unverändert. Der Compiler prüft die Gültigkeit des Quelldialekts getrennt von den Fähigkeiten des Zielsystems; die Zielunterstützung ist kein Nachweis für gültige Quellsyntax.

## Begrenztes bedingtes COUNT für MySQL und SQL Server

Eine Abfrage aus dem PostgreSQL-Quelldialekt wie `SELECT COUNT(*) FILTER (WHERE status = 1) FROM orders` lässt sich jetzt für MySQL oder SQL Server in eine nachgewiesen äquivalente bedingte Aggregation übersetzen. MySQL verwendet `COUNT(CASE WHEN ... THEN 1 END)`, SQL Server `COUNT_BIG(CASE WHEN ... THEN 1 END)`, um den 64-Bit-Zählbereich zu erhalten. Auch `COUNT(direkte_spalte)` wird unterstützt; NULL-Werte, leere Treffer und die Zählung innerhalb von Fensterrahmen behalten ihre Bedeutung.

**Das ist keine allgemeine Unterstützung für FILTER.** Zugelassen sind nur nicht qualifiziertes `COUNT(*)`, direktes lokales Spalten-COUNT und `COUNT(DISTINCT direkte_spalte)` ohne Fensterfunktion sowie nachweisbar einfache Spalten-/Konstantenbedingungen. `SUM`, berechnete Argumente, Unterabfragen, volatile Funktionen und äußere Bezüge bleiben gesperrt. `FILTER` bleibt als rohe MySQL-/SQL-Server-Quellsyntax ungültig. Die Übersetzung gilt nur für einen zulässigen Quelldialekt wie PostgreSQL. SqlCore führt kein SQL aus und gewährt keine Datenbankrechte.

## Bedingtes DISTINCT COUNT: eindeutige Werte gezielt zählen

`COUNT(DISTINCT amount) FILTER (WHERE status = 1)` aus gültiger PostgreSQL-Quellsyntax wird für MySQL als `COUNT(DISTINCT CASE WHEN status = 1 THEN amount END)` und für SQL Server als `COUNT_BIG(DISTINCT CASE WHEN status = 1 THEN amount END)` ausgegeben. Gleiche Werte zählen einmal; NULL und Zeilen mit falscher oder unbekannter Bedingung zählen nicht. Für eine leere Treffermenge ergibt sich null als Zahl, also **0**. Die Semantik für gruppierte und globale Ganzzahlwerte wurde auf echten PostgreSQL-16-, MySQL-8.4- und SQL-Server-2022-Instanzen getestet.

Erlaubt sind genau ein direktes lokales DISTINCT-Spaltenargument und ein begrenzt nachweisbares Prädikat. Berechnete oder mehrere DISTINCT-Argumente, Unterabfragen, volatile Funktionen und äußere Bezüge werden abgelehnt. **DISTINCT-Fensteraggregate mit `OVER (...)` bleiben verboten**, weil MySQL und SQL Server diese Syntax nicht unterstützen. `FILTER` ist weiterhin keine gültige rohe MySQL-/SQL-Server-Quellsyntax. Die Ganzzahltests belegen keine allgemeine Äquivalenz von Zeichenkettensortierungen oder Typumwandlungen zwischen Datenbanken. Es werden weder SQL ausgeführt noch Rechte erteilt.

## LAG und LEAD mit IGNORE NULLS für SQL Server und Oracle

SQL Server ab 2022 CU4 (16.0.4035.4) und Oracle ab 12.1 erhalten `LAG(amount) IGNORE NULLS OVER (PARTITION BY grp ORDER BY id)` sowie die entsprechende `LEAD`-Syntax unverändert. `IGNORE NULLS` überspringt NULL-Eingabewerte bei der Suche nach dem vorherigen oder nächsten Wert. Explizites `RESPECT NULLS` bewahrt die native Berücksichtigung von NULL. Der Zusatz steht **zwischen Funktionsaufruf und OVER**, nicht im Fensterrahmen. F# modelliert die NULL-Behandlung als typisierten Wert; sie wird weder ausgelassen noch stillschweigend umgedeutet.

Explizites `RESPECT NULLS` ist schon ab SQL Server 2022 RTM zulässig. Für `IGNORE NULLS` ist wegen eines von Microsoft in CU4 behobenen LAG/LEAD-Ergebnisfehlers jedoch ein nachgewiesener CU4-Build nötig; ein Profil mit bloß `16.0` genügt nicht.

Quell- und Zielseite benötigen ausdrücklich deklarierte `ServerVersion`-Profile. Der Host muss vor der Ausführung weiterhin die tatsächliche Datenbankversion prüfen. Für PostgreSQL, MySQL, SQLite und Firebird bleiben diese expliziten Zusätze unzulässig. Andere Fensterfunktionen, doppelte oder ungültige Zusätze sowie fehlendes `OVER` werden abgelehnt. Bestehende `LAG/LEAD`-Abfragen ohne Zusatz bleiben unverändert. `WindowSpec.NullTreatment` und `WindowDefinition.NullTreatment` durchlaufen dieselbe Prüfung; die Semantik wurde anhand tatsächlicher SQL-Server- und Oracle-Ergebniszeilen verglichen. Der Compiler führt keine SQL-Befehle aus und vergibt keine Berechtigungen.

## FIRST_VALUE und LAST_VALUE mit expliziter NULL-Behandlung

SQL Server ab 2022 und Oracle ab 12.1 unterstützen `IGNORE NULLS` und `RESPECT NULLS` für `FIRST_VALUE` und `LAST_VALUE` direkt vor `OVER`. Beispiel: `LAST_VALUE(amount) IGNORE NULLS OVER (PARTITION BY grp ORDER BY id ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)` berücksichtigt **die ganze Partition** statt des häufig bis zur aktuellen Zeile begrenzten Standardfensters. `IGNORE NULLS` liefert den ersten bzw. letzten Wert ohne NULL; `RESPECT NULLS` berücksichtigt NULL.

Quelle und Ziel benötigen passende explizite `ServerVersion`-Profile (SQL Server 16.0+ bzw. Oracle 12.1+). Die SQL-Server-2022-CU4-Korrektur gilt **speziell für LAG/LEAD IGNORE NULLS**, nicht für FIRST/LAST; die Fähigkeiten werden getrennt geprüft. Die vier anderen Datenbanken, andere Fensterfunktionen und ungültige Zusätze bleiben abgelehnt. Strukturierte C#-DTOs nutzen dieselbe typisierte F#-Prüfung und native SQL-Ausgabe. Der Compiler erteilt keine Berechtigung und führt kein SQL aus.

Eine Übersetzung zwischen SQL Server und Oracle wird weiterhin abgelehnt: Die Gleichwertigkeit der standardmäßigen NULL-Sortierung und Fensterrahmen ist nicht nachgewiesen.

## PostgreSQL-Abfragen in schreibgeschützten Transaktionen (3.1)

Ein PostgreSQL-`SELECT` ist nicht zwangsläufig schreibfrei: `VOLATILE`- oder benutzerdefinierte Funktionen können echte Daten verändern. Nach Kompilierung und Berechtigungsprüfung von `execute_query_sql` führt der Host den kompilierten Befehl **in einer ausdrücklich auf `READ ONLY` gesetzten PostgreSQL-Transaktion auf derselben geprüften Verbindung** aus. Nach dem vollständigen Einlesen der Ergebnisse wird die Transaktion zurückgerollt. Der F#-Compiler SqlCore stellt weiterhin keine Datenbankverbindung her.

Ein Test mit PostgreSQL 16 zeigte, dass vor der Korrektur ein zulässiges `SELECT` über eine benutzerdefinierte Funktion eine Tabellenzeile ändern konnte. Weitere reale Tests prüfen 32 Angriffe mit angehängten Anweisungen, fünf Umgehungen der Tabellenrechte, Sequenzänderungen, korrekt parametrisierte Werte sowie gültige OR-/CTE-Abfragen. Abgelehnte Anfragen dürfen weder Ergebniszeilen liefern noch den Datenbankzustand verändern.

Ein zweiter RED-Test auf PostgreSQL 16 zeigte, dass `pg_catalog.query_to_xml` auch innerhalb einer `READ ONLY`-Transaktion Daten aus einer nicht freigegebenen Tabelle lesen kann. Bei einer nicht leeren Tabellen-Freigabeliste lehnt die F#-Abfrage-Richtlinie daher nicht nachgewiesene benutzerdefinierte oder native Funktionen ab und erlaubt nur einen begrenzten Satz geprüfter `pg_catalog`-Funktionen. Zugelassene Aufrufe werden ausdrücklich mit `pg_catalog` qualifiziert, um das Überschreiben von Funktionsnamen über `search_path` zu verhindern. Gebräuchliche sichere Funktionen wie `LOWER` und `COUNT` bleiben verfügbar. Diese zusätzliche Prüfung ersetzt weder den Schreibschutz noch minimale Datenbankberechtigungen.

Die Absicherung gilt **derzeit ausschließlich für PostgreSQL-Abfragen**. Sie verleiht keine DML-/DDL-Rechte und belegt keinen entsprechenden Schutz für die anderen fünf Datenbankanbieter. Externe Nebenwirkungen wie Advisory Locks werden nicht vollständig isoliert; minimale Berechtigungen und Ausführungslimits bleiben erforderlich.
