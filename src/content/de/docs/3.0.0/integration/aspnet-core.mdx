## Erforderlicher Schutz von Geheimnissen

Konfigurieren Sie vor dem Docker-Start oder der Runtime-Registrierung drei unabhängige, zufällige 32-Byte-Geheimnisse in Base64. Verwenden Sie auf allen Knoten dieselben Schlüssel und behalten Sie sie nach Neustarts bei. `HMAC_KEY` und `JWT_KEY` bleiben getrennte Signaturgeheimnisse. Führen Sie `openssl rand -base64 32` dreimal separat aus.

| Docker-Variable | ASP.NET-Core-Konfiguration |
| --- | --- |
| `DB_ENCRYPTION_KEY` | `SecretProtection:DatabasePasswords:Keys:db-1` |
| `DML_ENCRYPTION_KEY` | `SecretProtection:DmlPayloads:Keys:dml-1` |
| `DML_FINGERPRINT_KEY` | `SecretProtection:DmlFingerprintKey` |

Setzen Sie `SecretProtection:DatabasePasswords:ActiveKeyId` auf `db-1` und `SecretProtection:DmlPayloads:ActiveKeyId` auf `dml-1`. Fehlende, ungültige oder mehrfach verwendete Schlüssel verhindern den Start. Die Platzhalter in Beispielen sind absichtlich ungültig.

`HsSqlAgent.Hosting` bindet `SecretProtection` automatisch. Modulare Hosts müssen die Bindung ausdrücklich konfigurieren:

```csharp
hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
```

Geben Sie für neue Bootstrap-MCP-Schlüssel `Bootstrap:Databases:*:McpKeys:*:Key` ausdrücklich an. Beim Start werden keine Schlüssel mehr erzeugt oder protokolliert. Bestehende verschlüsselte DB-Passwörter müssen erneut eingegeben werden. Lesen Sie vor Änderungen an bestehenden Installationen den [Upgrade-Leitfaden](/de/docs/reference/upgrade-guide).

Mehrere Module dürfen `AddHsSqlAgentCore()` für dieselbe `IServiceCollection` aufrufen. Die Konfiguration jeder Fähigkeit wird nur bei der ersten Registrierung akzeptiert; spätere Überschreibungen schlagen fehl. Getrennte Service-Collections bleiben isoliert.

Für ASP.NET-Core-Anwendungen gibt es zwei NuGet-Einstiegspunkte. Entscheidend ist, welche Grenzen die Hostanwendung selbst kontrollieren soll.

| Ziel | Paket | Verantwortungsgrenze |
| --- | --- | --- |
| Vollständiges Produkt einbetten | `HsSqlAgent.Hosting` | HsSqlAgent verwaltet Standard-Runtime, Admin Store, integrierte Identität, MCP, Admin API/UI, Telemetrie, Fehlerbehandlung und Auswahl des Freigabe-Providers. |
| Eigene Integration aufbauen | `HsSqlAgent.Server` | Die Anwendung wählt Funktionen aus und kann Authentifizierung, Autorisierung, UI, Middleware-Reihenfolge, Telemetrie oder Freigabe-Provider selbst behalten. |

Soll hs-sql-agent als eigenständiger Dienst statt innerhalb eines .NET-Hosts laufen, verwenden Sie das offizielle Docker-Image.

## Vollständiges Produkt mit HsSqlAgent.Hosting einbetten

Installieren Sie das vollständig vorkonfigurierte Paket:

```bash
dotnet add package HsSqlAgent.Hosting
```

Registrieren und aktivieren Sie den Standard-Host:

```csharp
using HsSqlAgent.Hosting;

var builder = WebApplication.CreateBuilder(args);
builder.AddHsSqlAgentStandardHost();

var app = builder.Build();
app.UseHsSqlAgentStandardHost();
await app.RunAsync();
```

Dies ist dieselbe offizielle Funktionskomposition und derselbe Konfigurationsvertrag wie beim ToolBox-/Docker-Host. URL-Binding und Logging bleiben normale Aufgaben des ASP.NET-Core-Hosts.

`HsSqlAgent.Hosting` enthält die Standard-Runtime aus `HsSqlAgent.Server` sowie den offiziellen Adapter `HsSqlAgent.Approvals.Webhook`. Dynamisches Laden von NuGet-Paketen oder DLL-Plugins wird nicht eingeführt.

### DML-Freigabe-Provider wählen

MCP Elicitation bleibt der offizielle Standard:

```json
{
  "DmlApproval": {
    "Provider": "McpElicitation"
  }
}
```

Für den offiziellen generischen Webhook-Adapter:

```json
{
  "DmlApproval": {
    "Provider": "Webhook",
    "Webhook": {
      "Endpoint": "https://approval.example.com/hssqlagent/requests",
      "CallbackUrl": "https://sql-agent.example.com/api/hs-sql-agent/approvals/webhook",
      "SigningSecret": "replace-with-a-unique-secret-at-least-32-bytes"
    }
  }
}
```

Umgebungsvariablen folgen der normalen ASP.NET-Core-Konvention, zum Beispiel `DmlApproval__Provider=Webhook`. Ein unbekannter Providername lässt den Start fehlschlagen.

Für einen eigenen `IDmlApprovalProvider` verwenden Sie `HsSqlAgent.Server` und registrieren ihn per Dependency Injection. Das Freigabesystem erhält keine Befugnis, beliebiges SQL auszuführen: HsSqlAgent behält Validierung, Bindung des Approval-Fingerprints, erneute Prüfung des aktuellen Zustands und den endgültigen Commit.

## Eigene Integration mit HsSqlAgent.Server aufbauen

Installieren Sie das modulare Paket:

```bash
dotnet add package HsSqlAgent.Server
```

Eine bestehende Anwendung kann ihre Authentifizierung und Autorisierung behalten und nur die benötigten HsSqlAgent-Funktionen hinzufügen:

```csharp
var hs = builder.Services.AddHsSqlAgentCore();

hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
hs.AddHsSqlAgentAdminStore(options =>
{
    options.Provider = "Postgres";
    options.ConnectionString =
        builder.Configuration.GetConnectionString("HsSqlAgent")!;
});
hs.AddHsSqlAgentHostAuthorization("SqlAgentAdmin");
hs.AddHsSqlAgentAdminApi();
```

Die ASP.NET-Core-Pipeline bleibt beim Host:

```csharp
var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();
app.UseHsSqlAgentAdminApi();
app.MapControllers();

app.Run();
```

Im Host-Autorisierungsmodus darf `AddHsSqlAgentBuiltInAuth()` nicht aufgerufen werden. HsSqlAgent verwendet den authentifizierten `HttpContext.User`, veröffentlicht keine integrierten Identitätscontroller und installiert kein HsSqlAgent-Identitätsschema.

Canonical Permissions wie `/runtime/db-management.edit` und `/auth/role.view` sind stabile Autorisierungsressourcen und keine URL-Routen. Eine Host-Policy kann sie in das eigene Berechtigungsmodell abbilden.

### MCP nur bei Bedarf hinzufügen

MCP bleibt eine eigene Sicherheitsgrenze für Maschinenzugriff:

```csharp
hs.AddHsSqlAgentMcp(options =>
{
    options.PublicEndpoint = "https://example.com/mcp";
    options.HmacSecretKey = builder.Configuration["HMAC_KEY"]!; // >= 32 bytes
});
```

Nach dem Erstellen der Anwendung wird MCP gemappt:

```csharp
app.UseHsSqlAgentMcp();
```

MCP-Schlüssel, Tool- und Tabellenumfang, Rate Limits und HMAC-Prüfung bleiben unabhängig von der menschlichen/Admin-Autorisierung.

### Integrierte Identität nur bei Bedarf verwenden

Soll der Host das HsSqlAgent-eigene JWT/member/role-Modell verwenden, wählen Sie die integrierte Authentifizierung anstelle der Host-Autorisierung:

```csharp
hs.AddHsSqlAgentBuiltInAuth(options =>
{
    options.Jwt.SecretKey = builder.Configuration["JWT_KEY"]!; // >= 32 bytes
});
```

Integrierte Identität und Host-Autorisierung schließen sich gegenseitig aus. Bei einem modularen Host kann auch die integrierte Admin UI entfallen.

## Zuständigkeit der Funktionen

| Funktion | Zuständigkeit |
| --- | --- |
| `AddHsSqlAgentRuntime()` | Runtime, Operabilität, Koordination, SQL-Parallelität und Persistenz von DML-Freigaben |
| `AddHsSqlAgentAdminStore()` | Admin-Datenbankprovider und Verbindungszeichenfolge |
| `AddHsSqlAgentBuiltInAuth()` | JWT, Passwort-Reset/SMTP, Unternehmensidentität/OIDC |
| `AddHsSqlAgentHostAuthorization()` | Delegation an eine bestehende ASP.NET-Core-Autorisierungs-Policy |
| `AddHsSqlAgentMcp()` | Öffentlicher MCP-Endpunkt und HMAC-Secret für MCP-Schlüssel |
| `AddHsSqlAgentAdminApi()` | Admin-Controller und Validierungs-/Fehlerabbildung |
| `AddHsSqlAgentTelemetry()` | Prometheus- und OTLP-Einstellungen |

Nicht ausgewählte Funktionen weisen ihre Optionen weder zu noch validieren sie.

## Aktuelle HTTP-Pfade

| Oberfläche | Pfad |
| --- | --- |
| MCP-Endpunkt | `/mcp` |
| Admin-API-Präfix | `/api` |
| Admin UI | `/` |

Beliebiges Verschieben dieser Pfade wird nicht als unterstützt beworben, solange Routing, Frontend-Basispfade/Assets, Callbacks und Sicherheitsgrenzen nicht gemeinsam verschoben werden können.

## Kompatibilitäts-API

Bestehende Nutzer können `AddHsSqlAgent()` und `UseHsSqlAgent()` weiter verwenden. Für neue Integrationen wird der Standard-Einstieg über `HsSqlAgent.Hosting` oder `AddHsSqlAgentCore()` mit expliziter Funktionsregistrierung empfohlen.

## G5: MySQL-8.4-Schemaänderungen (nur nach ausdrücklicher Freigabe)

**Atomare InnoDB-DDL ist keine durch die Anwendung rücknehmbare Transaktion.** Ein reguläres CREATE TABLE löst einen impliziten COMMIT aus und lässt sich nicht durch ROLLBACK rückgängig machen. Das vorhandene Werkzeug execute_ddl_sql bleibt standardmäßig verborgen und gesperrt. Erforderlich sind die gesonderte MySQL-Aktivierung, die ausdrückliche Berechtigung des MCP-Zugriffsschlüssels und eine unabhängige DDL-Freigabe.

Zugelassen ist zunächst nur ein einzelnes CREATE TABLE ohne Datenbankpräfix mit 1 bis 16 einfachen vorzeichenbehafteten INT-Spalten. Temporäre Tabellen, Tabellen aus Abfragen, Vorgabewerte, Constraints, ALTER, INDEX, DROP und mehrere Anweisungen bleiben gesperrt. Die Vorschau liest nur echte Metadaten. Vor der Ausführung prüft eine neue Verbindung die MySQL-8.4-Serveridentität, die zugelassene Datenbank, Groß-/Kleinschreibung, InnoDB und das Fehlen des Zielobjekts. Anschließend wird ausschließlich die von SqlCore kompilierte SQL-Anweisung einmal ausgeführt und das tatsächliche Spaltenschema geprüft.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentMySqlDdl(new MySqlDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedDatabases = new HashSet<string>(StringComparer.Ordinal) { "app_database" },
    PolicyRevision = "mysql84-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
```

Die Sitzungssperre koordiniert ausschließlich Anforderungen dieses Dienstes; sie **sperrt keine fremden DDL-Clients**. Ist das Ergebnis nach Ausführungsbeginn nicht mehr nachweisbar, lautet der Zustand outcome_unknown. Nicht automatisch wiederholen, sondern zuerst den Datenbankzustand abgleichen. Eine DML-Freigabe berechtigt niemals zu DDL. Die vier vorausgewählten lesenden Werkzeuge und die nicht ausgewählten DML-/DDL-Werkzeuge bleiben unverändert.

## G5: Oracle-26ai-Schemaänderungen (nur nach ausdrücklicher Freigabe)

Oracle führt **vor und nach jeder DDL-Anweisung einen impliziten COMMIT** aus. Eine erfolgreich angelegte Tabelle lässt sich selbst bei einem späteren Fehler nicht durch ein ROLLBACK der Anwendung entfernen. Das vorhandene Werkzeug `execute_ddl_sql` bleibt standardmäßig verborgen. Erforderlich sind eine gesonderte Oracle-Aktivierung, eine ausdrückliche MCP-Schlüsselberechtigung und eine unabhängige DDL-Freigabe.

Ausführbar ist ausschließlich ein einzelnes CREATE TABLE **im eigenen Schema ohne Schemapräfix**, mit 1 bis 16 einfachen INTEGER-Spalten. Constraints, Standardwerte, ALTER, INDEX, DROP, CREATE TABLE AS SELECT und Mehrfachanweisungen werden abgelehnt.

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentOracleDdl(new OracleDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedPdbNames = new HashSet<string>(StringComparer.Ordinal) { "FREEPDB1" },
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "SQLCORE" },
    PolicyRevision = "oracle26ai-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Also explicitly grant execute_ddl_sql to the relevant MCP access key.
```

```sql
-- DBA-run setup for the designated SQLCORE account in the target PDB.
GRANT SELECT ON SYS.V_$DATABASE TO SQLCORE;
GRANT SELECT ON SYS.V_$PDBS TO SQLCORE;
GRANT SELECT ON SYS.DBA_TRIGGERS TO SQLCORE;
GRANT EXECUTE ON SYS.DBMS_LOCK TO SQLCORE;
```

Der Host muss die tatsächliche Oracle-26ai-Version (Kernel ab 23.26), eine schreibbare primäre PDB, die freigegebene PDB und das Benutzerschema, vollständige Sicht auf DDL-Trigger sowie einen noch nicht vorhandenen Objektnamen nachweisen. Die Vorschau schreibt nichts. Nach der Freigabe nimmt der Host eine nur für eigene Anforderungen wirksame Sitzungssperre, prüft die Metadaten erneut, führt genau einmal das von SqlCore kompilierte SQL aus und kontrolliert die Spalten. **Fremde DDL-Clients werden dadurch nicht ausgeschlossen.**

Ist das Ergebnis nach dem Senden der DDL nicht nachweisbar, meldet der Host `outcome_unknown`. **Niemals automatisch wiederholen**; zuerst muss ein DBA den tatsächlichen PDB-Zustand prüfen. Die vier vorausgewählten Lesewerkzeuge bleiben ausgewählt, DML und DDL bleiben abgewählt.

## G6: PostgreSQL – Löschen einer nachweislich leeren Tabelle (separate Freigabe)

Das bestehende Werkzeug `execute_ddl_sql` erlaubt genau eine destruktive Ausnahme: ein unabhängig genehmigtes `DROP TABLE schema.table RESTRICT` unter PostgreSQL. Diese Funktion ist **standardmäßig deaktiviert** und erbt weder additive DDL- noch DML-Berechtigungen. Nach COMMIT ist die Tabellendefinition dauerhaft gelöscht; Tabellen mit Daten dürfen nicht gelöscht werden.


```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

services.AddHsSqlAgentPostgresDdl(new PostgresDdlExecutionOptions
{
    Enabled = true,
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "staging_cleanup" },
    AllowDropEmptyTable = true, // false by default; separate destructive opt-in
    PolicyRevision = "postgres-g6-destructive-governance-v1"
});
services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Separately grant execute_ddl_sql on the target MCP access key.
```

Vor der Ausführung prüft der PostgreSQL-Host das erlaubte Schema, den direkten Tabelleneigentümer, eine gewöhnliche permanente Tabelle mit 1–16 INTEGER-Spalten und das **Fehlen von Zeilen, Indizes, Constraints, abhängigen Views, Triggern, Row-Level-Security, Standardwerten, Vererbung, Publikationen und nicht nachgewiesenen Effekten**. Die Vorschau ist ausschließlich lesend. Nach unabhängiger menschlicher Freigabe nimmt die Transaktion eine `ACCESS EXCLUSIVE`-Sperre, prüft Tabellen-OID und Bedingungen erneut, führt nur das kompilierte `RESTRICT`-DDL aus und bestätigt das Entfernen vor COMMIT. Nur ein bestätigter Rollback beweist den Nichtabschluss. Bei unklarem COMMIT oder Rollback lautet das Ergebnis `outcome_unknown`; **niemals automatisch erneut ausführen**. `CASCADE`, `IF EXISTS`, nichtleere Tabellen, andere Datenbanken und DDL-Batches bleiben gesperrt. Die vier schreibgeschützten Standardwerkzeuge bleiben unverändert vorausgewählt.
