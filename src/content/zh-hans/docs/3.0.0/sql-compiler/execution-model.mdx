## 有界编译与结构证据

输入超过 4,194,304 个 UTF-16 单元、131,072 个非 End 词法 token、8,192 层括号分组或 65,536 个 AST 节点时，编译会拒绝。迭代式 AST 遍历与有界渲染在六种提供程序上保持参数顺序及无法证明安全即拒绝的原则，不保证任意深度的 SQL 都能通过。

资源上限包含每阶段 8,000,000 工作单元、每次编译 32,000,000 工作单元、每阶段 30 秒、每次编译 90 秒，以及每阶段累计 536,870,912 字节托管内存分配。这些是编译预算，不是数据库查询超时或进程内存上限；超限会返回带类型的资源诊断。

可选的不可变 schema snapshot 解析表名、列名及可证明的类型族，包含有序 CTE／派生查询投影，并将摘要绑定到计划指纹。这是有限范围的证明，并非完整数据库类型检查器。带 schema 证据的 DML 需要实时 freshness verifier；证据缺失或结构已变化时拒绝执行。默认不采集快照；`AddHsSqlAgentNativeDmlSchemaFreshness()` 提供需显式启用的原生支持。

hs-sql-agent 不会把 AI 生成的 SQL 直接当作可信命令执行。SQL 在真正执行前会经过解析、验证、功能支持检查、访问策略检查以及面向目标数据库的编译。

## 查询执行路径

查询大致按照以下顺序处理：

1. 验证 MCP 密钥，并应用该密钥限定的数据库、表、工具和运行时权限范围。
2. 把受支持的 SQL 解析为结构化定义 / AST。
3. 验证语句以及输入 SQL 的语义是否处于支持范围内。
4. 检查目标数据库是否能够安全表达保持这些语义所需的功能。
5. 为已配置的数据库编译并生成对应 SQL。
6. 在配置的运行时限制内执行 SQL。

SQL 编译器明确区分输入语义验证和目标数据库功能支持检查两个阶段。不支持的语法，或者无法确认能够安全保持相同语义的功能，会被直接拒绝，而不是静默替换为一个表面相似的结构。

## 为什么采用“失败即拒绝”（fail-closed）？

跨数据库 SQL 中有大量“看起来相同，实际含义不同”的结构，例如 NULL 行为、类型规则、运算符语义、分页、标识符、函数以及 DML 行为。

对于面向 AI 的执行入口，“尽力改写”很危险，因为 SQL 即使仍然语法正确，也可能已经改变原意。因此 hs-sql-agent 更愿意明确拒绝，也不会在后台偷偷降低语义保证。

## 按数据库生成 SQL

MCP 的公开接口是统一的，但最终 SQL 会针对不同数据库分别生成。目前支持的数据库包括：

- PostgreSQL
- MySQL
- SQL Server
- Oracle
- SQLite
- Firebird

支持范围是有意限定的。某个数据库出现在支持列表中，并不意味着该数据库提供的所有 SQL 语法都可以使用。只有当某项功能的语义能够被内部表示并验证时，编译器才会把它加入支持范围。

## GROUPS 窗口帧

PostgreSQL 11 及以上版本和 SQLite 3.28 及以上版本可以编译 `SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN 1 PRECEDING AND CURRENT ROW)` 这样的窗口帧。`GROUPS` 以排序键相同的行组为单位，而非按单行计数的 `ROWS` 或按排序值范围计算的 `RANGE`。窗口必须显式指定 `ORDER BY`。无效的帧边界、明确声明的过旧数据库版本都会被拒绝，也不会悄悄降级为其他帧类型。MySQL、SQL Server、Oracle 和 Firebird 暂不开放该能力。执行前仍须由宿主验证实际数据库版本。

## EXCLUDE：窗口帧的行排除规则

PostgreSQL 11 及以上版本和 SQLite 3.28 及以上版本可以在 `ROWS`、`RANGE` 或 `GROUPS` 帧后使用四种排除方式。`EXCLUDE CURRENT ROW` 只排除当前行；`EXCLUDE GROUP` 排除当前行及排序键相同的所有同行；`EXCLUDE TIES` 保留当前行，排除其他排序键相同的行；`EXCLUDE NO OTHERS` 不排除任何行。例如：`SUM(amount) OVER (ORDER BY grp GROUPS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW EXCLUDE TIES)`。即使采用 `ROWS` 帧，排除规则也会识别排序键相同的行。F# 编译器与 `WindowFrameDefinition.Exclusion` 会保留原有语义，不进行隐式改写。明确声明的过旧版本以及其他四种数据库提供程序都会被拒绝。执行前仍需由 Host 验证数据库实际版本。

## SQL Server 的 RANGE 窗口帧偏移限制

SQL Server 的 T-SQL 语法不允许在 `RANGE` 窗口帧中使用数值型 `PRECEDING` 或 `FOLLOWING` 偏移。例如，即使将 PostgreSQL 或 SQLite 设为目标数据库，`RANGE BETWEEN 1 PRECEDING AND CURRENT ROW` 仍会因为**源 SQL Server 语法无效**而被拒绝。合法的 `ROWS` 偏移以及 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` 仍受到支持；PostgreSQL 和 SQLite 原生的数值型 `RANGE` 语义不受影响。编译器会分别验证源方言和目标数据库能力，不会将目标数据库支持某种语法视为源语法有效的证明。

## MySQL 和 SQL Server 目标端的条件 COUNT

以 PostgreSQL 为源方言的 `SELECT COUNT(*) FILTER (WHERE status = 1) FROM orders` 现在可以安全编译至 MySQL 或 SQL Server。MySQL 使用 `COUNT(CASE WHEN ... THEN 1 END)`，SQL Server 使用 `COUNT_BIG(CASE WHEN ... THEN 1 END)`，从而保留 64 位计数范围。直接列的 `COUNT(列)` 也受到支持，并保持 NULL 不计数、没有匹配行时返回零以及窗口帧内的条件计数语义。

**这并不意味着全面支持 FILTER**：仅允许不带限定名的 `COUNT(*)`、直接本地列计数，以及非窗口聚合的 `COUNT(DISTINCT 直接列)`，并要求可证明的简单列／常量条件。`SUM`、计算表达式参数、子查询、易变函数和外层引用仍会被拒绝。以 MySQL／SQL Server 方言直接输入的 `FILTER` SQL 仍是无效源语法；该转换仅适用于合法源方言（例如 PostgreSQL）。SqlCore 不执行 SQL，也不授予数据库权限。

## 条件式 DISTINCT COUNT：只统计符合条件的不重复值

合法 PostgreSQL 源 SQL 中的 `COUNT(DISTINCT amount) FILTER (WHERE status = 1)` 现在可以编译成 MySQL 的 `COUNT(DISTINCT CASE WHEN status = 1 THEN amount END)`，或 SQL Server 的 `COUNT_BIG(DISTINCT CASE WHEN status = 1 THEN amount END)`。相同的值只计算一次；NULL、条件为假或未知的行不计数，没有符合条件的值时返回零。该能力使用 PostgreSQL 16、MySQL 8.4、SQL Server 2022 的真实数据库对分组和整体整数计数进行了测试。

DISTINCT 仅允许一个直接本地列参数，筛选条件必须受到有界证明。计算表达式参数、多个 DISTINCT 参数、子查询、易变函数和外层引用仍被拒绝。**不支持带 `OVER (...)` 的 DISTINCT 窗口聚合**，因为 MySQL 与 SQL Server 均不提供该语法。MySQL／SQL Server 源 SQL 中的 `FILTER` 仍无效；整型测试也不代表字符串排序规则或跨数据库类型转换一定等价。此功能不执行 SQL，也不授予数据库权限。
