## 审批准入、不确定结果与目标证据

要求选择性条件时，能够证明恒真的 `UPDATE`／`DELETE` 条件（例如 `WHERE 1=1`）会被拒绝。人工审批仍必须绑定精确计划与行集合证据。

自定义 challenge store 必须为单条和批量操作原子实现 `TryPromoteAsync`。Redis 与持久化续行使用版本化信封；不兼容的 challenge 必须重新预览与审批。参见[升级指南](/zh-hans/docs/reference/upgrade-guide)。

`dml.commit_outcome_unknown` 与 `dml.rollback_outcome_unknown` 是不同且不可重试的结果。请保留审批和目标证据并独立核查。缺少 witness 或 Redis key 都不能证明已经回滚，不可自动重放结果不明的变更。已确认提交后，即使审计持久化失败，也不能报告变更失败。

`AddHsSqlAgentTargetExecutionFence()` 需要显式启用，预先准备目标表及权限，并另行证明旧 worker 已失去 DML 权限。每次受管提交都在实际连接上执行两个额外的仅回滚就绪验证事务，提交后独立读取 Admission 与 Witness 各一次。Oracle 仅在 witness 唯一键冲突诊断中使用 READ COMMITTED，其他就绪阶段使用 SERIALIZABLE。证据矛盾时返回不确定结果；这不提供整个集群的节点纳管证明，也不自动处理仍存活的 worker。

DML 比 Query 使用更严格的执行路径，因为真正 commit 时，审批内容仍必须描述**同一份 Mutation Evidence**。

## 一个 Tool，同时支持单语句与多语句

`execute_dml_sql` 可以接受一个或多个受支持的 `UPDATE`、`DELETE`、`INSERT ... VALUES`，多个 Statement 用分号分隔。

没有额外的 batch DML Tool。多语句输入会解析成一个 Batch，只审批一次，按原始顺序执行，最后在一个由服务器掌握的 Transaction 中原子提交。

Client 不能传入 `BEGIN`、`COMMIT`、`ROLLBACK` 等 Transaction-control SQL；事务边界由服务器掌握。

## 审批绑定的内容

`UPDATE` / `DELETE` 审批绑定 Preview 时观察到的精确 Primary Key Row Set。Commit Transaction 内每个 Statement 在真正修改前都会立即重新验证。

`INSERT ... VALUES` 审批绑定不可变的 Literal Payload 与精确编译 Command。`INSERT ... SELECT` 在来源 Row Set 审批语义定义完成前仍不开放。

如果前一个 Statement 改变了后一个 Statement 原本获批的 Row Set，整个 Batch 会 fail closed 并 rollback。

## 审批 Provider

MCP Elicitation 仍是第一方默认 Provider。Host 也可以使用官方 `HsSqlAgent.Approvals.Webhook` adapter，或在 `HsSqlAgent.Server` 实现 `IDmlApprovalProvider`。

审批 Provider 收到的是与传输方式无关的 Evidence，不是 SQL 执行 primitive；不会取得 Database Connection、Transaction、已验证 Plan 或 commit 权限。

## Durable Pending Approval

Provider 可以为异步流程返回 `Pending`。存在 Admin Store 时，hs-sql-agent 会保存受保护的 Resume Intent 与 Approval Fingerprint。

之后收到完成决策时，服务器会重新加载当前授权与数据库配置、重新 Parse / Preview DML、比对审批 Evidence，再创建新的短效 Execution Challenge。授权、数据库配置、Policy、Plan、Row Set 或 affected-row Evidence 只要变化，就会被视为 stale 而不是 commit。

完成流程恢复的是**执行意图**，不是旧 Database Session。

## SQL Server：CTE 更新与删除的复合 INT 键

SQL Server 的 UPDATE／DELETE 在明确授权的前提下，可以通过 1～3 层线性、非递归 CTE 读取物理源表，但必须事先验证源表具有**由两个非空 INT 列组成的主键或唯一索引**。两个键列必须按物理索引中的顺序，在每层 CTE 中原样投影。最终修改语句必须通过强制性的 `AND` 与普通 `=`，分别匹配目标表的两个 INT 列。执行前还需要验证真实数据库元数据、预览受影响行、绑定审批内容，并在实际提交事务内重新检查元数据。

缺少或颠倒键列、仅通过 `OR` 匹配、类型转换、可空或计算列、筛选或禁用的索引，以及会增加匹配行数的连接，都会被拒绝。该能力不会扩展其他数据库的可执行范围。

### CTE 投影可以包含非键列（G8／M03）

1～3 层 CTE 除了必需的 1～2 列 INT 键，也可以同时投影**直接来自源数据行的其他列**，每层最多 32 列。例如先使用 `SELECT k1 AS a, payload AS extra, k2 AS b`，再使用 `SELECT a, extra, b`。键列在每一层都必须各出现一次，保持物理唯一索引中的相对顺序，最终仍须使用必要的 `AND` 和普通 `=` 匹配。重复、转换或计算键、别名歧义、多来源以及可能增加行数的 JOIN 均被拒绝。真实唯一索引检查、预览、审批和提交事务中的重新验证保持不变；此功能不等于支持普通 JOIN，也不改变其他数据库的执行范围。

### 单行 JOIN 的安全证明（G8／M07，受限子集）

SQL Server 的每层 CTE 现在最多可以额外使用一个**可证明不会增加行数的 JOIN**：连接来源必须是完全独立的 `SELECT 1 AS marker` 派生查询，不包含 `FROM`、`WHERE`、`UNION`、分组或其他行。`CROSS JOIN (SELECT 1 AS marker) AS one` 保持源行数；使用常量等式 `ON 1 = 1` 的 `INNER JOIN`／`LEFT JOIN` 同样不会增加行数。物理 INT 唯一键、原样键列投影、预览、审批和提交事务内的实时证明仍然必需。**这不意味着支持一般物理表 JOIN、APPLY、相关子查询、多行派生源或任意 JOIN。**

## Fail-closed 规则

审批被拒绝、过期、stale、Fingerprint 不匹配、权限被撤销、违反当前 Policy，或无法重现审批 Row Set 时，都不会提交 DML。
