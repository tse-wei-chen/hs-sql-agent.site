## 审批准入、不确定结果与目标证据

要求选择性条件时，能够证明恒真的 `UPDATE`／`DELETE` 条件（例如 `WHERE 1=1`）会被拒绝。人工审批仍必须绑定精确计划与行集合证据。

自定义 challenge store 必须为单条和批量操作原子实现 `TryPromoteAsync`。Redis 与持久化续行使用版本化信封；不兼容的 challenge 必须重新预览与审批。参见[升级指南](/zh-hans/docs/reference/upgrade-guide)。

`dml.commit_outcome_unknown` 与 `dml.rollback_outcome_unknown` 是不同且不可重试的结果。请保留审批和目标证据并独立核查。缺少 witness 或 Redis key 都不能证明已经回滚，不可自动重放结果不明的变更。已确认提交后，即使审计持久化失败，也不能报告变更失败。

`AddHsSqlAgentTargetExecutionFence()` 需要显式启用，预先准备目标表及权限，并另行证明旧 worker 已失去 DML 权限。每次受管提交都在实际连接上执行两个额外的仅回滚就绪验证事务，提交后独立读取 Admission 与 Witness 各一次。Oracle 仅在 witness 唯一键冲突诊断中使用 READ COMMITTED，其他就绪阶段使用 SERIALIZABLE。证据矛盾时返回不确定结果；这不提供整个集群的节点纳管证明，也不自动处理仍存活的 worker。

DML 比 Query 使用更严格的执行路径，因为真正 commit 时，审批内容仍必须描述**同一份 Mutation Evidence**。

## 一个 Tool，同时支持单语句与多语句

`execute_dml_sql` 可以接受一个或多个受支持的 `UPDATE`、`DELETE`、`INSERT ... VALUES`，多个 Statement 用分号分隔。

没有额外的 batch DML Tool。多语句输入会解析成一个 Batch，只审批一次，按原始顺序执行，最后在一个由服务器掌握的 Transaction 中原子提交。

Client 不能传入 `BEGIN`、`COMMIT`、`ROLLBACK` 等 Transaction-control SQL；事务边界由服务器掌握。

## 审批绑定的内容

`UPDATE` / `DELETE` 审批绑定 Preview 时观察到的精确 Primary Key Row Set。Commit Transaction 内每个 Statement 在真正修改前都会立即重新验证。

`INSERT ... VALUES` 审批绑定不可变的 Literal Payload 与精确编译 Command。`INSERT ... SELECT` 在来源 Row Set 审批语义定义完成前仍不开放。

如果前一个 Statement 改变了后一个 Statement 原本获批的 Row Set，整个 Batch 会 fail closed 并 rollback。

## 审批 Provider

MCP Elicitation 仍是第一方默认 Provider。Host 也可以使用官方 `HsSqlAgent.Approvals.Webhook` adapter，或在 `HsSqlAgent.Server` 实现 `IDmlApprovalProvider`。

审批 Provider 收到的是与传输方式无关的 Evidence，不是 SQL 执行 primitive；不会取得 Database Connection、Transaction、已验证 Plan 或 commit 权限。

## Durable Pending Approval

Provider 可以为异步流程返回 `Pending`。存在 Admin Store 时，hs-sql-agent 会保存受保护的 Resume Intent 与 Approval Fingerprint。

之后收到完成决策时，服务器会重新加载当前授权与数据库配置、重新 Parse / Preview DML、比对审批 Evidence，再创建新的短效 Execution Challenge。授权、数据库配置、Policy、Plan、Row Set 或 affected-row Evidence 只要变化，就会被视为 stale 而不是 commit。

完成流程恢复的是**执行意图**，不是旧 Database Session。

## SQL Server：CTE 更新与删除的复合 INT 键

SQL Server 的 UPDATE／DELETE 在明确授权的前提下，可以通过 1～3 层线性、非递归 CTE 读取物理源表，但必须事先验证源表具有**由两个非空 INT 列组成的主键或唯一索引**。两个键列必须按物理索引中的顺序，在每层 CTE 中原样投影。最终修改语句必须通过强制性的 `AND` 与普通 `=`，分别匹配目标表的两个 INT 列。执行前还需要验证真实数据库元数据、预览受影响行、绑定审批内容，并在实际提交事务内重新检查元数据。

缺少或颠倒键列、仅通过 `OR` 匹配、类型转换、可空或计算列、筛选或禁用的索引，以及会增加匹配行数的连接，都会被拒绝。该能力不会扩展其他数据库的可执行范围。

### BIN2 VARCHAR／NVARCHAR 物理文本键的精确证明（G9／M04，仅 develop）

SQL Server CTE `UPDATE`／`DELETE` 的物理唯一键证明新增有限长度的内置 `VARCHAR(n)` 和 `NVARCHAR(n)`，**仅允许实际排序规则 `Latin1_General_100_BIN2`**。来源 UNIQUE 索引、目标比较列以及独立验证的第二个 JOIN 来源，必须在**每个键位置**同时匹配 SQL 原生类型、最大长度和排序规则。`NVARCHAR` 先按照 `sys.columns.max_length` 的字节数验证，再换算为声明字符数。此能力并不允许所有文本键：`VARCHAR(MAX)`、`NVARCHAR(MAX)`、`CHAR`、`NCHAR`、长度差异、Unicode/非 Unicode 隐式转换、其他二进制或不区分大小写的排序规则、自定义别名类型和可空来源键均会被拒绝。

Host 使用已有的 `SqlSchemaValueKind.Text` 记录真实文本类型，但**快照中的 Text 声明绝不能单独授权执行**。F# 封闭键类型独立验证实际列长度与排序规则、内置类型身份、完整且启用的无筛选 UNIQUE 索引，以及受限 CTE／JOIN 的必要普通等号关系。Preview→独立 Approval→Commit 仍在实际提交事务中持锁重新验证物理元数据；ProofIdentity 升至 v7，旧审批不可重用。SQL Server 2022 实测覆盖文本与 UUID／整数／小数复合键、UPDATE／DELETE、1～3 层 CTE、self/跨表 JOIN、审批提交及索引撤销，并验证排序规则或长度不匹配必须拒绝。其他五个数据库、MCP 工具和默认权限不变。


### CTE 投影可以包含非键列（G8／M03）

1～3 层 CTE 除了必需的 1～2 列 INT 键，也可以同时投影**直接来自源数据行的其他列**，每层最多 32 列。例如先使用 `SELECT k1 AS a, payload AS extra, k2 AS b`，再使用 `SELECT a, extra, b`。键列在每一层都必须各出现一次，保持物理唯一索引中的相对顺序，最终仍须使用必要的 `AND` 和普通 `=` 匹配。重复、转换或计算键、别名歧义、多来源以及可能增加行数的 JOIN 均被拒绝。真实唯一索引检查、预览、审批和提交事务中的重新验证保持不变；此功能不等于支持普通 JOIN，也不改变其他数据库的执行范围。

### 单行 JOIN 的安全证明（G8／M07，受限子集）

SQL Server 的每层 CTE 现在最多可以额外使用一个**可证明不会增加行数的 JOIN**：连接来源必须是完全独立的 `SELECT 1 AS marker` 派生查询，不包含 `FROM`、`WHERE`、`UNION`、分组或其他行。`CROSS JOIN (SELECT 1 AS marker) AS one` 保持源行数；使用常量等式 `ON 1 = 1` 的 `INNER JOIN`／`LEFT JOIN` 同样不会增加行数。物理 INT 唯一键、原样键列投影、预览、审批和提交事务内的实时证明仍然必需。**仅凭上述单行／自连接证明仍不能连接其他物理表；下文另以双重物理唯一键验证开放有限范围、APPLY、相关子查询、多行派生源或任意 JOIN。**

另一种受限形式允许**同一物理源表使用不同别名进行 INNER／LEFT 自连接**，但 ON 条件必须通过必要的 AND 和普通等式完整匹配**在实际数据库中验证的每个 INT 唯一键列**。因此第二个别名对每行源数据最多匹配一行。缺少键列、仅通过 OR、计算或转换键，以及连接其他表均会被拒绝。

### 跨物理表 JOIN 的双重唯一键证明（M07）

SQL Server CTE 现在允许通过一次 **INNER** 或 **LEFT JOIN** 连接另一张物理表。两个源表都必须分别通过真实数据库的唯一键验证：1～2 列非空 `INT`／`BIGINT`，索引必须启用且未经过筛选。JOIN 的 `ON` 条件必须通过必要的 `AND` 和普通 `=` 完整匹配两侧的每个键列，且各位置的实际类型必须完全相同。虚拟目录、隐式类型转换、仅匹配部分键或筛选索引均不能构成证据。两个索引的身份均绑定执行计划和审批，并在实际提交事务中再次验证；预览后撤销任一证据都会阻止提交。这不代表开放第三张来源表、多对多 JOIN、`RIGHT`／`FULL JOIN`、跨数据库方言转换或任意 JOIN。

### 完整键关联的 EXISTS／NOT EXISTS 筛选（M07，受限阶段）

SQL Server 的 CTE `UPDATE`／`DELETE` 可以在第一层 CTE 的 `WHERE` 使用 **`EXISTS`（半连接）或 `NOT EXISTS`（反连接）**，但子查询只能用另一别名读取**同一张已完成物理唯一键验证的源表**。子查询仅投影常量，不允许增加 JOIN、分组、排序或集合运算，且必须通过必要的 `AND` 与普通 `=` 完整关联 1～2 个 `INT`／`BIGINT` 唯一键列；还可用子查询列与常量的比较进一步筛选。这种条件只保留或排除源行，不会增加行数；现有的真实索引证明、预览、审批身份绑定和提交事务中的重新验证仍然必需。**并未开放任意嵌套子查询、未验证的其他表或通用的 EXISTS／反连接执行权限。**

### TINYINT 与 SMALLINT 物理键的精确类型证明（G9／M04，仅 develop）

SQL Server 的 CTE `UPDATE`／`DELETE` 物理唯一键证明，现在除了 `INT`、`BIGINT`，也支持内置 `TINYINT`（无符号 8 位）和 `SMALLINT`（有符号 16 位）。对于一列或两列的物理唯一键，来源列、目标比较列以及独立验证的 JOIN 列，**在每个索引键位置的实际 SQL Server 类型必须完全一致**。整数类型的隐式转换、自定义别名类型或虚拟目录都不能替代物理证据。原有的受限 CTE 键传递、不会增加行数的 JOIN 证明、影响行预览、独立审批、不可变计划指纹以及实际提交事务中的索引重新验证仍然必需。SQL Server 2022 测试覆盖更新、删除、混合键类型和索引撤销。本次扩展不开放 DECIMAL、UUID、可空唯一键、任意 JOIN 或其他数据库的执行权限。


### UNIQUEIDENTIFIER 物理键的精确证明（G9／M04，仅 develop）

SQL Server 的 CTE `UPDATE`／`DELETE` 现在支持**内置 128 位 `UNIQUEIDENTIFIER` 键**的物理证明。`Uuid` 是独立的架构值类型，**不能假装成 Numeric、文本或二进制键**。Host 读取实际 `sys.tables`、`sys.columns`、`sys.types` 元数据，为源表、目标表及可选的第二张独立验证 JOIN 表建立有类型的键快照。F# 封闭类型再次验证完整 UNIQUE 索引中的每个键位置，以及快照声明与物理类型的一致性。不得通过隐式转换，将 `UNIQUEIDENTIFIER` 与 `INT`、`DECIMAL`、`VARCHAR`、`BINARY(16)` 的比较当作执行授权证据。

一列或两列复合键可以混合 UUID 和经精确验证的整数／小数键；原有 1～3 层受限 CTE、不增加行数的 JOIN、变更预览、独立审批及提交事务内的 `IsCurrent` 重新验证仍然有效。ProofIdentity 升至 v6，旧审批证据不能重用。SQL Server 2022 实测覆盖 UUID UPDATE／DELETE、主键和唯一索引、Host 自动发现、跨表 JOIN、预览后索引撤销及错误类型拒绝。此功能不新增 MCP 工具、不默认启用 DML、不开放任意 JOIN，也不改变其他五个数据库。

### DECIMAL／NUMERIC 物理键的精确证明（G9／M04，仅 develop）

SQL Server 的 CTE `UPDATE`／`DELETE` 物理唯一键证明现在也支持内置 `DECIMAL(p,s)` 和 `NUMERIC(p,s)`，其中 `1 ≤ p ≤ 38`、`0 ≤ s ≤ p`。这两个名称在 SQL Server 中是同义类型，但来源键、目标比较列以及经过独立验证的 JOIN 来源键，**在每个索引键位置的精度与小数位数必须完全一致**。`DECIMAL(12,2)` 不能通过隐式转换证明与 `DECIMAL(13,2)`、`DECIMAL(12,3)` 或整数键等价。

Host 会读取实际 `sys.columns` 与 `sys.types` 元数据，并完整检查原始 UNIQUE 索引中的**所有键列**；即使某列使用不支持的自定义别名类型，也绝不能把 `UNIQUE(a,b)` 错当作 `UNIQUE(a)`。F# 封闭类型保留精确精度和小数位数。原有的 1～3 层受限 CTE、不会增加行数的 JOIN 证明、受影响行预览、独立审批、带版本的证明身份以及实际提交事务中的重新验证都不变。SQL Server 2022 实测覆盖小数值、混合整数／小数键、跨物理表 JOIN、索引撤销和精度／位数不匹配拒绝。此证明不开放 UUID／文本键、可空唯一键、任意 JOIN 或其他五种数据库的执行权限。


## Fail-closed 规则

审批被拒绝、过期、stale、Fingerprint 不匹配、权限被撤销、违反当前 Policy，或无法重现审批 Row Set 时，都不会提交 DML。
