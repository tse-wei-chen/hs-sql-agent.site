## 必需的机密保护配置

启动 Docker 或注册运行时前，请配置三组独立、随机生成的 32 字节 Base64 机密。所有节点必须使用相同密钥，重启后也必须保留。`HMAC_KEY` 与 `JWT_KEY` 仍为独立的签名机密。请分别运行三次 `openssl rand -base64 32`。

| Docker 环境变量 | ASP.NET Core 配置 |
| --- | --- |
| `DB_ENCRYPTION_KEY` | `SecretProtection:DatabasePasswords:Keys:db-1` |
| `DML_ENCRYPTION_KEY` | `SecretProtection:DmlPayloads:Keys:dml-1` |
| `DML_FINGERPRINT_KEY` | `SecretProtection:DmlFingerprintKey` |

将 `SecretProtection:DatabasePasswords:ActiveKeyId` 设为 `db-1`，`SecretProtection:DmlPayloads:ActiveKeyId` 设为 `dml-1`。缺失、无效或重复使用的密钥会导致启动失败；示例占位值故意设为无效。

`HsSqlAgent.Hosting` 自动绑定 `SecretProtection`；模块化宿主必须显式绑定：

```csharp
hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
```

新 bootstrap MCP 密钥必须显式提供 `Bootstrap:Databases:*:McpKeys:*:Key`，启动时不再生成或记录密钥。现有加密数据库密码必须重新输入。更改现有部署前，请阅读[升级指南](/zh-hans/docs/reference/upgrade-guide)。

多个模块可在同一 `IServiceCollection` 上调用 `AddHsSqlAgentCore()`。各项能力仅接受首次注册时的配置，后续覆盖会失败；不同服务集合仍彼此隔离。

ASP.NET Core 应用有两个 NuGet 入口。请根据“宿主需要掌握哪些边界”来选择，而不是把两个包当成同一层级的别名。

| 目标 | 包 | 边界 |
| --- | --- | --- |
| 嵌入完整产品 | `HsSqlAgent.Hosting` | HsSqlAgent 负责标准运行时、Admin Store、内置身份系统、MCP、管理 API/界面、遥测、异常处理和审批提供程序选择。 |
| 构建定制集成 | `HsSqlAgent.Server` | 应用自行选择能力，可以保留已有身份验证、授权、前端、中间件顺序、遥测或审批提供程序。 |

如果要把 hs-sql-agent 作为独立服务运行，而不是嵌入 .NET 宿主，请直接使用官方 Docker 镜像。

## 使用 HsSqlAgent.Hosting 嵌入完整产品

安装完整主机包：

```bash
dotnet add package HsSqlAgent.Hosting
```

添加并启用标准主机：

```csharp
using HsSqlAgent.Hosting;

var builder = WebApplication.CreateBuilder(args);
builder.AddHsSqlAgentStandardHost();

var app = builder.Build();
app.UseHsSqlAgentStandardHost();
await app.RunAsync();
```

这与官方 ToolBox / Docker 主机使用相同的第一方能力组合和配置契约。URL 绑定与日志仍由常规 ASP.NET Core 宿主负责。

`HsSqlAgent.Hosting` 会带入标准 `HsSqlAgent.Server` 运行时和官方 `HsSqlAgent.Approvals.Webhook` 适配器；它不会加入运行时 NuGet 或 DLL 插件加载机制。

### 选择 DML 审批提供程序

MCP Elicitation 仍是默认的第一方审批方式：

```json
{
  "DmlApproval": {
    "Provider": "McpElicitation"
  }
}
```

要使用官方通用 Webhook 适配器：

```json
{
  "DmlApproval": {
    "Provider": "Webhook",
    "Webhook": {
      "Endpoint": "https://approval.example.com/hssqlagent/requests",
      "CallbackUrl": "https://sql-agent.example.com/api/hs-sql-agent/approvals/webhook",
      "SigningSecret": "replace-with-a-unique-secret-at-least-32-bytes"
    }
  }
}
```

环境变量使用 ASP.NET Core 常规命名，例如 `DmlApproval__Provider=Webhook`。未知的 provider 名称会在启动时直接失败。

如果需要自定义 `IDmlApprovalProvider`，请使用 `HsSqlAgent.Server` 并通过依赖注入注册。审批系统不会获得任意执行 SQL 的权限：SQL 验证、审批 fingerprint 绑定、当前状态重新验证和最终 commit 仍由 HsSqlAgent 负责。

## 使用 HsSqlAgent.Server 构建定制集成

安装模块化包：

```bash
dotnet add package HsSqlAgent.Server
```

已有应用可以保留自己的身份验证与授权，只加入所需的 HsSqlAgent 能力：

```csharp
var hs = builder.Services.AddHsSqlAgentCore();

hs.AddHsSqlAgentRuntime(options =>
{
    builder.Configuration.GetSection("SecretProtection").Bind(options.SecretProtection);
});
hs.AddHsSqlAgentAdminStore(options =>
{
    options.Provider = "Postgres";
    options.ConnectionString =
        builder.Configuration.GetConnectionString("HsSqlAgent")!;
});
hs.AddHsSqlAgentHostAuthorization("SqlAgentAdmin");
hs.AddHsSqlAgentAdminApi();
```

ASP.NET Core 管线仍由宿主管理：

```csharp
var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();
app.UseHsSqlAgentAdminApi();
app.MapControllers();

app.Run();
```

使用宿主授权时不要调用 `AddHsSqlAgentBuiltInAuth()`。HsSqlAgent 直接使用已验证的 `HttpContext.User`，不发布内置身份控制器，也不安装 HsSqlAgent 身份结构。

`/runtime/db-management.edit`、`/auth/role.view` 这类 canonical permission 是稳定的授权资源标识，不是路由。宿主策略可以把它们映射到已有权限模型。

### 需要 MCP 时再加入

MCP 仍是独立的机器访问安全边界：

```csharp
hs.AddHsSqlAgentMcp(options =>
{
    options.PublicEndpoint = "https://example.com/mcp";
    options.HmacSecretKey = builder.Configuration["HMAC_KEY"]!; // >= 32 bytes
});
```

构建应用后再挂载：

```csharp
app.UseHsSqlAgentMcp();
```

MCP 密钥、工具范围、数据表范围、速率限制和 HMAC 验证，都与人员/管理端授权策略分开。

### 确实需要时才使用内置身份系统

如果宿主要使用 HsSqlAgent 自己的 JWT/member/role 模型，请选择内置身份验证，而不是宿主授权：

```csharp
hs.AddHsSqlAgentBuiltInAuth(options =>
{
    options.Jwt.SecretKey = builder.Configuration["JWT_KEY"]!; // >= 32 bytes
});
```

内置身份与宿主授权互斥；模块化宿主也可以选择不挂载内置管理界面。

## 能力与配置职责

| 能力 | 负责内容 |
| --- | --- |
| `AddHsSqlAgentRuntime()` | 运行服务、可观测运行状态、协调机制、SQL 并发和 DML 审批持久化 |
| `AddHsSqlAgentAdminStore()` | Admin database provider 与连接字符串 |
| `AddHsSqlAgentBuiltInAuth()` | JWT、密码重置/SMTP、企业身份/OIDC |
| `AddHsSqlAgentHostAuthorization()` | 委托到现有 ASP.NET Core 授权策略 |
| `AddHsSqlAgentMcp()` | 公开 MCP 端点与 MCP key HMAC secret |
| `AddHsSqlAgentAdminApi()` | 管理控制器及控制器范围的验证/异常映射 |
| `AddHsSqlAgentTelemetry()` | Prometheus 与 OTLP 配置 |

未选择的能力不会分配或验证它的配置。

## 当前 HTTP 挂载位置

| 功能面 | 路径 |
| --- | --- |
| MCP endpoint | `/mcp` |
| Admin API prefix | `/api` |
| Admin UI | `/` |

在路由、前端基础路径/静态资源、callback 和安全边界能够一起移动之前，不宣告支持任意搬移这些路径。

## 兼容 API

已有包使用者仍可继续使用 `AddHsSqlAgent()` 与 `UseHsSqlAgent()`。新的集成应优先选择标准 `HsSqlAgent.Hosting` 入口，或使用 `AddHsSqlAgentCore()` 后明确注册能力。

## G5：MySQL 8.4 结构变更（必须明确启用）

MySQL InnoDB 的**单条结构变更原子性，不等于应用事务可以回滚**。普通 CREATE TABLE 会隐式提交，无法使用 ROLLBACK 撤销。现有 execute_ddl_sql 工具默认隐藏并拒绝执行；必须单独启用 MySQL，向 MCP 访问密钥明确授予工具权限，并配置独立的结构变更审批服务。

首阶段只允许单条、不带数据库前缀的 CREATE TABLE，包含 1–16 个基本有符号 INT 字段。不支持临时表、查询建表、默认值、约束、修改表、创建索引、删除或多语句执行。预览仅读取真实元数据；审批通过后重新验证 MySQL 8.4 服务器标识、许可的目标数据库、大小写规则、InnoDB 引擎和目标不存在的条件。随后只执行一次由 SqlCore 编译的原生语句，并核对实际字段。

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentMySqlDdl(new MySqlDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedDatabases = new HashSet<string>(StringComparer.Ordinal) { "app_database" },
    PolicyRevision = "mysql84-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
```

专用会话锁只协调本服务的请求，**不能阻止其他客户端修改结构**。执行开始后若无法确认结果，将返回 outcome_unknown；禁止自动重试，应先核对数据库实际状态。数据修改审批不能替代结构变更审批；四个默认只读工具及 DML／DDL 默认不勾选的行为保持不变。

## G5：Oracle 26ai 结构变更（必须明确启用）

Oracle 会在结构变更语句**执行前后隐式提交事务**。即使后续操作失败，也无法通过应用程序 ROLLBACK 撤销已创建的数据表。`execute_ddl_sql` 仍默认隐藏；必须单独启用 Oracle，向 MCP 访问密钥明确授予工具权限，并配置独立的结构变更审批人。

当前仅允许在登录用户自己的模式中执行**单条、不带模式前缀的 CREATE TABLE**，包含 1–16 个基本 INTEGER 字段。约束、默认值、ALTER、INDEX、DROP、查询建表和多语句全部拒绝。

```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

builder.Services.AddHsSqlAgentOracleDdl(new OracleDdlExecutionOptions
{
    Enabled = true,
    AllowCreateTable = true,
    AllowedPdbNames = new HashSet<string>(StringComparer.Ordinal) { "FREEPDB1" },
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "SQLCORE" },
    PolicyRevision = "oracle26ai-ddl-governance-v1"
});
builder.Services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Also explicitly grant execute_ddl_sql to the relevant MCP access key.
```

```sql
-- DBA-run setup for the designated SQLCORE account in the target PDB.
GRANT SELECT ON SYS.V_$DATABASE TO SQLCORE;
GRANT SELECT ON SYS.V_$PDBS TO SQLCORE;
GRANT SELECT ON SYS.DBA_TRIGGERS TO SQLCORE;
GRANT EXECUTE ON SYS.DBMS_LOCK TO SQLCORE;
```

宿主必须验证真实的 Oracle 26ai（23.26 及以上内核）、可写入的主 PDB、许可的 PDB 和用户模式、完整的 DDL 触发器字典权限，以及目标不存在。预览不会修改数据库。审批后使用仅协调本服务请求的会话锁，再次核对实体元数据，只执行一次 SqlCore 编译的原生 SQL，并检查实际字段；**不能排除其他客户端的并发变更**。

语句发送后若无法确认结果，将返回 `outcome_unknown`，**禁止自动重试**，应由数据库管理员先核对真实状态。四个默认只读工具继续选中，DML／DDL 默认仍不选中。

## G6：PostgreSQL 高风险删除空数据表（须单独启用）

现有的 `execute_ddl_sql` 工具只新增一项**破坏性例外操作**：在 PostgreSQL 上，经过独立审批后执行明确指定模式的 `DROP TABLE schema.table RESTRICT`。此功能**默认关闭**，不继承新增结构或数据修改权限。事务提交后，表结构将被永久删除；含数据的表一律禁止删除。


```csharp
using HsSqlAgent.Server.Extensions;
using HsSqlAgent.Server.Services;

services.AddHsSqlAgentPostgresDdl(new PostgresDdlExecutionOptions
{
    Enabled = true,
    AllowedSchemas = new HashSet<string>(StringComparer.Ordinal) { "staging_cleanup" },
    AllowDropEmptyTable = true, // false by default; separate destructive opt-in
    AllowedDropPrincipals = new HashSet<string>(StringComparer.Ordinal)
    {
        "mcp-key:123" // replace with authenticated MCP key identity
    },
    PolicyRevision = "postgres-g6-destructive-governance-v1"
});
services.AddSingleton<IDdlApprovalProvider, MyIndependentDdlApprovalProvider>();
// Separately grant execute_ddl_sql on the target MCP access key.
```

实际认证的 MCP 密钥身份还必须列入 `AllowedDropPrincipals`；只有普通的 `execute_ddl_sql` 权限**不能**授权破坏性删除。允许名单变更会使尚未执行的审批失效。

PostgreSQL 主机还必须证明当前用户为表所有者、模式在允许名单内，并且目标是包含 1–16 个 INTEGER 列的普通永久表，**不存在数据行、索引、约束、依赖视图、触发器、行级安全策略、默认值、继承、发布或其他未证实的影响**。预览仅读取实际元数据，不修改数据库。独立人工审批后，主机在 PostgreSQL 事务内取得 `ACCESS EXCLUSIVE` 锁，重新核实实际表 OID 和全部前置条件，只执行已编译的 `RESTRICT` 指令，确认表已不存在后提交。已确认的回滚意味着未提交；提交或回滚结果不明时返回 `outcome_unknown`，**禁止自动重试**。`CASCADE`、`IF EXISTS`、非空表、其他数据库和多语句 DDL 仍不开放。前端默认仍只选中四个只读工具；DML 和 DDL 均不预选。
